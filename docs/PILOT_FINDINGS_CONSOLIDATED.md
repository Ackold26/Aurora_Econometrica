> **Источник:** пилотный прогон Кагоцел РФ+ через Tauri dev окно с Антоном.

## P0 — Блокеры production

### B-01 Декомпозитор 500: holiday columns не найдены ⛔ блокер пилота

**Где:** шаг «Декомпозиция» после обучения модели.

**Симптом:** `Ошибка sidecar (500): "['holiday_newyear_preshop', 'holiday_newyear_postsale', 'holiday_valentine', 'holiday_defender_day', 'holiday_march8', 'holiday_may_holidays', 'holiday_russia_day', 'holiday_back_to_school', 'holiday_unity_day', 'holiday_black_friday', 'holiday_cyber_monday', 'holiday_school_breaks'] not in index"`

**Корень:** `modeler.py` инжектирует 12 holiday-колонок в X-матрицу при обучении (ADR-019 §5 РФ holidays). `decomposer.py` пытается их найти в **исходном** DataFrame (Excel) — но их там нет. Feature engineering leakage между этапами.

**Фикс:** в `decomposer.py` инжектировать holiday колонки в DataFrame через `holiday_calendar_ru.inject_holiday_features(df, date_col)` перед обработкой. Список колонок есть в `normalization.holiday_cols_injected` (поле v2.0.0).

### B-02 State propagation: 3 разных ratio одновременно

**Где:** под-шаг 2 «Роли колонок» Валидации.

**Симптом:** на одном экране три значения ratio:
- Sticky header: **1.4:1**
- RatioInfoCard: **2.8:1**
- Инсайты справа: **2.8:1**

**Корень:** `pipelineHeaderMetrics` derived store не subscribed на актуальные изменения `validateData` после frontend exclusions.

**Фикс:** Single source of truth — создать derived store `validationMetrics` в `project-state.js`. Все компоненты читают из него.

---

### B-03 Severity «моделирование невозможно» при ratio 2.8:1

**Где:** инсайты Валидации.

**Симптом:** «Критические проблемы с данными. Моделирование невозможно без исправления.» при ratio 2.8:1.

**Корень:** Категорично-ложное сообщение. При ratio 2.8 Bayesian модель технически обучится (проверено пилотом — она и обучилась с MQS=50).

**Фикс:** 5-уровневая градация severity, **никаких «невозможно» при ratio ≥ 2:1**:

| Ratio | Severity | Текст |
|---|---|---|
| < 2:1 | error | «Слишком мало данных - модель почти наверняка переобучится» |
| 2-3:1 | warning высокий | «Критически мало данных - модель ненадёжна» |
| 3-4:1 | warning | «Мало данных - широкие доверительные интервалы» |
| 4-5:1 | info | «Достаточно для пилота. Для production ≥4:1» |
| ≥ 5:1 | success | «Хорошее соотношение» |

### B-04 PerChannelInputSelector теряет каналы (5→1)

**Где:** под-шаг 4 «Подтверждение» (ModeDerivedExplanation).

**Симптом:** на Manager mode настроено 5 каналов (4 в ₽ + 1 TRP с CPP). После входа в Expert mode → подтверждения → переход к summary → показывает «Каналов: 1». Реально в модели 5 — баг сводки.

**Корень:** PerChannelInputSelector в Expert перезаписывает `perChannelInput` store, оставляя только последний явно выбранный канал. Manager-mode state не pre-fill в Expert.

**Фикс:** при входе в Expert mode — pre-fill PerChannelInputSelector ВСЕМИ текущими каналами из Manager state. При confirmation — merge, не replace.

## P1 — High priority UX

### U-01 «Далее» не активна в Manager mode на «Метрики каналов»

**Где:** под-шаг 3 «Метрики каналов» (AppliedModeSummary).

**Симптом:** все 5 каналов корректно настроены ✓, но global «Далее» неактивна. Пользователь обязан зайти в Expert mode и пройти PerChannelInputSelector чтобы активировать переход.

**Фикс:** добавить кнопку «Далее ▶» под AppliedModeSummary в Manager mode (как сделали для KPISelector в Партии rc1).

---

### U-02 Текст PerChannelInputSelector не mode-aware (50% неверен)

**Где:** Expert mode на «Метрики каналов».

**Симптом:** текст «выберите более надёжный источник: бюджет (₽) или физические контакты (показы, клики, GRP)» — представляет выбор как **равноправный**, но это **не так**:

- В ROI режиме физические контакты как самостоятельная метрика **невозможны** (нельзя посчитать ROI в TRP)
- В Эффективности рубли как самостоятельная метрика **не дают долей вклада**

**Фикс:** 3 версии текста (ROI / Эффективность / Mixed), каждая объясняет специфику режима. Также пересмотреть заголовок «Какие метрики каналов используем?» и WhyThisStep «Зачем это?».

---

### U-03 Рекомендации исключают важные каналы вместо конверсии

**Где:** под-шаг 2 «Роли колонок» Валидации.

**Симптом:** для Кагоцел рекомендовано исключить **TRPs бренд (W 25-54)** без парного бюджета и без data quality проблем. Также инсайт «Исключите 3 канала → ratio станет 3.9:1» предлагает убрать TRPs + OLV Бюджет + Banners Бюджет — это профессионально вредно.

**Корень:** Aurora фокусируется на math (ratio observations/parameters), игнорируя бизнес-валидность. ТВ — 30-70% медиа-бюджета OTC фармы. Модель без ТВ = omitted variable bias.

**Фикс:** иерархия ratio-fix:
1. **Объединение** коррелированных каналов (data preservation)
2. **Конверсия** физических метрик через CPP (data preservation)
3. **Сбор больше истории** (honest about limitation)
4. **Исключение каналов с >50% нулей** (data quality)
5. **Прочее исключение** — только с предупреждением «потеряете объяснительную силу для X% продаж»

Также — НИКОГДА не предлагать автоматическое исключение основных media каналов (ТВ, OLV, Banners для бренда) без явных проблем с данными.

### U-04 Финальный экран «Подтверждение» — слишком беден

**Где:** под-шаг 4 «Подтверждение» (ModeDerivedExplanation).

**Симптом:** 3 строки текста + 1 цифра в сводке. Не хватает:
- Таблица каналов с ролями + единицами + итогами
- Внешние факторы (controls)
- Исключённые колонки с причинами
- Контроль качества (ratio, период, VIF)
- Прогноз стабильности (MQS, ожидаемое R²)
- Время обучения

**Фикс:** переписать `ModeDerivedExplanation.svelte` (или новый `ValidationSummary.svelte`) с 5-7 секциями.

### U-05 Инсайты не контекстные на под-шаге «Целевая метрика»

**Где:** под-шаг 1 Валидации.

**Симптом:** инсайты показывают анализ каналов (Retail Media 64.5% нулей, и т.д.) — релевантно под-шагу 2, не текущему.

**Фикс:** разделить `validateInsights()` на 4 функции по под-шагам (kpi/roles/metrics/confirm). На «Целевая метрика» — инсайты про выбор режима и KPI:
- A. Подсказка режима из данных
- B. Подсказка выбора KPI
- C. Якорь на типичный выбор (90% ROI)
- D. Объяснение рисков выбора

---

### U-06 Две колонки как «Целевая метрика»

**Где:** под-шаг 2 «Роли колонок».

**Симптом:** Aurora классифицировала **обе** «Продажи в руб. бренд» и «Продажи в уп. бренд» как Целевая метрика. Модель должна обучаться на ОДНОЙ KPI колонке.

**Фикс:** при выборе KPI на под-шаге 1 → backend пересчёт ролей с фильтром по типу:
- monetary KPI (Выручка/Прибыль) → ищет в **рублях**
- count KPI (штуки/лиды/...) → ищет в **штуках**
- Несовместимые с выбранным KPI → автоматически в «Не использовать»
- Если несколько кандидатов одного типа → modal с radio выбор одного

### M-04 Текст «Модель объясняет только 99%» грамматически странный

**Где:** шаг «Модель» summary.

**Symptom:** «Модель объясняет только 99% вариации продаж (R²)» — «только 99%» звучит как недосказанность.

**Фикс:** «R² = 99% — это завышенный показатель, признак переобучения (модель выучила 31 точку, а не закономерность)».

**Фикс:** «ВЫБОР ЕДИНИЦ ДЛЯ КАЖДОГО КАНАЛА» или «ПОКАНАЛЬНЫЙ ВЫБОР ЕДИНИЦ».

### M-06 Holdout валидация на графике факт-прогноз

**Где:** шаг «Модель», график «ФАКТ VS ПРОГНОЗ».

**Symptom:** при overfitting (R²=0.989 на 31 точке) график визуально идеален → пользователь доверяет модели несмотря на инсайт «переобучение».

**Фикс:** показывать также **holdout validation** — train fit идеальный, но holdout с разрывом. Это визуально показывает «модель выучила, но не обобщает».

---

### M-07 Технические параметры в основном тексте

**Где:** шаг «Модель».

**Symptom:** «5 дивергенций (0.06% от 8000 draws) (Tune=2000, Draws=2000, target_accept=0.95)» — слишком детальные параметры в основном тексте.

**Фикс:** перенести параметры в свёрнутую «Техническая диагностика», в основном тексте — только осмысленные числа.
