## E1. Backtest-витрина ⭐ (Фаза 1 — первая инвестиция «в идеал»)

**Идея:** при каждом обновлении данных продукт САМ показывает: «в прошлом квартале модель
предсказала X, факт — Y, попадание в интервал — да/нет». Самый убедительный слайд для
продления подписки, генерируется из того, что уже есть.

**Что уже есть (красть, не строить):**
- `engines/backtest.py` (10 КБ) — основа механики (⚠ не аудирован глубоко — аудит = первый шаг);
- `utils/forecast_validation.py` — conformal_planning_intervals, quantiles;
- per-sample forward (`posterior_sampler` из inverse.py, мат-аудит F-02) — честные интервалы предсказания;
- `scenario.predict_scenario` — прогноз на произвольный план (S8 CI).

**Реализация:**
1. Rolling-origin валидация: обучение на [1..k] → предсказание [k+1..k+h] против факта; k скользит.
   Канон: out-of-sample по холдауту, НЕ in-sample R² (RAG: Hyndman forecasting / Gelman BW —
   поднять цитаты при реализации, двуязычный запрос «скользящее происхождение rolling origin
   out-of-sample forecast evaluation»).
2. Метрики витрины: попадание факта в 90%-интервал (coverage — главная!), MAPE holdout,
   сравнение с наивным прогнозом (модель обязана бить наивный — иначе честно сказать).
3. Доставка (урок F-04/F-13 — сразу все слои!): endpoint + Rust-команда + карточка UI
   («Проверка на истории: 7 из 8 кварталов в интервале») + слайд в PPTX-отчёт + narrative.
4. Триггер: автоматически при переобучении на расширенных данных; вручную — кнопка «Проверить
   модель на истории».

**Критерий готовности:** на Кагоцеле/MMX витрина показывает честный holdout-результат;
число «coverage» сверено канарейкой с пересчётом; слайд в отчёте; никакого in-sample вранья.
**Осторожно:** короткие ряды (31 мес) → мало точек holdout — честно показывать «оценка по N окнам»,
при N<3 — «истории недостаточно для проверки» (не рисовать пустую уверенность).

## E2. Калибровка экспериментами (Фаза 3 — методологический пик)

**Идея:** результат lift-теста / гео-эксперимента клиента («канал X дал +Z% по тесту»)
вводится в продукт и становится калибрующим приором β канала. Канон кабинета это уже обещает
(«использую результаты A/B и Geo-Lift как priors») — движок НЕ умеет. Отличие Meridian-класса.

**Реализация:**
1. UI-форма «Результат эксперимента»: канал, период, измеренный lift ± интервал, тип теста.
2. Движок: калибровка приора β канала под измеренный lift (пересчёт lift → вклад в KPI-масштабе
   через существующую цепочку adstock→Hill; prior = Normal вокруг калиброванного значения с σ
   из интервала теста). RAG перед реализацией: Robyn calibration + Jin 2017 (experiments as priors)
   — запрос «калибровка MMM экспериментами lift test calibration prior experiments Robyn».
3. Отчёт: пометка [CALIBRATED] у канала + строка «приор откалиброван тестом от <дата>».
4. Честность: расхождение модель-vs-тест ВНЕ интервалов — не замалчивать, показывать
   («модель и тест расходятся — вероятные причины…»).

**Критерий:** синтетика с зашитым lift → калиброванная модель восстанавливает его лучше
некалиброванной (характеризующий тест); pickle-совместимость сохранена (новые поля additive).

## E3. Жизненный цикл модели (Фаза 2 — retention)

**Идея:** клиент обновляет данные раз в месяц/квартал → переобучение → продукт САМ сравнивает
с прошлой моделью: «ROI ТВ был 3.2 [2.6-3.9], стал 3.4 — стабильно» / «изменился резко — вот
3 вероятные причины». Сейчас продукт мыслит «одной моделью».

**Что уже есть:** `persistence*` (пикл-версии), `/compute/model_history` endpoint (server.py:1700 —
проверить, что возвращает и подключён ли к UI — снова урок доставки!), `compare_scenarios` паттерн.

**Реализация:**
1. Версионирование: `models/latest.pkl` → архив поколений с метаданными (дата, данные до, gate-метрики).
2. Сравнение поколений: per-channel ROI/decay/долей с интервалами; вердикт «стабильно / сдвиг
   в пределах интервалов / резкий сдвиг» (перекрытие CI — критерий, канон Jin: у оценок есть дисперсия).
3. Дрейф-мониторинг: R² holdout нового периода на СТАРОЙ модели падает → «пора переобучить» (связка с E1).
4. Доставка: карточка «История модели» + раздел в отчёте «Что изменилось с прошлого квартала».

**Критерий:** два поколения на Кагоцеле (обучение на 25 мес vs 31 мес) → корректное сравнение
с интервалами; UI-карточка; повторный запуск детерминирован.

## E4. Рекомендации-обещания (Фаза 3, замыкает петлю с E1)

**Идея:** от «что было» к «что делать»: каждая рекомендация — проверяемое обещание.
«Сдвиньте 10% с X на Y → ожидаем +Z [интервал] → проверьте через 8 недель → вот метрика».
Следующий backtest (E1) сам показывает, сбылось ли.

**Что уже есть:** `engines/channel_action.py` (Scale/Hold/Watch/Reduce/Cut + reasoning) — зачаток;
scenario-механика для «ожидаем +Z [CI]»; extrapolation-маркеры (не обещать за пределами данных).

**Реализация:** объект «рекомендация» (дата, действие, ожидание с CI, срок проверки) →
сохраняется в проект → при следующем обновлении данных E1-механика сверяет факт → карточка
«Сбывшиеся рекомендации». Честность: рекомендация в зоне экстраполяции получает пометку и
широкий интервал (уже реализовано в ядре — донести в объект).

## Анти-фокус (сознательно НЕ делаем — защита от распыления)

1. **Geo-MMM** (Meridian-уровень) — данных такого уровня у российских клиентов почти нет; не наш ров.
2. **Нейросетевые/DL-MMM** — убивает главную ценность: объяснимость и честность.
3. **Causal-блок** — держать «экспериментальным» (пометка в UI), не полировать до спроса.
4. **Гонка фич с конкурентами** — наш ров: «продукт, который никогда молча не врёт и раз в квартал
   доказывает свою правоту». Каждая новая фича проверяется вопросом: укрепляет ли она петлю доверия?

## Правила исполнения (наследие мат-аудита — обязательны)

- Число-доказательство до правки, число-подтверждение после; первый дефект класса — линза для серии;
  батч умирает в пределах хода; готовые леса красть (`_build_project`, живой Kagocel-зонд).
- Каждая фича честности проектируется СРАЗУ во всех слоях: движок → endpoint → Rust → UI → отчёт
  ([[feedback_audit_delivery_not_just_computation]] — «вычислено ≠ доставлено»).
- Методология — только с RAG-атрибуцией первоисточников; INV-50 без исключений; детерминизм и
  pickle-совместимость не ломать; тесты `-n 4`; durable-реестр + heartbeat при автономной работе.
