## Раунд 1: Клиентский ландшафт

### Q1.1 — Реальные customers сегодня

Кто конкретно уже пользуется или пилотировал Aurora Econometrica MMM Optimizer? Кагоцел и Венарус — это из pilot tests (OTC фарма). Кто ещё в актуальной клиентской базе или ближайших pipeline? Хотя бы 5-10 имён компаний с типом бизнеса.

**Ответ Антона:**

**1 реальный клиент = рекламное агентство**, которое **несистемно** использует программу для своих клиентов, **прежде всего для фармы**.

### Структурный insight #2 (критическое для UX)

Pipeline сегодня узкий — **одно агентство**. Это значит:

- **Aurora = B2B2C модель**: Aurora → агентство → бренд-клиент. Прямого targetинга брендов нет.
- **Primary user = агентский аналитик-маркетолог** (не бренд-менеджер!). У него больше образования чем у бренд-менеджера (умеет читать ROI, понимает adstock), но не эконометрист PhD.
- Бренд-менеджер видит **только output** — отчёт / презентацию / dashboard, не работает с pipeline.
- Шаблоны = **гипотезы** которые валидируются через 3-5 пилотов агентства на разных типах их клиентов (не оптимизация под existing rich clientelle).

## Раунд 2: Границы продукта vs Launch / Brand / Trade & Pricing / Data Studio

### Q2.1 — Scope MMM Optimizer

**Ответ Антона (2026-05-13/14):** Чёткие границы продуктов линейки:

**Aurora Econometrica MMM Optimizer (95% готов, v1.0.16):**
- **Scope:** Оптимизация распределения **медийного** бюджета между каналами для **established brands** с ≥24 мес истории spend/sales. **Реклама → продажи.**
- **NOT in scope:** запуски новых продуктов (→ Launch), awareness/ЗПЛ (→ Brand Tracker), цена/промо/нерекламные факторы (→ Trade & Pricing).
- **ICP:** mixed аудитория, но **рекламные агентства преобладают** (флагман для них). In-house бренд-команды FMCG / OTC / ритейл тоже работают напрямую.

**Aurora Econometrica Launch Planner (85% готов, v0.1.0-rc1):**
- **Scope:** МММ для **новых продуктов** или продуктов с **перерывом в коммуникации**. Прокси-MMM: обучение на ближайшей категорийной бенчмарке, применение к плану нового продукта, уточнение по мере поступления собственных данных.
- **Math:** transfer learning — двухэтапная иерархическая Bayesian модель с donor-benchmark как prior.
- **NOT in scope:** оптимизация бюджета established бренда (→ Optimizer).

**Aurora Econometrica Brand Tracker (40% готов, math finished, UI not started):**
- **Scope:** Динамика **знания-потребление-лояльности (ЗПЛ)** + bridge «реклама → ЗПЛ → продажи/лиды».
- **Math:** двухступенчатая Bayesian + Weibull adstock. Awareness modeling + brand-to-sales bridge.
- **ICP:** CMO/CFO для стратегического планирования и defense brand equity.
- **NOT in scope:** budget optimization (→ Optimizer), launch forecast (→ Launch).

**Aurora Econometrica Trade & Pricing (40% готов):**
- **Scope:** **Нерекламные факторы** — аптечные контракты, визиты к специалистам, конференции, скидки / сезонные, промо-акции (отложенный спрос, покупки впрок), эластичность цены, кросс-эластичность.
- **ICP:** **Клиенты-бренды преобладают** (Commercial Excellence Director), агентства редко. **Mixed аудитория** — агентства тоже могут использовать.
- **NOT in scope:** медийная оптимизация (→ Optimizer), awareness (→ Brand Tracker).

**Aurora Econometrica Data Studio (~85% готов):**
- **Scope:** Инфраструктурный слой — формирует данные для всех 4 приложений из стандартных выгрузок (DSM, Mediascope, AdEx, TV Index, Excel/CSV). **Единые стандарты данных** для всей линейки, координация форматов.
- **Implication:** шаблоны Optimizer завязаны на data contracts Data Studio. Если Data Studio определяет правила колонок «media_spend_rub» / «media_grp» / «target_sales_packs», шаблон применяет их.

### Q2.2 — Сроки разработки

**Ответ:** Все 4 продукта будут готовы **в ближайшие 3 месяца** (к ~2026-08-14). Первым выходит **Launch Planner (85%)**. Философия проработана у всех.

**Implication:** шаблоны MMM Optimizer должны **уже знать про границу** с соседними продуктами. Если пользователь приходит с задачей «launch нового препарата» — Optimizer должен **корректно отказать + предложить Launch Planner** (cross-sell), а не пытаться обработать с искажениями.

### Q2.3 — Multi-tenant фичи

**Ответ:** **Не критично.** Модели очень индивидуальные, клиентов обычно не сравнивают. Cross-project comparison / agency dashboard / white-label = **не в v2.0.0 scope**. Можно отложить в v2.x.

**Implication:** UX дизайн упрощается — концентрируемся на **single-project flow** + хорошая project library / list.

- **Audience mixed для всех продуктов**, но preferred persona разный:
  - MMM Optimizer — **агентства преобладают** (но бренды тоже)
  - Trade & Pricing — **бренды преобладают** (но агентства тоже)

| Customer задача | Где обрабатывается |

| Запуск нового препарата OTC | Launch Planner |
| Возобновление коммуникации после перерыва | Launch Planner |

## Раунд 3: Wizard flow + cross-product behavior + auto-detect scope

### Paradigm shift (Антон 2026-05-14)

> «Я бы не хотел, чтобы проект воспринимался как набор шаблонов. Они скорее должны быть в логике пошагового интерфейса, чем варианты шаблонов для первоначального выбора. Программа по загруженным данным и ответам на вопросы должна сама подводить проект к нужному шаблону. Категория тут вторична — первична задача.»

**Implication:** **Не TemplateGallery (каталог карточек).** **ScenarioWizard (диагностический мастер).** Шаблон выводится системой, не выбирается пользователем.

Категория (фарма / FMCG / косметика / БАДы / ритейл) — **terminology layer поверх**, не primary axis. БАДы и продукты питания по бизнес-логике одинаковы — wizard ведёт их одной веткой.

### Декомпозиция задачи (4 фактора, не категория)

| Фактор | Определяется через | Влияет на |
|---|---|---|
| F1. Activity status | Auto-detect из data signature (history длина, gaps) | Optimizer / Launch / Brand Tracker / Trade |
| F2. Output type | Auto-detect из target column type (₽ / штуки / лиды / подписки) | KPI kind + type |
| F3. Media input type | Auto-detect из media column types | Mode (ROI / Эффективность / Expert mixed) |
| F4. Task intent | Wizard вопрос на старте | Task profile (budget_opt / what_if / inverse_opt) |

### Q3.1 — Длина wizard (ответ Антона)

**До 5-7 шагов до обучения модели.** Достаточные для построения качественной модели + понимания что хочет пользователь (продажи / лиды / подписки / CPU / ROI).

### Q3.2 — Cross-product disambiguation (ответ Антона)

**Не cross-product redirect.** Вместо «это задача Launch Planner, идите туда» — **открыть Expert mode** где математический аппарат доступен полностью без guidance. Пользователь сам пробует смоделировать.

**Feasibility (моя оценка):** ДА, полностью реализуемо. Expert mode = unlock всех ручных настроек pipeline. Все math machinery уже в продукте (`PerChannelInputSelector`, `UnitCostsPanel`, raw model params). Wizard в этом сценарии не блокирует — переключает в free-form режим.

**Логика:** Manager wizard ведёт по типовым задачам. Если wizard понимает что данные не подходят (нет истории / promo-driven / awareness-driven) — не редиректит, а **предлагает Expert mode** с pre-disclosure «эта задача не входит в типичные сценарии Optimizer; вы можете попробовать сами в режиме эксперта, или использовать другой продукт линейки (Launch / Brand Tracker / Trade & Pricing) когда будут доступны».

### Q3.3 — Category layer timing (ответ Антона)

**В v2.0.0.** Не откладываем. Базовое category detection + category-flavored insights — часть первого релиза.

### Q3.4 — Manual override после wizard'а (ответ Антона: «нужно реко»)

**Моя рекомендация: B + C.**

- **B (primary):** После wizard'а — сводка с кнопкой «Изменить настройки». Открывает Expert-режим где видны все derived параметры с возможностью править любой. Не разрушает wizard'у работу — делает её результат editable. При изменении ключевого параметра (KPI, mode, task) — wizard пересчитывает сводку и flag'ует «вы вышли за пределы рекомендованной конфигурации».

- **C (secondary):** На старте — небольшая ссылка «Я умею сам, начать с пустого Expert mode» (для опытных эконометристов, чтобы они не проходили wizard). Не главная CTA, а опция для уверенного пользователя.

- **A (заблокированный wizard)** — отклонить. Manager должен иметь право вмешаться.

### Q3.5 — Auto-detect scope (ответ Антона) — критическая корректировка

**Не источники (DSM / Mediascope / AdEx форматы) распознавать, а ТИПЫ ПЕРЕМЕННЫХ:**

- **Формат медиа** — TV / Digital / OOH / Performance / Print / Radio / Аптечный OOH и т.д.
- **Медиа-показатель** — TRP / GRP / impressions / clicks / views / OTS / contacts / reach
- **Бюджет** — currency (₽, USD), per-channel или aggregate
- **Внешний фактор** — сезонность, погода, конкуренты, макроэкономика
- **Контрольный фактор** — distribution, promo activity, price, trade activity

**Расширенный определитель должен распознавать target metric types:**
- sales_rub / revenue / profit (monetary)
- sales_packs (упаковки / units)
- leads / заявки
- subscriptions / подписки
- registrations / регистрации
- applications / заявления
- loyalty_cards
- app_installs

**Это уже было в прошлой версии — автодетект на этапе валидации** (`ColumnMapperConfirm.svelte` + `column_detection.py`). Расширить + усилить.

### Best-practice recommendations (soft requirements)

Wizard / auto-detector предлагает рекомендации (warn, не block):

- **TRP должны быть приведёнными** (gross/net приведение) — если detected raw TRP, suggest «привести к стандарту».
- **Медиа-KPI должны быть ключевыми по каждому показателю:**
  - Performance → **клики**
  - Display advertising (баннеры больших размеров) → **показы**
  - OLV (online video) → **просмотры**
  - TV → **TRP**
  - OOH → **OTS / contacts**
- **Смешивать показатели (клики для OLV) — методологически неправильно**, но **рекомендация**, не блок.

«Significant share of answers уже в данных» — wizard минимизирует вопросы, делая heavy lifting через auto-detect.
