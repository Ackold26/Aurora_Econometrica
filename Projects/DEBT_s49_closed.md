### Команды зонда и вывод (для реестра)

Инструмент: `makensis.exe` из комплекта Tauri
(`C:\Users\ackol\AppData\Local\tauri\NSIS\makensis.exe`); пробный долгоживущий процесс –
копия `ping.exe` под именем `econprobe.exe`; процесс поднимает и меряет PowerShell, NSIS
только бьёт.

| Вариант в учебном установщике | Вывод `taskkill` | Код | Процесс |
|---|---|---|---|
| `nsExec::ExecToStack 'taskkill /IM "econprobe.exe" /FI "USERNAME eq %USERNAME%" /T /F'` | «Информация: задачи, отвечающие заданным критериям, отсутствуют» | **0** | **ЖИВ** |
| `ExpandEnvStrings $R0 "%USERNAME%"` + фильтр `$R0` | «Успешно: процесс … был завершён» | 0 | убит |
| `nsExec::ExecToStack 'cmd /c taskkill … /FI "USERNAME eq %USERNAME%" …'` | «Успешно: процесс … был завершён» | 0 | убит |

Ключевое: **код 0 при нулевом действии**. Он уходит в `Pop $0`, и установщик считает файлы
освобождёнными.

Отдельно опровергнут путь `$%USERNAME%`: NSIS разворачивает эту запись **во время
компиляции, на машине сборщика**. Доказано различающимся значением – пользовательская
переменная среды при сборке была `COMPILE_TIME_VALUE`, при запуске `RUNTIME_VALUE`, и
`$%…%` дал `COMPILE_TIME_VALUE` (а `ExpandEnvStrings` – `RUNTIME_VALUE`). В установщик
вшилось бы имя сборщика, и у клиента фильтр не совпал бы никогда. Это важно для сравнения
вариантов: предложенный «вариант 2» в исходном виде не альтернатива, а та же мина.

### Выбор устройства

Сравнение по трём признакам:

| Признак | `cmd /c` (Creative Hub, DocMaster) | `ExpandEnvStrings` |
|---|---|---|
| (а) имя разворачивается | да, проверено делом | да, проверено делом |
| (б) видимое окно консоли | нет – `nsExec::Exec` запускает скрыто, вывод в лог не тащит | нет, по той же причине |
| (в) вид связки для антивируса | хуже: посредник `cmd` | лучше: прямой `taskkill` |

**Выбрано устройство DocMaster** (`ROSST_AI_DocMaster/src-tauri/nsis/installer-hooks.nsi`,
09.09.2026), а не `ExpandEnvStrings`. Причины, по убыванию веса:

1. Оно закрывает **вторую беду того же места**, а `ExpandEnvStrings` – только первую.
   Вторая беда: после `taskkill` стояли глухие `Sleep 1500` и `Sleep 1000` (половина
   CPD-75). Приложение при самообновлении завершает себя само уже после старта установщика,
   в момент распаковки может ещё умирать, и отмеренной секунды хватает не всегда, а
   «не хватило» выглядит как успешная установка.
2. Преимущество `ExpandEnvStrings` – «без лишнего процесса» – **исчезает**: проверка факта
   требует конвейера `tasklist | find`, то есть оболочка появляется в любом случае.
3. Решение прожило в бою месяц в родственном продукте – меньше своего изобретения в файле,
   который нельзя проверить сборкой.

Отвергнутое, одной строкой каждое: `$%USERNAME%` – разворачивается на машине сборки
(доказано); `ExpandEnvStrings` – работает, но оставляет вторую половину дефекта;
снятие по PID из `sidecar.json` – PID система переиспользует, разбор JSON в NSIS негде
проверить.

### 🔴 Единственное отступление от образца – и оно вынужденное

`find` зовётся полным путём `$SYSDIR\find.exe`, а не по PATH. **Причина доказана зондом:**
при установленном Git for Windows в PATH оказывается его `find` (утилита Unix), которая
ключа `/I` не понимает.

| Проверка живости ЖИВОГО процесса | Код | Вывод |
|---|---|---|
| `cmd /c tasklist … \| find /I "econprobe.exe"` (как в образце) | **1** – «процесса нет» | `find: ‘/I’: No such file or directory` |
| `cmd /c tasklist … \| "$SYSDIR\find.exe" /I "econprobe.exe"` | **0** – найден | строка `tasklist` |
| то же по отсутствующему образу | 1 | пусто |

То есть на машине с Git в PATH приём DocMaster **молча вырождается** в прежнее «сняли и не
посмотрели» – так же тихо, как вырождался фильтр. `$SYSDIR` – константа NSIS времени
установки (проверено: `C:\WINDOWS\system32` на машине запуска), не времени сборки.

Полные пути для `cmd`, `taskkill` и `tasklist` пробовались и **отвергнуты делом**: команда,
начинающаяся с закавыченного пути, ломает разбор кавычек в `cmd /c`, и снятие переставало
работать вовсе (в зонде процесс остался жив).

### Правка (для реестра)

Файл: `src-tauri/installer_hooks.nsh`. Затронуты оба макроса –
`NSIS_HOOK_PREINSTALL` (было: строки 60–66) и `NSIS_HOOK_PREUNINSTALL` (было: строки 82–88).

**Старый текст** (одинаковый в обоих макросах, по два образа в каждом):
```
nsExec::Exec 'taskkill /IM "econometrica-sidecar.exe" /FI "USERNAME eq %USERNAME%" /T /F'
Pop $0
Sleep 1500
nsExec::Exec 'taskkill /IM "aurora-econometrica-gui.exe" /FI "USERNAME eq %USERNAME%" /T /F'
Pop $0
Sleep 1000
```

**Новый текст** – общий макрос плюс две вставки на каждый хук:
```
!define AURORA_KILL_ATTEMPTS 5

!macro AURORA_KILL_AND_WAIT IMAGE TAG
  Push $0
  Push $1
  StrCpy $1 0
${TAG}_check:
  ; `find` возвращает 0, когда строка НАЙДЕНА, то есть процесс ещё жив.
  ; Обнаружение БЕЗ фильтра по учётной записи - иначе чужой сеанс невидим.
  nsExec::Exec 'cmd /c tasklist /FI "IMAGENAME eq ${IMAGE}" /NH | "$SYSDIR\find.exe" /I "${IMAGE}"'
  Pop $0
  StrCmp $0 "0" 0 ${TAG}_gone
  IntCmp $1 ${AURORA_KILL_ATTEMPTS} ${TAG}_stuck 0 ${TAG}_stuck
  ; Снятие - только СВОЁ.
  nsExec::Exec 'cmd /c taskkill /FI "USERNAME eq %USERNAME%" /IM "${IMAGE}" /T /F'
  Pop $0
  Sleep 500
  IntOp $1 $1 + 1
  Goto ${TAG}_check

${TAG}_stuck:
  SetShellVarContext current
  CreateDirectory "$LOCALAPPDATA\com.aurora.econometrica"
  FileOpen $0 "$LOCALAPPDATA\com.aurora.econometrica\.update-blocked" w
  FileWrite $0 "${IMAGE}"
  FileClose $0
  MessageBox MB_ICONSTOP|MB_OK "Обновление не выполнено: программа всё ещё запущена и держит свои файлы. ..."
  Abort

${TAG}_gone:
  Pop $1
  Pop $0
!macroend
```
```
!insertmacro AURORA_KILL_AND_WAIT "econometrica-sidecar.exe" pre_sidecar
!insertmacro AURORA_KILL_AND_WAIT "aurora-econometrica-gui.exe" pre_gui
```
(в PREUNINSTALL – те же две вставки с метками `un_sidecar` / `un_gui`: одинаковые метки в
одной функции NSIS не допускает).

Макрос введён вместо четырёх одинаковых блоков намеренно: без него четыре копии разошлись бы.
`$0`/`$1` сохраняются через `Push`/`Pop`, потому что хук встраивается в чужую функцию шаблона
Tauri. Глухие `Sleep 1500` / `Sleep 1000` удалены – их заменило ожидание факта.

### Что проверено и что НЕТ

Проверено:
- `makensis` компилирует боевой файл через учебную обёртку с `!include` и вставкой всех трёх
  макросов – **код 0**;
- точная копия итогового блока, все три ветки (таблица выше): процесса нет – 0 ударов;
  свой – убит с первого удара; неснимаемый – 10 попыток, отказ, след записан, окно показано;
- **цикл ожидания действительно крутится** и упирается в ограничитель – зацикливания нет;
- регистры `$R0`/`$0`/`$1` после блока не испорчены;
- показ окна в тихом режиме (`/S`) – отдельным зондом;
- кодировка файла цела: UTF-8 с BOM, 233 CRLF, ни одного одиночного LF.

🔴 **НЕ проверено делом. Правка ждёт живой пробы на собранном установщике при запущенной
программе – процесс должен исчезнуть.** Ни компиляция, ни поведение копии блока, ни поиск
строк по собранному установщику (содержимое сжато) этого не заменяют. Также не проверено
живьём: не заняты ли `$0`/`$1` окружающим кодом шаблона так, что `Push`/`Pop` недостаточно;
и принудительное закрытие окна программы при установке поверх – теперь оно заработает, а
прежде не случалось ни разу.

Худший случай по времени: до ≈10 секунд на образ, то есть до ≈20 секунд на хук, если
процесс не умирает. Штатный – около 9 секунд.

### Доработка после предсборочного чеклиста (вторая половина V77)

Чеклист прав: починка мёртвого фильтра сама по себе сценарий не закрывала.

🔴 **Найденный пробел, который не был назван ни в чеклисте, ни в задании:** проверка живости
тоже шла с фильтром `USERNAME eq %USERNAME%`, а значит программу, запущенную под ДРУГОЙ
учётной записью, хук бы просто **не увидел** – и снова доложил бы «успешно» поверх занятого
файла. Ожидание факта без этой правки чинило бы только свой случай.

**Решение – обнаружение и снятие разведены:**
- живость проверяется БЕЗ фильтра по учётной записи (видим любой процесс с нашим именем
  образа);
- снимается только своё, фильтр оставлен.

**Развилка (а) / (б) – выбрано (а)**, и это совпадает с мнением команды. Обоснование от
устройства установки: при `installMode: currentUser` шаблон Tauri ставит в
`$INSTDIR = $LOCALAPPDATA\<productName>` (проверено по сгенерированному `installer.nsi`),
то есть чужой сеанс работает со СВОЕЙ копией в СВОЁМ профиле и наших файлов не замыкает.
Единственная ситуация, где чужой процесс реально держит наш файл, – давняя МАШИННАЯ
установка в Program Files, и там честный отказ уместнее снятия чужой работы на терминальном
сервере.

**Как именно «не молчать» – и что об этом выяснилось.**
- Путь «прервать и сказать из программы» **закрыт**: `updater.rs::apply_update` запускает
  установщик через `Start-Process` без ожидания и сразу делает `std::process::exit(0)` –
  читать код возврата некому.
- 🔴 Опасение «MessageBox в тихом режиме подавлен» **не подтвердилось**. Проверено делом:
  явный `MessageBox` без флага `/SD` в режиме `/S` показывается и ждёт ответа – учебный
  установщик, запущенный с `/S`, висел на окне «ProbaV77 Setup» 32 секунды и не вышел.
  Подавляются страницы интерфейса и автоматические окна NSIS, а для подавления явного окна
  существует отдельный флаг `/SD` – его наличие само по себе доказывает обратное. Именно
  поэтому в нашем `NSIS_HOOK_POSTINSTALL` стоит явный `IfSilent +2`.

**Внедрено (итоговая редакция – РЕШЕНИЕ ВЛАДЕЛЬЦА 18.09.2026, выбор из трёх вариантов:
«отказаться и сказать человеку»):** при исчерпании попыток – `DetailPrint` (ASCII, правило
файла), след `.update-blocked` в `%LOCALAPPDATA%\com.aurora.econometrica\`, окно отказа
**БЕЗ `IfSilent`** (показывается и при тихом обновлении) и `Abort` – установка не идёт,
прежняя версия остаётся целой.

Редакция менялась дважды: я поставила отказ с окном → руководитель блока заменил на
«продолжить, окно под `IfSilent`» → владелец выбрал отказ с окном. Промежуточная редакция
опиралась на посылку «в тихом режиме окна человек не видит», которую сняли два зонда (ниже).

🔴 **Почему без окна человек не узнал бы НИЧЕГО.** Файла журнала установки **не существует
вовсе** – `makensis` из комплекта Tauri собран без `NSIS_CONFIG_LOG`, и `LogSet` отвергается
прямо на компиляции («LogSet specified but NSIS_CONFIG_LOG not defined», проверено
18.09.2026). `DetailPrint` уходит только в окно хода установки, которого в тихом режиме нет.
Сказать из самой программы нечем – `updater.rs::apply_update` запускает установщик через
`Start-Process` без ожидания и сразу делает `std::process::exit(0)`. То есть окно –
единственный носитель факта, и это делает выбор владельца единственно рабочим.

**Цена, названная владельцу заранее и принятая им:** окно появляется и при тихом обновлении и
ждёт ответа – если человек отошёл, обновление повиснет до его возвращения.

🔴 **Подавление в тихом режиме – наш сознательный выбор, а не свойство NSIS.** Записано в
шапке хука именно так, с предупреждением «не чинить добавлением `IfSilent`»: иначе следующий
читатель выровняет это место по окну успеха в POSTINSTALL и снимет единственный способ
сообщить человеку.

**Предложение читать `.update-blocked` при следующем запуске программы** вынесено владельцу
отдельно; пока след остаётся диагностикой без читателя.

**Предел попыток: 5** (снижен с 10 по находке аудита и решению руководителя – довод про две
минуты молчания при тихой установке принят). Довода против у меня нет, есть довод ЗА:
`taskkill /F` завершает процесс принудительно, а не просит закрыться, и штатно программа при
самообновлении уходит сама за секунды; переживший пять принудительных попыток образ не наш по
учётной записи либо не снимается вовсе – десятая попытка ничего не изменит, только продлит
молчание.

Замеры на точной копии блока: один вызов через оболочку ≈0,9 с, попытка ≈3 с. Полный проход
по неснимаемому процессу: при десяти попытках **26,6 с**, при пяти – **16,6 с** (тихий режим,
установка дошла до конца). Штатно (процесс умирает с первого удара) ≈3 с на образ; когда
программа не запущена вовсе – одна проверка ≈0,9 с и **ни одного удара** (проверка стоит
первой).

(Расхождение с цифрами аудитора – 2,7 с на попытку и расчёт от 20 – несущественно: порядок
тот же, свои замеры не пересматривала.)

**Ветки проверены делом** (учебный установщик – точная копия боевого макроса):

| Ветка | Результат |
|---|---|
| процесса нет вовсе | 0 ударов, мгновенный выход |
| процесс свой, снимается | 1 удар, процесс исчез |
| процесс жив, снятие бьёт мимо, режим **тихий** (`/S`) | 5 попыток → ветка отказа, след записан, **окно показано**, установка до конца **не дошла**, установщик за 60 с не завершился |
| то же, режим **обычный** | то же самое |

🔴 **Отдельный прямой зонд на видимость окна** – потому что прежний вывод опирался на
косвенный признак («процесс не завершился»). Учебный установщик записывает отметку сразу
ПОСЛЕ `MessageBox`: в обоих режимах отметки нет, управление из окна не возвращается. То есть
окно действительно показано и ждёт ответа, а не подавлено.

Честно о промахе: первый прогон ветки отказа в тихом режиме показал «завершился сам за 38 с»,
что противоречило прямому зонду. Повторный прогон дал ожидаемое (висит 60 с), то есть первое
наблюдение было помехой. Вывод держится на двух согласующихся зондах, а не на одном.

**Что остаётся открытым – записано и в шапке хука:** при занятом файле обновление НЕ
устанавливается, человек видит окно (в том числе при тихом обновлении), прежняя версия цела;
чужой процесс не снимаем – обновление не пройдёт, пока человек не закроет программу во втором
сеансе сам; окно требует человека у экрана, иначе тихое обновление ждёт сколь угодно долго;
процесс, запущенный от администратора при непривилегированном установщике, `taskkill` не
