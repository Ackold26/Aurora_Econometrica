## ЗОНД 1 — вердикт канала с отрицательной предельной отдачей: ВОСПРОИЗВЕЛОСЬ

Фикстура: 4 канала (tv/ooh/online_video/убыточный_канал), OLS-обучение на синтетических
данных, где `убыточный_канал` имеет ОТРИЦАТЕЛЬНУЮ относительную отдачу (каннибализация).
`optimize({'total_budget': None, 'min_pct': 50, 'max_pct': 150}, project)`.

Сырой вывод (канал `убыточный_канал`):
```
name = 'убыточный_канал'
current_spend_money = 371379215.0
optimal_spend_money = 185689608.0
mroi_current = -59.8461
mroi_optimal = -154.2846
delta_pct = -50.0
action = 'Watch'
action_label = 'Под наблюдением'
action_reasoning = '-59.85×, разрыв +0.0 пп - нужен мониторинг'
action_tone = 'neutral'
ratio(opt/cur) = 0.5000000013463327
```
Оптимизатор упёр канал ровно в нижнюю границу (50 %) — дальше сокращать некуда (границы
50–150 %), но при mROI = −59.85× (глубоко убыточный) вердикт — «Под наблюдением», самый
мягкий из шести, с той же приоритетностью, что у нейтрального «не хватает сигнала».

Граница `ratio < 0.5` — подтверждена прямым вызовом `compute_channel_action` на
контролируемом словаре (`mroas=-1.5`, cur=1 000 000):
```
ratio=0.49      -> action.key='Cut'   ("Оптимизатор рекомендует -51% ...")
ratio=0.499999  -> action.key='Cut'   ("Оптимизатор рекомендует -50% ...")
ratio=0.5       -> action.key='Watch' ("-1.50×, разрыв +0.0 пп - нужен мониторинг")
ratio=0.500001  -> action.key='Watch'
ratio=0.51      -> action.key='Watch'
```
Вход, дающий противоположный результат: тот же канал с `ratio=0.499999` (на 1 деньгу меньше
у optimal_spend) — получает «Cut». Значит зонд измеряет ровно эту границу, а не шум.

Причина в коде (`engines/channel_action.py`):
- строка 328: `if cur_spend > 1e-9 and ratio < 0.5:` → `Cut` (строгое `<`, не `<=`).
- строка 388: `if eff_mroas > 0 and eff_mroas < 0.8:` → `Cut` (ловит только ПОЛОЖИТЕЛЬНЫЙ
  eff_mroas ниже точки безубыточности; отрицательный eff_mroas сюда не попадает).
- Все остальные ветки (Reduce/Scale/Hold, шаги 6a–10) либо требуют `eff_mroas >= 1.0`,
  либо `eff_mroas > 0`, либо не срабатывают при ratio ровно на границе → канал с
  отрицательной отдачей и ratio ∈ [0.5, ...) падает в дефолтный fallback «Watch».

Вывод: заявленный дефект воспроизведён числом (не гипотезой) — самый убыточный канал в
портфеле получил самый мягкий вердикт, и граница `ratio==0.5` действительно промахивается
мимо «Cut» ровно в момент, когда оптимизатор упирает убыточный канал в нижний предел.

```
    "attempts": [
      {"start_name": "current", "success": false, "iterations": 1,
       "message": "Singular matrix C in LSQ subproblem"},
      ... (все 6 стартов - та же ошибка солвера) ...
    ]
  },
  ...
}
```
Заявленные в задаче числа совпали буквально: `status: ok`, `optimization_converged: false`,
`expected_lift_pct: 11.0`. Сумма `optimal_spend_money` по каналам = 6 742 812 742 ₽ — то есть
клиенту показан «оптимальный» план и заявленный прирост +11 %, хотя ВСЕ 6 попыток SLSQP
упали с «Singular matrix» (NaN в равенстве-ограничении `sum(x) - money_target == 0`
не даёт солверу зацепиться), сходимости не было вообще.

Причина в коде (`engines/optimizer.py`, feasibility-гейт ~730–780): проверки
```
if money_target > sum_upper_money * 1.001: ... INFEASIBLE_BUDGET_HIGH
if money_target < sum_lower_money * 0.999: ... INFEASIBLE_BUDGET_LOW
```
при `money_target = NaN` обе сравнения дают `False` (NaN не `>` и не `<` ничего) — гейт
молча пропускает NaN дальше, до самого солвера.

Дополнительно — `Inf` и `-Inf` (проверка отличия от NaN, тот же гейт):
```
optimize(total_budget=Inf)  -> {"status": "error", "error_code": "INFEASIBLE_BUDGET_HIGH",
  "message": "Целевой бюджет inf ₽ превышает максимально допустимый 10,114,219,112 ₽ ..."}
optimize(total_budget=-Inf) -> {"status": "error", "error_code": "INFEASIBLE_BUDGET_LOW",
  "message": "Целевой бюджет -inf ₽ ниже минимального 3,371,406,371 ₽ ..."}
```
Уточнение: `Inf`/`-Inf` гейт ловит КОРРЕКТНО — сравнение `inf > x` истинно, так что защита
срабатывает без всякой проверки на конечность. Дефект специфичен именно для `NaN`
(единственное значение, для которого любое сравнение ложно), не для "нефинитности" вообще.

- Через прямое вмешательство в рендер-путь (monkeypatch, убирающий тире из ЛЮБОЙ текстовой
  фигуры колоды целиком, не только денежных ячеек) — **ДА, красный получить можно** (показано
  в П.2). Но такой красный ничего не говорит о деньгах: он сработал бы точно так же, укради

  способен покраснеть, но не способен покраснеть ОТ ТОГО, ЧТО ОН, СУДЯ ПО НАЗВАНИЮ, ДОЛЖЕН
  ЛОВИТЬ: регресс рендеринга отсутствующих денег.

Итог: заявленная защита INV-50 («прочерк вместо ложного нуля для отсутствующих денег») этим
тестом фактически не проверяется — ни при каком варьировании относящихся к делу данных. Плюс
установленный в П.1 факт: на настоящем слайде плана отсутствующие деньги рендерятся как
литеральное `"н/д"`, не как тире — то есть даже дойди цикл до нужного слайда, ассерт на «–»
всё равно не о том, что задумано докстрингом теста.
