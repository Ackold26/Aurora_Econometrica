## Отчёт

### 🔴 Главное расхождение с постановкой — важно прочитать первым

Аудиторская находка H-4 говорила: «критерий совпадения не доходит до клиента ни в HTML-отчёте, ни в PPTX-презентации» (`Projects/PULSE_audit_repro_2026-08-16.md:87-95`, адрес `methodology_cert.py:1125-1186`). **Эта часть H-4 сейчас закрывается ПАРАЛЛЕЛЬНО, в этом же рабочем дереве, кем-то ещё** — `git status` показывает некоммиченные правки в `aurora_html/sections.py`, `aurora_pptx/builder.py`, `engines/methodology_cert.py`, плюс новый тест-гейт `tests/test_h4_repro_criterion_disclosure.py`, который **проходит 3/3** (прогнала лично: подраздел «Критерий совпадения» есть в HTML, строка «Совпадение расчётов» есть на слайде PPTX, оба документа называют одну и ту же ветвь и одно и то же число).

Но твоя постановка задачи говорит о другом — о **живом интерфейсе программы** («вывести его в интерфейс к демонстрации покупателю», п.3 задания: Rust-команда + Svelte-компонент). Это ТРЕТЬЯ поверхность показа, отдельная от HTML-отчёта и PPTX-презентации, и она **не тронута вообще** — ни готовящейся сейчас правкой (та меняет только экспортные форматы), ни чем-либо ранее. Дальше отчёт — по ней, как и просил пункт 3 задания.

### 1. Где живёт логика критерия

`sidecar/econometrica/utils/repro_tolerance.py` (849 строк). Ядро:
- `applicable_mode(passport)` / `detect_mode(run_a, run_b)` — определяют ветвь допуска САМИ, по числу итоговых выборок в паспорте (`chains × draws`), читателю выбор не предлагается (инвариант handoff.md №6);
- `compare_runs(model_a, model_b, ...)` — сверяет два реальных расчёта (в продукте пока нигде не вызывается, это внутренний инструмент проверки — отмечено находкой M-2 аудита);
- `criterion_for_certificate(passport=None)` — отдаёт критерий как структуру (для сертификата методологии), это то, что реально течёт в JSON к фронтенду;
- `criterion_lines()` / `criterion_note()` — критерий в виде готовых русских строк «название – значение» (используются только для рендера HTML/PPTX, в JSON-выдаче их нет).

**Три ветви допуска** (`MODE_EXACT`/`MODE_STRICT`/`MODE_WIDE`), определяются автоматически, не выбираются вручную:
1. `exact` — повторный запуск той же программой в той же среде (зерно и среда совпали). Допуск нулевой. 🔴 Стороннему покупателю неприменима в принципе (побитовое совпадение даёт не зерно, а идентичность кода) — это ветвь самопроверки продукта, не демо-аргумент.
2. `other_seed_full` — другое зерно, полный расчёт (≥ 8000 итоговых выборок). Это ветвь, применимая к демонстрации/стороннему покупателю при обычном расчёте.
3. `reduced_or_other_env` — сокращённый расчёт, другая среда/настройки, либо зерно/среда не записаны. Самый широкий допуск.

### 3. Путь до интерфейса — фактически, а не гипотетически

Специальной Rust-команды для критерия нет, и заводить её отдельно, скорее всего, не нужно: **данные уже приезжают во фронтенд бесплатно**. Цепочка: `decomposer.py:1517` кладёт `methodology_certificate` (с вложенным `repro_tolerance`) в тот же словарь `result`, что возвращает `decompose()` → Rust-команда `econ_decompose` (`src-tauri/src/commands/econometrica.rs:197-215`) — простой pass-through `post_json("/compute/decompose", ...)`, поля не фильтрует → результат кладётся в стор `decomposeData` (`src/lib/components/pipeline/DecomposeStep.svelte:324-332`). То есть `$decomposeData.methodology_certificate.repro_tolerance` уже доступен в момент отрисовки шага «Декомпозиция» — просто ни один компонент туда не заглядывает.

Свежая аналогия того же типа находки (H-5, тот же аудит 2026-08-16) — «обещана выгрузка параметров, которой у пользователя нет» — **уже закрыта** по классическому паттерну: Rust-команда `econ_export_params` (`econometrica.rs:538`) + кнопка в `ReportStep.svelte` (`H-5: выгрузка параметров модели`, строки 152-154, 792-805, 1047-1049). Если для критерия совпадения решите делать отдельную Rust-команду (например, чтобы дергать её вне декомпозиции — на шаге «Отчёт»), это готовый образец для копирования паттерна.

**Куда критерий логически встал бы** (два кандидата, не исключают друг друга):
- **Шаг «Декомпозиция» (`DecomposeStep.svelte`)** — рядом с уже существующим баннером ненадёжности (`reliability-warn-banner`, F-A1-9, строки 533-537) и на этом же шаге данные УЖЕ есть в сторе без доп. работы. Естественное место для «вот что подтверждает воспроизводимость этого расчёта».
- **Шаг «Отчёт» (`ReportStep.svelte`)** — рядом с блоком H-5 (выгрузка параметров) и текстовыми описаниями того, что внутри HTML/PPTX/XLSX (строки 600-639) — здесь показ критерия в интерфейсе будет зеркалить то, что готовящаяся сейчас правка добавляет в сами файлы экспорта, и это ближе к моменту, когда покупатель реально просит «докажите, что это не рандом».

Для живой демонстрации через неделю естественнее ШАГ «ДЕКОМПОЗИЦИЯ» — данные там уже есть безо всякой новой Rust-обвязки, и это момент показа результатов, где обычно и звучит вопрос «а если пересчитать — сойдётся?».

### 4. Что уже показывается рядом (чтобы новый блок не дублировал и не противоречил)

- `DecomposeStep.svelte` — баннер `reliability-warn-banner` (F-A1-9): плашка ненадёжности над денежными инсайтами, срабатывает по вердикту `model_reliability` с бэкенда. Про СХОДИМОСТЬ и качество ОДНОГО расчёта, не про совпадение ДВУХ расчётов — не пересекается по смыслу с критерием.
- `OptimizeStep.svelte` — `reliability-banner`/`pre-optimize-reliability-warn`, тот же `model_reliability`-вердикт, тоже про качество/уверенность модели, не про воспроизводимость.
- `ConvergenceDashboard.svelte` — MQS (Model Quality Score), «надёжность выводов оценивайте по баллу качества». Тоже другое измерение: сходимость сэмплера этого прогона, не сверка двух прогонов.
- `TrustBanner.svelte` — предупреждение про smell_flags (экстремальный ROI, смешанные единицы измерения). Тоже не про критерий совпадения.
- `RatioInfoCard.svelte` — про статистическую надёжность через Ratio (наблюдения/параметры). Смежная, но другая метрика.

**Вывод: смыслового дублирования нет ни с одним существующим блоком** — все они отвечают на вопрос «насколько хорош ЭТОТ расчёт», а критерий совпадения отвечает на другой вопрос — «если пересчитать, сойдётся ли». Их стоит визуально не путать (разные заголовки, возможно разная иконка/цвет), но противоречить друг другу они не будут.

### 5. Точные числа критерия — дословно из кода (`repro_tolerance.py:217-246`)

Порог полноты расчёта: `FULL_RUN_DRAWS = 8000` (итоговых выборок = цепи × выборки; 4 цепи × 2000 — настройка по умолчанию при наличии компилятора).

| Величина | `exact` (та же программа, та же среда) | `other_seed_full` (другое зерно, полный расчёт) | `reduced_or_other_env` (сокращённый/другая среда) |
|---|---|---|---|
| Окупаемость канала (roi) | 0 % | 5,0 % | 10,0 % |
| Коэффициент канала (beta) | 0 % | 5,0 % | 10,0 % |
| Скорость переноса (decay) | 0 % | 5,0 % | 10,0 % |
| Форма насыщения (alpha) | 0 % | 5,0 % | 10,0 % |
| Точка насыщения (gamma) | 0 % | 5,0 % | 10,0 % |
| Доля канала во вкладе (contribution_pct) | 0 п.п. | 1,5 п.п. | 3,0 п.п. |

Вторая опора (`CI_SHARE_LIMIT_PCT = 25.0`): расхождение засчитывается как совпадение и тогда, когда оно не превышает 25 % ширины правдоподобного диапазона той же величины — но 🔴 **фактически работает сегодня только для `roi`** (`CI_BOUNDS = {'roi': (...)}`, `repro_tolerance.py:249-251`; для `beta`/`decay`/`alpha`/`gamma`/`contribution_pct` возвращает `None` всегда). Это отдельная находка H-3 того же аудита (`repro_tolerance.py:228-230`), на момент разведки НЕ закрыта нигде — при написании клиентского текста про «вторую опору» нельзя обещать её для всех шести величин, только для окупаемости.

Числа сняты замером 2026-08-16 (см. docstring-шапку `repro_tolerance.py:1-114`): ветвь 2 — на трёх парах прогонов (зёрна 42/7/123, 4×2000 выборок) максимальное расхождение было 2,4 % по окупаемости; ветвь 3 — на сокращённых прогонах (500 выборок на цепь) до 3,5 % по окупаемости. Объявленные допуски — с запасом примерно вдвое к измеренному максимуму, и это тоже стоит явно сказать в демо-тексте: числа не «взяты с потолка», а измерены и удвоены для запаса.
