# Handoff для внешнего аудитора — блок s44 (13.09.2026)

Продукт: «Aurora AI Econometrica» (Optimizer MMM) 2.5.2. Tauri v2 + SvelteKit 5 (JS + JSDoc,
не TypeScript) + Rust + Python sidecar.

База диффа: `fbc80994` (последний коммит предыдущей сессии s43) → `HEAD` = `c8f4a49b`.
🔴 База определена вручную: файл `claude-session-base-sha`, который пишет хук старта сессии,
на момент генерации содержал хеш последнего коммита блока, а не первого — то есть был
перезаписан по ходу. Диапазон проверен по `git log`: все 7 записей блока принадлежат этой сессии.

---

## 1. Цель блока

Доводка продукта перед показом покупателю по порядку работ владельца: чиним → проверяем →
аудируем → дорабатываем → проверяем, и только потом собираем установщик. Блок закрывает находки
внешнего аудита предыдущей сессии (путь отказа обновления), класс «клиентский текст и числа на
экранах», гигиену поставки, две задачи по интерфейсу от владельца со снимков экрана, и добавляет
в модель новое событие календаря — православную Пасху.

Сборка установщика в этом блоке НЕ производилась намеренно: она последнее действие, а живые
пробы пути обновления ещё не сделаны.

## 2. Ключевые инварианты

1. **Клиентский текст** — русский без англицизмов там, где есть русское слово; короткое тире
   «–» (U+2013), длинное «—» запрещено; текст говорит человеку, ЧТО сделать.
2. **Честность метрик (INV-50)** — число на экране обязано соответствовать источнику;
   псевдоточность запрещена. В карточке профит-фронтира это охраняется флагом
   `maximum.reportable`: число максимума показывается, только когда его честно можно назвать.
3. **Старые модели воспроизводятся** — список праздников, на котором обучена модель, хранится
   в ней (`normalization.holiday_cols_injected`) и при декомпозиции используется он, а не
   текущий набор. Добавление 13-го события не должно менять поведение ранее обученных моделей.
4. **Собранный пакет ≠ среда разработки (INV-96)** — ресурс, который код читает по пути от
   `__file__`, обязан быть перечислен в `--add-data` PyInstaller, иначе в поставке его не будет,
   а в разработке путь сойдётся.
5. **Поставка клиенту собирается только командой со шлюзом**, установка и обновление — без прав
   администратора (`installMode: currentUser`).
6. **Персональные данные** — с этого блока программа не собирает контакт клиента в форме
   обратной связи (решение владельца). Отпечаток машины — хеш характеристик, не ПДн: ни имени
   пользователя, ни имени машины, ни путей (INV-38).
7. **Тесты движка гоняются как `pytest tests`**, а не голым `pytest`: голый прогон подхватывает
   каталог `_internal/` (собранный PyInstaller-пакет, лежит рядом) и гоняет чужие тесты чужих
   библиотек — 52 падения и 15 630 ошибок, не имеющих отношения к коду.

## 3. Осознанные компромиссы

1. **Признак «текст для человека» — явная метка `[клиенту]` в строке отказа, а не разбор языка.**
   Решение → внешний аудит предлагал признак «в детали есть кириллица»; проверка всех веток
   `updater.rs` показала русские СЛУЖЕБНЫЕ строки («Загрузка обновления уже идёт», «Частичный
   файл не соответствует серверному»), которые такой признак вытащил бы на блокирующий экран.
   Цена: договор о формате строки держится тестом, а не типом.
2. **Пасха добавлена окном −7…+3 дня, пересечение с майскими не устраняется, а объявляется.**
   Решение → в годы поздней Пасхи окна совпадают (2024 — 11 дней из 11), разделить вклады нельзя.
   Сужение окна не помогло бы в 2024 и обессмыслило бы фактор в прочие годы. Пара внесена в
   `EXPECTED_OVERLAPS`: программа предупредит, при доле выше 85 % предложит объединить.
3. **Страховка от отсутствия `:has()` сделана гейтом `@supports`, а не безусловным полом высоты.**
   Решение → безусловный `min-height` сломал бы ручное УМЕНЬШЕНИЕ окна разворота (требование
   владельца). Цена: в браузерах без `@supports selector()` (ниже Chrome 83) блок отбрасывается —
   для WebView2 нереалистично.
4. **Секция «Прогноз» в веб-отчёте починена добавлением ключа в контекст, условие в оглавлении
   НЕ добавлено.** Решение → соседняя секция «trust» имеет проверку живых данных, эта — нет;
   после правки данные есть, и пункт перестал быть мёртвым. Если данных не будет по другой
   причине, мёртвая ссылка вернётся.
5. **`@ts-nocheck` в сторожевом тесте пути обновления** — файл читает `node:fs`/`node:path`,
   `@types/node` в проекте нет. Тот же приём стоит в шести соседних сторожах репозитория.
6. **Возврат `"sent"`, а не `"recorded"` из отправки обращения** — признак записи лежит в теле
   ответа сервиса, а тело остаётся внутри общего крейта, который отдаёт только «отправка не
   отвергнута». Утверждать запись по такому ответу нельзя.

## 4. Зоны неуверенности

1. **🔴 Кривые отдачи на шаге «Оптимизация» не проверены живьём.** Условие показа —
   `optData?.response_curves && Object.keys(scaledParams).length > 0` (`OptimizeStep.svelte:2503`);
   `scaledParams` пуст, если пуст `mData.channelParams`. Гипотеза: параметры не восстанавливаются
   в состоянии программы при повторном открытии проекта. Исполнитель нашёл рядом с моделью файл
   `models/latest-params.json` (29 КБ) и оборвался на связи. В блоке НЕ чинилось. Заглушка при
   этом советует запустить оптимизацию, которая уже выполнена, — то есть врёт.
2. **Живое измерение вёрстки относится к состоянию ДО части правок.** Числа 75–77,5 % высоты и
   следование холста за размером сняты исполнителем до того, как в тот же файл легли правки
   подсказки (вынос пузыря в корень документа) и мои правки цветов. Совместное поведение
   портала подсказки и разворота карточки живьём не проверялось.
3. **Правка цветов проверена расчётом контраста, а не глазами.** Посчитаны пары «цвет текста /
   фактический фон» по токенам тем: от 4,63 до 11,50:1. Но фактический фон элемента мог быть
   иным, чем взятый в расчёт (подложки с прозрачностью, наложения). На экране после правки
   никто не смотрел.
4. **Форма обратной связи не прогонялась после правки.** Убрано поле контакта, изменена
   сигнатура команды Rust (`submit_feedback` потерял параметр `contact`), добавлен предел длины
   и технический хвост. `cargo check` проходит, но отправка живьём не выполнялась — в том числе
   не проверено, что сервис принимает обращение с хвостом и не отвергает его по длине.
5. **Пасха: влияние на обучение модели не проверено прогоном.** Проверены даты, границы окна,
   объявленное пересечение и то, что существующие тесты зелёные. Но ни одна модель с 13-м
   праздником не обучалась: как поведёт себя проверка коллинеарности на реальных данных клиента
   и не всплывёт ли предупреждение там, где его не ждут, — неизвестно.
6. **Секция «Прогноз» после правки не отрисовывалась на живых данных.** Ключ в контекст добавлен,
   тесты приведены к боевой форме и зелёные, но HTML-отчёт с непустым прогнозом не собирался.
