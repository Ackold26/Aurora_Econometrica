# Handoff: честность вердикта надёжности и разведение редакций (2026-08-10)

Диапазон блока: `97499e1..HEAD` (записи `4d763bb` · `505bfce` · `8428992` · `6466cb2`, плюс
документные `4d0c918`, `9824d45`, `638f7dc`, `9e4c80b`).

## 1. Цель блока

Вердикт надёжности модели — честностный гейт продукта: при непроверенной или ненадёжной модели
клиент обязан увидеть предупреждение во всех выходах отчёта (Markdown, XLSX, HTML, презентация).
Состояние «надёжность не проверена» не показывалось нигде, а отсутствие вердикта в данных молча
приравнивалось к «модель надёжна». Блок делает это состояние видимым и единообразным во всех
четырёх выходах. Второй, независимый предмет блока: две редакции продукта (облачная и локальная)
делили один файл состояния движка и могли снять расчёт друг друга.

## 2. Ключевые инварианты

- **Отсутствие вердикта ≠ надёжная модель.** Пустое значение, отсутствие ключа и строка из пробелов
  трактуются как «надёжность не подтверждена» во всех выходах.
- **Отсутствие вердикта ≠ отказ от рекомендаций.** `verdict_refuses` остаётся только про
  `unreliable`. Приравнивание отключило бы рекомендации всем проектам, обученным прежними сборками.
  Предупреждать, а не отключать.
- **Единственная точка чтения вердикта в Rust** — `normalize_reliability_verdict`. Структурный
  сторож требует ровно одно прямое чтение в продуктовом коде (внутри самого нормализатора).
- **Текст клиенту — единым источником и побайтово зеркалится** Python ↔ Rust
  (`RELIABILITY_UNKNOWN_NOTE` ↔ `RELIABILITY_UNKNOWN_TEXT`), сторож на шве плюс запрет длинного тире.
- **Надёжная модель не перепредупреждается:** ветка `reliable` по-прежнему молчит, даже если рядом
  остался текст оговорки от прошлого расчёта.
- **Сверка расхождения диагностики и оптимизации молчит при неполных данных** — отсутствие величины
  там законно означает «старый проект», ложная тревога дороже пропуска. На нормализатор эта сверка
  намеренно НЕ переведена.
- **`product_id` рукопожатия движка остаётся общим для обеих редакций** (это значение сверяется с
  модулем Python, собранным из одного файла); разводится только каталог файла состояния.

## 3. Осознанные компромиссы

- **Вердикт по-прежнему берётся из двух источников:** Markdown и XLSX — из замороженной копии в
  результатах оптимизации, HTML и презентация — из живой диагностики. Причина: замороженный вердикт
  описывает те числа, что стоят рядом с ним. Решение владельца — предупреждать о расхождении, а не
  сводить к одному значению. Блок этого не менял.
- **Структурный сторож оставлен, хотя доказано слеп** к эквивалентной записи другого синтаксиса.
  Причина: он дёшев и ловит небрежный возврат к прежнему коду; поведение защищено отдельным
  поведенческим тестом (вердикт из пробелов обязан давать плашку).
- **В презентации для состояния «не подтверждена» убрана короткая машинная строка** «качество не
  измерено». Причина: она дублировала новую развёрнутую оговорку, клиент читал две строки об одном.
  Тексты остальных состояний не тронуты.
- **Молчаливый запасной путь заменён предупреждением в журнал, а не отказом.** Причина: экспорт
  отчёта не должен падать из-за невычисленного вердикта; но и молчать о том, что он не вычислен,
  нельзя.
- **Три существовавших теста переписаны, а не оставлены.** Они опирались на исправляемый дефект
  (пустой вердикт = твёрдая директива); один из них к тому же был зелёным случайно — проверял
  «надёжную модель», ни разу её не получив (пустая диагностика через шов, который до него не доходил).

## 4. Зоны неуверенности

1. 🔴 **Поведение при вердикте `unknown` не проверено живым обучением.** На машине нет ни одного
   проекта, обученного после появления штампа: все четыре обученных дают `uncertain`. Значит новая
   плашка проверена только на синтетических данных тестов, а не на настоящем прогоне пайплайна.
2. 🔴 **Структурный сторож обходится, и обход доказан.** Подмена чтения на цепочку
   `get(...).and_then(...)` без обрезки пробелов оставила весь набор зелёным. Поведенческий тест
   закрывает известный сценарий (строка из пробелов), но не гарантирует, что не существует другого
   способа получить пустой вердикт мимо нормализатора.
3. 🔴 **Согласованность четырёх выходов проверена по одному классу расхождения.** Сторож на
   противоречие «баннер против канальной директивы» написан для HTML и презентации; для Markdown и
   XLSX такого документного сторожа нет — там проверяется только наличие плашки.
4. **Правка `identifier_dir` не проверена живым сосуществованием двух редакций на одной машине.**
   Вывод о безопасности сделан из кода: у облачной редакции значение совпадает с прежним жёстко
   заданным, у локальной путь переезжает, а сам файл состояния эфемерен. Реального прогона двух
   установленных редакций не было.
5. **Пересобранный движок не проверен работой приложения.** Сборка прогнала собственный smoke-тест
   (проверка CSV и XLSX) и подтвердила свежесть, состав правок внутри проверен чтением файлов в
   собранном каталоге — но отчёт настоящим прогоном продукта не строился.
