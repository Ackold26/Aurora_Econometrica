# Handoff — CPD-69/CPD-70 (Econometrica, v2.4.8)

## Цель блока

Устранить класс дефекта «молчаливая потеря результата клиента» в Aurora AI Econometrica, найденный внешним письмом Docs Lab (перенесено из их продукта). Два независимых дефекта:

1. **CPD-69.** Функция `clear_workspace_files` при каждом запуске программы удаляла файлы не только из `inbox` (временные входящие одного прогона — это нормально), но и из `exports` (готовые документы клиента на его Рабочем столе, `%USERPROFILE%\Desktop\AIAgency\<кабинет>\exports`) — без предупреждения, без корзины, без строки в журнале о том, что именно удалено.
2. **CPD-70.** Сохранение готового документа (md/docx/xlsx/pptx/html-отчёт) шло по вычисленному имени без проверки, существует ли уже файл с таким именем — повторная генерация молча затирала предыдущий результат.

Код обязан: (а) чистить при старте только `inbox`; (б) при коллизии имени экспортируемого документа — не перезаписывать существующий файл, а сохранять новый рядом со счётчиком («имя (2).ext», «имя (3).ext», …).

## Ключевые инварианты

- **Папка `exports` неприкосновенна на старте программы.** Ничто в пути запуска приложения не должно трогать файлы в `<workspace>/exports/*`. Это закреплено именованной константой `WORKSPACE_DIRS_CLEARED_ON_START = &["inbox"]` (Rust) и структурным тестом-сторожем, который проверяет САМУ константу, а не поведение функции — он ловит будущую попытку вернуть `"exports"` в список по невнимательности.
- **Коллизия имени при экспорте разрешается детерминированно и монотонно.** `unique_export_path(path)` — свободный путь возвращается как есть; занятый получает суффикс `(2)`, если тоже занят — `(3)`, и так далее без верхнего предела. Функция НЕ создаёт файл и не блокирует его — только вычисляет путь; запись остаётся на вызывающей стороне. Между вычислением пути и фактической записью есть TOCTOU-окно (два параллельных вызова могут теоретически получить один и тот же путь) — это осознанно принято как устраняющее РЕГУЛЯРНЫЙ случай (повторный ручной экспорт одного пользователя), а не гонку потоков.
- **Путь, возвращаемый клиенту в ответе команды, обязан совпадать с реально записанным файлом.** Там, где команда возвращает JSON с полем `path` (например `econ_generate_report`, `econ_export_xlsx`), защита от коллизии применена ДО вызова функции записи, а не внутри неё — чтобы возвращаемый путь не разошёлся с фактическим.
- **Существует ровно ОДНА реализация `unique_export_path` на язык** — Rust (`commands/mod.rs`) и Python (`utils/safe_io.py`) — общего слоя между языками в продукте нет, дублирование логики между ними неизбежно и осознанно.

## Осознанные компромиссы

1. **Защита в `report.rs::econ_export_xlsx` стоит НЕ в точке `wb.save(path)` внутри `build_xlsx`, а на вычислении `path` ДО вызова `build_xlsx`.** Причина: `build_xlsx` получает путь по ссылке и не возвращает итоговый путь наружу — правка внутри неё разошлась бы с ответом команды клиенту (см. инвариант выше). Единственный продакшен-вызов `build_xlsx` подтверждён (остальные вызовы в тестах) — то есть защита покрывает весь боевой путь, но НЕ покрывает саму функцию `build_xlsx`, если у неё появится второй вызывающий в будущем без такой же предварительной защиты.
2. **`pptx_processor.rs:539` (`chunk_*.json`) сознательно НЕ тронут.** Это служебные файлы пайплайна для батч-отправки слайдов в Claude, не документ, который открывает клиент. Решение принято по прочтении контекста, не по одному имени файла.
3. **`persistence_safe.py` (`latest.pkl`) сознательно НЕ тронут.** Внутреннее сохранение состояния модели — оно ДОЛЖНО перезаписываться при каждом обучении, это не документ клиента.
4. **`claude.rs:602` (partial-снимок при retryable error) починен ТЕМ ЖЕ паттерном, хотя изначальное задание просило «решить по месту».** Обоснование субагента: тот же `exports_dir`, тот же видимый клиенту список файлов, при быстрых повторных ошибках подряд секундный таймстемп в имени может совпасть. Проверено лично по диффу, не переделывалось.
5. **Дважды заведена общая функция вместо переиспользования одной.** Rust и Python — разные рантаймы одного продукта, разделяемого модуля кода между ними нет технически.
6. **`json_export.py::export_model_params_to_file` НЕ тронут** — сохраняет без проверки существования, но функция нигде не вызывается из `server.py`/боевого движка (мёртвый код относительно живых потоков). Если позже подключится — тот же класс дефекта там будет присутствовать.

## Зоны неуверенности

1. **Второй носитель класса CPD-69 в других путях запуска.** Проверено, что `close_session`/`close_all` (`session/manager.rs`) чистят только `inbox` временного каталога сессии (не пользовательской папки) — это признано by-design и НЕ тем же классом. Но полного грепа по ВСЕМ вызовам `remove_file`/`remove_dir_all` в дереве не делалось — только целевой поиск по сигнатуре исходного дефекта (`&["inbox", "exports"]`) и по имени функции `clear_workspace_dirs`.
2. **Реальная частота коллизий имени в проде не измерена.** `server.py` формирует имена с секундным таймстемпом (`mmm_report_{ts}.pptx`) — по утверждению Python-субагента коллизия «маловероятна, но не исключена» (двойной клик/ретрай). Защита добавлена на общих основаниях, но нет данных о том, как часто она реально сработает у клиентов и не станет ли неожиданностью «почему у меня появился файл с (2) в имени».
3. **Совместимость поля `"renamed"` в событии `exports-updated-{cabinet_id}` с фронтендом подтверждена ТОЛЬКО чтением `FileList.svelte` за один проход** (субагент сообщил, что фронтенд поле не читает) — не гонялся живой UI-тест на предмет того, что добавление нового поля в JSON-событие не ломает какой-то менее очевидный обработчик события в другом месте кода.
4. **Структурный сторож CPD-69 (тест на константу `WORKSPACE_DIRS_CLEARED_ON_START`) проверен мутацией лично.** Но не проверялось, существует ли в проекте ДРУГОЙ, независимый структурный тест где-то ещё (например, паритетный тест Rust↔фронтенд, как это принято в других блоках этого продукта — см. историю `feedback_measure_where_the_consumer_reads`), который мог бы теперь читать устаревший текст логов (строка журнала поменялась с `"Workspace cleaned for {cabinet_id}: inbox + exports"` на новую формулировку с числом) — целевого грепа по старому тексту строки лога не проводилось.
