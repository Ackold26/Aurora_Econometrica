# Handoff для внешнего аудитора – s50, «доля канала одним числом» + экран разложения

Диапазон на аудит: `21526770..473f4967` (кодовые записи `0f3f8d7a`, `7877a5d8`, `473f4967`; остальные записи
диапазона – документы `Projects/*.md`). Предыдущая часть сессии `8ea0e6b0..21526770` (перенос CPD-84, первая
правка доли) уже прошла независимый аудит (Opus, находки в `Projects/PULSE_s50_auditor.md`); эта правка – его
следствие (H-1, M-1, M-3, L-3 и находка вне правки про экран разложения).

## 1. Цель блока

Доля канала в эффекте (вклад канала / весь медиа-вклад, %) должна показываться клиенту ОДНИМ числом из ОДНОГО
источника на всех поверхностях отчёта и экрана: таблица каналов (веб и презентация), заголовок раздела S7
(«топ-N каналов дают X%»), доля лидера в тексте и крупным числом, счётчик крупного числа в вебе, экран разложения
в режиме «Эффективность». Источник – `contribution_pct` из движка (`engines/decomposer.py`, одна десятая,
знаменатель – вклад ВСЕХ каналов); его протягивают через `narrative_adapter._merge_channels`, а при отсутствии
(старые сохранённые проекты) – вычисляют по всем каналам через `utils/kpi_display.py::channel_share_pcts`.
Отдельно: экран разложения умножал уже процентную `share_of_effect` на 100 ещё раз («8750.0%»).

## 2. Ключевые инварианты

- INV-50: число на экране равно расчёту; одна и та же доля на одной поверхности не может отличаться между
  заголовком и строкой.
- Знаменатель доли – весь медиа-вклад (все каналы), а не видимые 10 строк таблицы.
- Заголовок топ-N = сумма УЖЕ ОКРУГЛЁННЫХ долей строк топ-N (совпадает с тем, что читатель сложит глазами).
- `fmt_pct` с условной точностью (приросты, MAPE) не менялся – меняются только места показа ДОЛИ канала.
- Старые проекты без `contribution_pct` открываются и показывают долю, посчитанную по всем каналам.
- Сторожа переполнения текста в презентации не ослабляются: при конфликте чинится макет.
- Клиентский текст: русский, короткое тире «–», разделитель дроби – точка (как в соседних числах таблиц).

## 3. Осознанные компромиссы

- Одна десятая не гарантирует сумму ровно 100.0 (три равных канала: 33.3×3 = 99.9) → принято; метод наибольшего
  остатка не вводился, чтобы число строки совпадало с расчётом движка. Докстрока `share_pct_value` это говорит.
- Крупное число слайда 4 при 6 знаках («100.0%») конфликтует с подписью под ним на 0.2" по оценке проверки
  переполнения → оставлено строгим `xfail` (`test_pptx_big_number_with_decimal_fits[100.0]`), решение за
  владельцем; кегль крупного числа ужимается под длину (отдельный тест «в одну строку»).
- Прежняя промежуточная правка `af8c2015` (столбец таблицы через `share_pct_value`) не откатывалась – поверх неё
  введён единый источник.

## 4. Зоны неуверенности

1. **Протягивание `contribution_pct` через `narrative_adapter._merge_channels`** – не теряется ли поле на каком-то
   ином пути сборки payload (другие вызовы builder'ов, JSON для экрана, XLSX, markdown `report.rs`), где доля
   по-прежнему считается на месте и может разойтись.
2. **Подбор кегля крупного числа в `aurora_pptx/builder.py` (~стр. 900)** – не ломает ли он другие крупные числа
   того же макета (не-доли: суммы, ROI), которые идут через ту же функцию.
3. **Счётчик `interactive.py` (animateCounter/formatCounterValue/setupCounters)** – число знаков после запятой
   берётся из разметки; не задето ли поведение счётчиков сумм и целых величин.
4. **`DecomposeStep.svelte` `channelSharePct`** – фолбэк `contribution / total_contribution * 100` для данных без
   `share_of_effect`: верен ли `total_contribution` по смыслу (медиа-вклад или весь с базой).
5. Сторож `tests/test_channel_share_single_source.py` строится на синтетических payload; живой отчёт на
   реальном проекте после этой правки НЕ пересобирался (движок в поставке 2.5.5 – до правки).
