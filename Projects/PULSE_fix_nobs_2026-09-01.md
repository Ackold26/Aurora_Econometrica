# PULSE — fix_nobs (2026-09-01)

## 00:51 — старт, пересказ своими словами

Задача: две соседние проверки в мастере Econometrica показывают пользователю разные числа наблюдений по одному и тому же файлу, и разница не подписана.

- «Проверка данных» (`POST /compute/validate`) считает 104 — строки, где известна целевая величина (обучающая история).
- «Предполётная проверка» (`POST /compute/preflight`) считает 130 — все строки файла, включая 26 недель медиаплана вперёд.

Оба числа верны для своей цели, но подряд, без пояснения, выглядят как расхождение. Расчёт трогать нельзя — только подписи в интерфейсе (и, если понадобится, в самом ответе движка, если оттуда текст доезжает до экрана без изменений).

## План
1. Найти в движке (`sidecar/econometrica/engines/validator.py`, `server.py`) откуда идут `rows`/`n_obs`, убедиться что это те самые два числа.
2. Найти во фронтенде (`src/lib/components/pipeline/...`, вероятно шаг «Валидация» и `ConfigPanel.svelte` для предполётной) — где эти числа выводятся пользователю.
3. Подписать оба текстом, поясняющим разницу, не меняя расчёт.
4. Прогнать `npm run check` (0 ошибок должно остаться) и, если правил Python — тесты движка.
5. Отчёт с диффами и цитатами подписей.

Это подтверждает рамку задачи: оба числа посчитаны верно для своей цели (история обучения vs
полный объём файла), но по разным путям чтения одного файла — почему они и расходятся.

**Важная находка:** сырое число `n_obs` из `/compute/preflight` (130) нигде во фронтенде не читается —
`grep -r "\.n_obs" src/` не дал ни одного совпадения. `ConfigPanel.svelte` (реальный вызов
`invoke('econ_preflight', ...)`, строка 474) показывает только качественную подпись источника
(`PREFLIGHT_SOURCE_RU.n_obs = 'объём наблюдений'`, без числа) и текстовые `warnings`/`recommendation`
из движка. Число «130» на демо-файле НЕ попадает в эти тексты, потому что `_honest_n_obs_tone`
даёт `'good'` и для 104, и для 130 (порог ≥30) — а `reason` с явным `n=…` добавляется в warnings
только когда тон **не** `'good'` (`server.py:1127`). Значит на экране пользователь никогда не видел
«130» рядом со «104» в этом сценарии — расхождение было видно только при прямом сравнении JSON-ответов
двух эндпоинтов, не на экране.

**Риск на будущее (не чиню, вне периметра задачи — «расчёт не менять»):** для пограничного файла
(история 25-29 недель + длинный хвост плана, суммарно ≥30 строк) `/compute/preflight` посчитает
`n_obs_tone='good'` по надутому числу (с хвостом плана), хотя настоящих обучающих недель мало —
и тон не совпадёт с тем, что показывает «Валидация» по тем же данным. Сообщаю team lead отдельно,
чтобы завести как отдельный пункт (это не подпись, это основание вывода движка).
