## 2. High-2 – признак верит протухшему `results/media_plan.json`

**Вердикт: ПОДТВЕРЖДЕНА.**

### Вывод зонда ДО правки (дословно)

```
=== High-2: один каталог проекта, сначала плановый образец, потом базовый ===
  шаг 1 — импорт planning/synth_fmcg_brand.xlsx: validate=ok
  [после планового] media_plan.json существует = True, n_future_periods = 32, media_plan_absent() = False
  шаг 2 — импорт базового synth_fmcg_brand.xlsx (без хвоста): validate=ok

  ОЖИДАЕТСЯ media_plan_absent() = True (в текущих данных плана нет)
  ФАКТ: False  → находка ПОДТВЕРЖДЕНА
```

Причина ровно та, что назвал аудитор: запись файла жила **внутри** `if _tail_result.get('found')`,
то есть при отсутствии хвоста файл прошлого импорта никто не трогал.

### Что изменено

Лечение на стороне записи – источник признака остался ОДИН (`results/media_plan.json`,
тот же файл, что читает интерфейс), второй формулы не заведено.

- `sidecar/econometrica/engines/validator.py:368-434` – новая функция `_write_media_plan_state`.
  Пишет файл атомарно (`mkstemp` + `os.replace`) при **любом** исходе проверки данных:
  хвост найден → найденное; хвоста нет → `n_future_periods: 0`; определить не удалось →
  `n_future_periods: null` + `detection: "unavailable"`.
- `sidecar/econometrica/engines/validator.py:487-549` – блок детекции перестроен: состояние
  хвоста собирается в `_tail_found`, запись вынесена из-под условия «хвост найден» и делается
  всегда, когда задан абсолютный `project_dir`.
- Файл **не удаляется** (правило проекта – удаление только в корзину): он перезаписывается
  честным содержимым.
- `src/lib/project-state.js:1261-1267` – **обязательное следствие**: раз файл теперь есть
  всегда, при загрузке проекта с диска его нельзя класть в `mediaPlanDetected` без проверки.
  Стало `if (r.mediaPlan && (r.mediaPlan.n_future_periods ?? 0) > 0)`. Без этой защиты на
  данных без плана поднялся бы баннер подтверждения медиаплана на шаге «Валидация»
  (`ValidateStepV13.svelte:227`) и шаг «Планирование» увидел бы пустой план.

### Чем доказано, что доехало

- `tools/test_narrative_coherence.py`, проверки **S4a/S4b**: тот же каталог проекта, сначала

## 3. Medium – проглоченный сбой записи превращался в «плана нет»

**Вердикт: ПОДТВЕРЖДЕНА.**

### Вывод зонда ДО правки (дословно)

```
=== Medium: сбой записи media_plan.json при валидации плановых данных ===
  validate вернул status = ok (сбой проглочен: наружу не вышел)
  в данных ХВОСТ ЕСТЬ: media_plan_detected в ответе = True
  media_plan.json записан = False; validation.json записан = True
  media_plan_absent() = True
  ОЖИДАЕТСЯ: не True (план в данных ЕСТЬ) — либо False, либо None «определить не удалось»
  ФАКТ: True → находка ПОДТВЕРЖДЕНА
```

### Что изменено

`sidecar/econometrica/engines/optimizer.py:267-297` – `media_plan_absent` различает три
состояния честно:

- файла нет → **`None`** («определить не удалось»). Прежнее правило «нет файла, но есть
  `validation.json` → плана нет» убрано: именно оно превращало сбой записи в уверенную ложь.
  Правило стало безопасным ровно потому, что `validate_data` теперь пишет файл всегда;
- `n_future_periods: null` в файле → **`None`** (проверка данных не смогла определить хвост);
- иначе → `True`/`False` по числу будущих периодов.

Плюс, если запись сорвалась, а на диске лежит файл прошлого импорта, он отводится в сторону
под именем `media_plan.json.stale` (`validator.py:428-434`) – переименование, не удаление.
Иначе молчащий сбой оставил бы прошлогоднюю правду выдавать себя за текущую.

`None` для вызывающего означает прежнее поведение: ветка про будущие периоды не поднимается,
клиенту показывается честная причина остановки решателя.

### Чем доказано, что доехало

- `tools/test_narrative_coherence.py`, проверка **S5**: имитация сбоя `os.replace` на
  `media_plan.json` при плановых данных → признак `None`, а не `True`. Зелёная.
- `tools/test_optimizer_stalled_insight.py::test_media_plan_state_is_three_valued` –
  все три состояния плюс файл с `n_future_periods: null`.

## 5. Что я НЕ стала менять и почему

1. **Сам решатель и математику оптимизации** (многостарт, SLSQP, якорь границ по умолчанию,
   пороги достаточности 20/30 и покрытия 0,5/0,8) – прямой запрет в задании. Зонд показывает,
   что настоящая причина нулевого прироста живёт здесь: улучшение на 1,07 % целевой функции
   существует, а решатель выходит на первой итерации. **Это не закрыто и остаётся открытым
   дефектом** – моя правка сделала текст честным, но не вернула клиенту прирост.
2. **`src/lib/insights-rules.js:2288`** – действие «Расширьте границы – Мин. % → 20–30 %,
   Макс. % → 200–300 %: оптимизатор получит пространство для перекладки». Оставила намеренно и
   выношу на решение: (а) это досессионный код, а не воскрешение мной удалённого совета;
   (б) он поднимается только когда насыщена хотя бы половина каналов (`manyChannelsSaturated`),
   то есть не на каждом нулевом приросте; (в) сформулирован как «получит пространство», без
   обещания прироста. Но замер на демо-наборе (0,0 % и на 0/500) означает, что клиент,
   последовавший ему, получит тот же ноль. Если решите убрать – это одна строка, скажите.
3. **Копии сборки** `sidecar/econometrica/dist/econometrica-sidecar/_internal/` и
   `sidecar/econometrica/_internal/` – там лежат те же файлы со старым текстом, но это
   артефакты сборки, а не исходники; правятся пересборкой сайдкара. Сборку не запускала
   (запрет в задании). **Перед показом покупателю сайдкар нужно пересобрать**, иначе в
   приложении останется старый текст.
4. **Ветку `binding_constraints`** («все каналы упёрлись в границы, расширьте до 10/300 %») –
   не трогала: она про другое состояние, аудит её не оспаривал, замер её не опровергал.
5. **Соседний текст SCQAR** «оптимизатор не нашёл значимого перераспределения. Возможные пути
   роста: расширение бюджета или новые каналы» (ветка малой переброски при найденном приросте) –
   досессионный, к находке отношения не имеет, оставлен как есть.
6. **`Projects/NEXT_SESSION_PROMPT.md`, `Projects/handoff.md`, файлы памяти** – по запрету.

### 8.2 Что происходит с прежним `media_plan.json` – точно

Ты просила описать точно, потому что зондом это не проверяла. Код –
`sidecar/econometrica/engines/validator.py:415-434`.

**Обычный ход (запись удалась).** Файл **переписывается на месте**, атомарно: содержимое
пишется во временный `results/.mp_XXXX.tmp`, затем `os.replace` переносит его на боевое имя
`results/media_plan.json`. Рядом не остаётся ничего – ни копии, ни следа прежнего содержимого.
Прежняя версия не сохраняется нигде: она заменяется. Удаления файлов нет.

**Сбой записи.** Временный файл (наш собственный, только что созданный) снимается `os.unlink` –
это досессионная строка, я её не добавляла; пользовательских данных она не касается. Дальше
прежний `results/media_plan.json`, если он есть, **переносится** (`os.replace`) в
`results/media_plan.json.stale`. То есть **да, рядом с проектом остаётся файл**.

**Может ли кто-то прочитать `.stale` как настоящий – нет.** Проверила всех читателей: они
обращаются по точному имени, а не по маске.

| Читатель | Что открывает |
|---|---|
| `engines/optimizer.py:288` (`media_plan_absent`) | `results/media_plan.json` |
| `engines/planning.py:654` (подтверждение плана) | `results/media_plan.json` |
| `src-tauri/src/commands/project.rs:656` (загрузка проекта) | `read_json("media_plan.json")` |

Перебора `results/*.json` по маске в дереве нет вовсе: маски встречаются только по
`results/scenarios/*.json` (`scenario.py:1271`, `server.py:2314`, `:2385`),

(`engines/causal/preflight.py:221`). Ни одна не захватывает `results/` верхним уровнем.

**Файлов не копится.** Повторный сбой снова делает `os.replace` на то же имя `.stale` –

удалось» вместо уверенной лжи «план есть» на данных, где его нет. Сам `.stale` остаётся
следом для разбора, не источником.

его тоже не подхватят.
