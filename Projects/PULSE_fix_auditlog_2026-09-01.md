# PULSE — правка гонки записи журнала аудита

## Задача своими словами
В `%LOCALAPPDATA%\com.aurora.econometrica\audit.log` строки при частых параллельных вызовах
(`online_auth` подряд) физически наложились друг на друга — метка времени разорвана. Причина:
`Mutex<Vec<AuditEntry>>` в `src-tauri/src/metrics/audit.rs` защищает только вектор в памяти;
запись в файл (`append_to_file`) выполняется УЖЕ ПОСЛЕ отпускания этого замка, без своей
синхронизации — несколько потоков пишут в файл одновременно, строки перемешиваются.
Второй, менее явный случай той же гонки: `rotate_if_large` (переименование файла при превышении
размера) тоже вызывается без синхронизации — один поток может переименовать файл, пока другой
в него пишет.

## План
1. [00:50] Прочитать `audit.rs` и `durable_store::rotate_if_large` — подтвердить причину.
2. Добавить отдельный статический замок `Mutex<()>` только для файловой записи (не расширять
   область существующего замка памяти). Взять его на всю `append_to_file` — и ротацию, и открытие
   файла, и запись строки.
3. Поведение при отравлении замка (`PoisonError`) — не ронять программу, сохранить мягкость
   («по возможности», `let _ =` у вызывающего) через `unwrap_or_else(|poisoned| poisoned.into_inner())`.
4. Написать проверку: много потоков пишут в журнал во временный каталог, читаем файл, считаем
   строки — без правки красная (наложения/потери строк), с правкой зелёная.
5. `cargo check` с `CARGO_TARGET_DIR="D:/cargo-targets/ai-agency"`.
6. Отчёт с дифом и числами.

## Отчёт [01:05]

**Причина подтверждена.** `AUDIT_LOG: Mutex<Vec<AuditEntry>>` защищает только вектор в памяти
и отпускается в `log_event` ДО вызова `append_to_file` (`audit.rs:31-41` до правки) — файловая
запись шла вообще без синхронизации. `rotate_if_large` вызывался тем же путём без замка —
второй, менее явный случай гонки (переименование файла параллельно с записью в него).

**Решение:** отдельный статический замок `AUDIT_FILE_LOCK: Mutex<()>` только для файловой
записи, взятый на всё тело `append_to_file` (ротацию, открытие файла, запись строки) —
не расширяет область существующего `AUDIT_LOG` на время работы с диском (это было явное
пожелание, и оно совпадает с общим принципом «не держать замок памяти на время I/O»).
`PoisonError` не роняет запись: `unwrap_or_else(|poisoned| poisoned.into_inner())` достаёт
guard даже из отравленного замка — вызывающий код и так трактует `append_to_file` как
best-effort (`let _ =`), и это поведение сохранено без изменений.
