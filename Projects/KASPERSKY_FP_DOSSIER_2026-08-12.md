## 5. Объяснение подозреваемых поведений (со ссылками на код)

Ниже — по каждому пункту из контекста задачи: что реально делает код и почему это легитимное поведение десктопного приложения, а не вредоносная активность. Цитаты — с указанием файл:строка в исходниках репозитория `D:\Docs\Aurora_Ai\Dev\Aurora_Econometrica_thinwt\src-tauri\src\`.

**1. `icacls` на каталог сессий** — `session/manager.rs:114-120`:
```rust
let mut icacls_cmd = std::process::Command::new("icacls");
icacls_cmd.args([
    sessions_root.to_str().unwrap_or_default(),
    "/inheritance:r",
    "/grant:r",
    &format!("{qualified}:(OI)(CI)F"),
]);
```
При старте приложение один раз ограничивает права доступа к своей рабочей папке `sessions\` (в `%APPDATA%`) только текущим пользователем — там временно распаковываются расшифрованные данные из зашифрованного vault-хранилища клиента (маркетинговые бюджеты, медиапланы). Цель — не дать прочитать эти данные другому пользователю той же машины (многопользовательский Windows/RDP-сценарий). Это защитное, а не деструктивное действие: программа СУЖАЕТ доступ к СВОИМ ЖЕ файлам, не трогая чужие каталоги и не повышая собственные привилегии.

**2. `netstat` через `cmd /C`** — `econ_sidecar.rs:235-236`:
```rust
let output = Command::new("cmd")
    .args(["/C", &format!("netstat -ano -p tcp | findstr :{port}")])
```
Перед запуском локального Python-движка (`econometrica-sidecar.exe` / `server.py`) на выбранном локальном порту приложение проверяет, не занят ли порт «зависшим» процессом от предыдущего аварийного завершения, и следом убивает только зависший процесс, если тот принадлежит тому же пользователю ОС и совпадает по имени образа: `if !sidecar_runtime::is_our_process_and_user(pid, &SIDECAR_CONFIG) { ...skipping kill... }` (`econ_sidecar.rs:253-258`). На multi-user машине чужие процессы намеренно не трогаются — комментарий в коде это явно оговаривает (`econ_sidecar.rs:230-231`). Далее в этом же файле есть `taskkill /PID ... /T /F` (`econ_sidecar.rs:260-263` и `:710-713`) — тот же самый механизм: принудительное завершение СВОЕГО ЖЕ зависшего дочернего процесса при штатной остановке или при обнаружении «зомби» на нужном порту, не сторонних процессов.

**3. Спавн дочернего процесса Python-движка** — `econ_sidecar.rs:293-298` (упакованный бинарь) и `:330-336` (dev-режим, системный `python`):
```rust
let mut cmd = Command::new(&exe_path);
cmd.arg(port.to_string())
    .env("AURORA_PRODUCT_ID", SIDECAR_CONFIG.product_id)
    .env("AURORA_PRODUCT_VERSION", SIDECAR_CONFIG.version)
    .stdout(Stdio::null())
    .stderr(Stdio::null());
```
Приложение по архитектуре — Tauri-обёртка (Rust) + локальный расчётный движок на Python (байесовское MMM-моделирование), упакованный как «sidecar»-процесс. Родительский процесс GUI запускает движок как дочерний процесс на локальном порту (`127.0.0.1`), передаёт ему через переменные окружения только идентификатор и версию продукта — никакой сетевой активности вовне, обмен строго между GUI и локальным движком на loopback. Это стандартный паттерн Tauri (см. документацию `tauri-sidecar`), а не техника внедрения/маскировки процесса.

**4. Шифрование собственных файлов хранилища AES-256-GCM** — `crypto/aes.rs:13-29`:
```rust
pub fn encrypt(key: &[u8; 32], plaintext: &[u8]) -> Result<Vec<u8>> {
    let cipher = Aes256Gcm::new_from_slice(key)...
    let nonce = Nonce::from_slice(&nonce_bytes);
    let ciphertext = cipher.encrypt(nonce, plaintext)...
```
Ключ шифрования выводится через HKDF из машинного отпечатка и лицензионной соли (см. `CLAUDE.md` проекта, раздел «Система защиты»: «Vault: AES-256-GCM, ключ = HKDF(fingerprint, license.salt)»). Это шифрование клиентского vault-хранилища (маркетинговые данные заказчика) для локального хранения на диске — не шифрование чужих файлов пользователя и не программа-вымогатель: ключ производный от лицензии конкретной машины, шифруются только собственные файлы приложения в его собственном каталоге данных, назначение — конфиденциальность данных клиента (агентства работают с коммерческой тайной рекламодателей), не вымогательство.

**5. Сбор отпечатка машины для лицензии** — `crypto/fingerprint.rs:44-58` и `:69-165`:
```rust
/// Collects machine-unique identifiers and produces a SHA-256 fingerprint.
/// Components: Machine UUID + Disk Serial + Motherboard Serial.
pub fn get_machine_fingerprint() -> Result<String> { ... }
```
Через WMI (`Win32_ComputerSystemProduct`, `Win32_DiskDrive`, `Win32_BaseBoard`) собираются публично читаемые идентификаторы оборудования (UUID материнской платы, серийные номера жёсткого диска и платы), из них считается SHA-256-хеш — «отпечаток машины». Это стандартный механизм привязки офлайн-лицензии к конкретному компьютеру (защита от копирования лицензионного файла на другие машины), применяемый повсеместно в коммерческом ПО с офлайн-активацией. WMI-запросы — штатный, документированный Windows API, не эксплуатация уязвимостей; данные никуда не передаются без согласия пользователя в рамках процедуры лицензирования.
