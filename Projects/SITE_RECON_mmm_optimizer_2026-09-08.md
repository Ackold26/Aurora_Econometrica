## 2. Как устроен образец (synthetic-research.pro)

Дерево: D:\Docs\Aurora_Ai\http_synthetic_research_pro — pnpm-монорепозиторий, подтверждено: НЕ под git (git status → fatal: not a git repository).

Устройство:
```

packages/guards/            охранные тесты клиентского текста (общие для всех сайтов)
```

Корневой package.json называется "aurora-product-sites" — монорепо изначально задумано на несколько продуктовых сайтов (sites/<продукт>/), общий слой пока не выделен ("выделять нечего, пока сайт один" — README.md). Для второго сайта это готовый каркас: завести sites/mmm-optimizer/ рядом.

Сборка: `corepack pnpm@9.15.0 build` (pnpm нет в системном пути, только через corepack) → sites/synthetic-research/dist/. Node ≥22.

Сторожа (запускаются `pnpm test` = `vitest run`): 20 файлов тестов в packages/guards/src/*.test.ts — проверяют текст на: запрещённые упоминания клиентов, несовпадающие с кодом продукта данные, регресс юридических пометок, запрещённый телефон/цену, "уверенные" формулировки без числа, склеенные слова, висящие короткие слова, корректность JSON-LD, покрытие маршрутов nginx, отсутствие ссылок на /ru/, факты панели, числа из product-facts.ts, мягкие переносы и др. Состояние на 01.09: 174 проверки, 0 пропусков, каждый сторож проверен мутацией (внесённый дефект красит ровно свой тест). Периметр vitest.config.ts явно исключает Projects/** — иначе подхватывает исторические снимки сторожей.

Выкладка — deploy/deploy.sh <путь-к-dist>, запускается НА узле:
- копирует dist/ в /var/www/<продукт>/releases/<UTC-метка>/;
- атомарно переключает симлинк current на новый релиз (ln -s + mv -T, rename атомарен);
- старые релизы не удаляются — откат = переключить симлинк вручную, чистка отдельная и вручную;
- перезагрузка nginx не нужна при обычном обновлении контента (root — симлинк).

Порядок первой выкладки (deploy/README.md, детально):
0. Владелец чинит DNS (см. §1 выше).
1. Мы собираем статику, кладём nginx.conf + security-headers.conf на узел (/etc/nginx/sites-available/ + симлинк в sites-enabled/, snippets/), `nginx -t && systemctl reload nginx`.
2. deploy/deploy.sh <dist>.
3. Владелец выпускает сертификат: `certbot --nginx -d <домен>` — certbot и автопродление уже настроены на узле a, шаг только добавляет домен. Известная ловушка, найденная боем на synthetic-research.pro: certbot дописывает свои блоки server для редиректа http→https и НЕ переносит в них access_log off; — нужно руками добавить и проверить мутацией (тестовые запросы + grep -c по журналу), иначе IP посетителей пишутся в общий журнал узла вопреки политике. Для второго домена этот шаг уже известен — просто повторить.
4. 8 проверок после выкладки (deploy/README.md §2): nginx -t, 200 на /, robots.txt, sitemap-index.xml, честный 404 (не стандартный nginx), заголовки безопасности, пустой/отсутствующий access.log, 502 на /api/lead пока приёмщик не поднят.

## 4. Кратчайший путь к заглушке — два варианта

### (а) Минимальная одностраничная заглушка

Один статический HTML/Astro-файл: название + tagline + 3-4 буллета "что делает" (из ванпейджера — экспертиза в движке / байесовское моделирование / паспорт расчёта / локально) + контакт (почта или телефон) + правовой минимум в подвале (см. §5). Без формы, без сравнительных таблиц, без FAQ.

- Технически: можно сделать прямо в этом же монорепо aurora-product-sites — sites/mmm-optimizer/ по образцу sites/synthetic-research/, но с одной страницей index.astro вместо шести. Общий Astro-каркас (конфиг, стили, layout) копируется и упрощается — часа 2-3 работы, если писать по образцу. Сторожа packages/guards частично общие (запрещённая цена/телефон/клиенты), частично специфичны для SR-текста — для заглушки достаточно 3-4 самых общих (запрещённый телефон, запрещённая цена не по канону, глюки текста), не все 20.
- Что копировать один в один: deploy/deploy.sh, deploy/nginx.conf (переименовать домен), deploy/security-headers.conf, порядок из deploy/README.md §0 (DNS) и §1 (выкладка) — процедура идентична, только имя домена и каталог /var/www/mmm-optimizer/.
- Оценка времени: вёрстка страницы 2-4 часа + перенос DNS-процедуры (известна, но ждёт распространения — TTL записи и выпуск сертификата не мгновенны, закладывать час-два на пропагацию) + выкладка на узел 30-60 минут. Реалистично успеть к утру четверга, если DNS-перенос начать сегодня-завтра, а не в среду вечером — сама миграция зоны у synthetic-research заняла у владельца часть 04.09, плюс TTL и выпуск сертификата съедают время, не зависящее от нас.

### (б) Страница поплотнее, по образцу synthetic-research.pro

Полноценная многоэкранная страница: главная драматургия (проблема → продукт → таблица "разница, которую видно" → 4 отличия из "Чем отличается" → для кого → цена/пилот → призыв), возможно вторая страница про методологию.

- Технически: тот же монорепо, sites/mmm-optimizer/ с несколькими страницами по образцу sites/synthetic-research/src/pages/, полный набор из 20 сторожей (большинство сразу переиспользуются, т.к. проверяют паттерны текста, а не конкретный продукт).
- Оценка времени: это по объёму сопоставимо с работой, которая заняла над synthetic-research.pro неделю с лишним (судя по датам файлов в Projects/ образца — с 29.08 по 08.09, включая копирайт, дизайн, юридический контур, GEO/SEO, конкурентный анализ). К четвергу 10.09 нереально при том же уровне глубины.
