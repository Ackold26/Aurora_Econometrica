## Вердикт

**Хвосты безвредны для поведения 2.5.5 (доказано).** Движок у обновившегося покупателя импортирует ровно тот же код, что и при чистой установке, а программа не может запустить старый движок 2.5.0.0 из `dist\`. Ниже три независимые линии доказательства, каждая закрывает свой путь влияния:

1. **Хвосты вне `_internal` (`dist`, `tests`, `.hypothesis`, исходники верхнего уровня) недостижимы для импорта.** В замороженном движке `sys.path` = `[_internal\base_library.zip, _internal\python3.12\lib-dynload, _internal]`: каталога exe, рабочего каталога и `PYTHONPATH` в нём нет. Это показано зондом на той же версии PyInstaller и подтверждено вживую канарейками на самом движке.
2. **Хвосты внутри `_internal` – только содержимое `__pycache__`** (1 342 из 1 342 файлов, 170 лишних каталогов, и все они `__pycache__`). Python не берёт `.pyc` из `__pycache__` без исходника (PEP 3147). Исходники всех 1 331 `.pyc` есть в поставке 2.5.5, но заголовки всех `.pyc` устарели и будут отброшены. 1 327 из 1 331 модулей к тому же лежат в PYZ 2.5.5, а PYZ проверяется раньше диска. Кэши numba устарели по штампу исходника.
3. **Живой A/B-прогон** «грязной» и «чистой» копии движка: `/health` одинаков, журналы запуска совпадают построчно (разница только в номере порта), канарейки в 2 222 хвостовых `.py` не сработали ни разу, записей в каталоги движка ноль.

Что **не** безвредно, хоть и не касается поведения: примерно 1 ГБ на диске, хвосты переживают удаление программы (см. §7), в профиле пользователя лежит лишний старый исполняемый движок. Влияние хвостов на время установки (антивирус) не проверено.

## 2. Механизм импорта: что перекрыто PYZ

- Установленный `econometrica-sidecar.exe` побайтно равен exe из дерева: md5 `bd34b008e59e20e746ee971cb3ee50d9`, 67 394 533 байта. Оглавление прочитано `PyInstaller.archive.readers` из `C:\Users\ackol\AppData\Local\Programs\Python\Python312` (PyInstaller 6.19.0), скрипт – `pyz_toc.py`. **В PYZ 8 413 модулей**, например jax 572, pytensor 291, xarray 197, arviz 146, linearmodels 130, pymc 126, utils 35, engines 31. Параметров выполнения (`o`) в архиве нет.
- Порядок поиска в PyInstaller 6.19 (`PyInstaller\loader\pyimod02_importers.py`). `PyiFrozenFinder` ставится крючком пути сразу после `zipimporter`:
  > `sys.path_hooks.insert(idx + 1, PyiFrozenFinder.path_hook)`

  Внутри каждого элемента пути сначала проверяется PYZ, при промахе – обычный `FileFinder`:
  > `entry_data = self._pyz_archive.toc.get(pyz_entry_name)` … `# Entry not found - try using fallback finder (for example, python's own FileFinder) to resolve on-disk`

  Модули движка, загруженные из PYZ, совпадают побайтно с мини-сборкой (`cmp_loader.py`): `pyimod01_archive`, `pyimod02_importers` и `pyiboot01_bootstrap` одинаковы (md5 `c791ebb1…` у importers). Значит, движок собран тем же PyInstaller.
- **Сверка хвостовых `.pyc` с PYZ** (скрипт `pyc_vs_pyz.py`, вывод – `pyc_vs_pyz_out.txt`): из 1 331 `.pyc` **1 327 относятся к модулям, которые есть в PYZ 2.5.5**, и полностью перекрыты. **4 модуля в PYZ отсутствуют**: `aurora_pptx.check_overflow`, `aurora_pptx.font_embed`, `aurora_pptx.text_metrics`, `engines.verdicts`. Их `.py` есть в нагрузке 2.5.5, о судьбе их `.pyc` – в §3.
- **Заголовки `.pyc` устарели все** (`pyc_hdr.py`): ни у одного из 1 162 `cpython-312.pyc` время и размер источника в заголовке не совпадают с `.py` 2.5.5. Пример: у `jax\__init__` заголовок 11.09 12:08:55, а у `.py` в установке 18.09 12:57:56. Python такой `.pyc` отбросит и прочитает исходник. Файлы `cpython-314` интерпретатор 3.12 не видит вовсе (другой тег). Файлы `pytest` используются только pytest.
- **Кэш numba** (`nbi_stamp.py`): штамп в индексе `(1789117734.96, 32215)` для `arviz\stats\density_utils` и `(1776123797.29, 5765)` для `arviz_stats\numba\array`, а у исходников 2.5.5 `mtime = 1789725476.0`. Штамп не совпадает, поэтому numba считает кэш несвежим и компилирует заново – так же, как при чистой установке.
- **Пакеты-пространства имён**: лишних каталогов в `_internal` 170, из них не-`__pycache__` 0 (`nsdirs.py`). Значит, хвост не может превратить отсутствующий модуль в пустое пространство имён и тем самым изменить исход `try: import X / except ImportError`.

## 3. Импортирует ли 2.5.5 хвостовое хоть где-то

- **Модули вне PYZ, до которых можно дотянуться с диска, лежат только в `_internal`.** Хвосты там – одно содержимое `__pycache__`, а `.pyc` без `.py` из `__pycache__` не загружается. Поэтому ни ленивый, ни условный, ни транзитивный импорт (pymc→pytensor, arviz→xarray, `arviz.preview` → `arviz_base/stats/plots`) не может получить из хвостов модуль, которого нет в чистой установке. Все перечисленные пакеты к тому же лежат в PYZ (§2).
- **4 модуля вне PYZ рабочим кодом 2.5.5 не импортируются.** Совпадения grep:
  - `engines/verdicts.py:12` – текст внутри докстринга самого модуля;
  - `aurora_pptx/check_overflow.py:27,30` и `aurora_pptx/font_embed.py:151,153` – взаимные импорты `text_metrics` внутри этой тройки инструментов, запуск которых рассчитан на скрипт (`except ImportError:  # запуск как скрипт, не как модуль пакета`).

  Даже при импорте Python взял бы свежий `.py` 2.5.5, потому что `.pyc` устарел.
- **Имена, существующие только в хвостах верхнего уровня** (`tools`, `tests`, `server`, `build_sidecar`), в коде `engines/ utils/ aurora_html/ aurora_pptx/ charts/ optimize/ server.py aurora_tokens.py` не импортируются: grep пуст.

## 5. Может ли 2.5.5 запустить движок 2.5.0.0 из `dist\`

**Нет.** Кандидатов ровно два, оба – точные пути, без поиска по каталогу (`src-tauri/src/econ_sidecar.rs:466-479`):
```rust
fn resolve_bundled_exe(app_handle: &AppHandle) -> Option<std::path::PathBuf> {
    [
        "sidecar/econometrica/econometrica-sidecar.exe",
        "_up_/sidecar/econometrica/econometrica-sidecar.exe",
    ]
```
Тот же путь используется и как ожидаемый образ при снятии зомби (`expected_engine_image_path`, `econ_sidecar.rs:285-305`). Путь `dist\econometrica-sidecar\econometrica-sidecar.exe` не совпадает ни с одним кандидатом.

Резерв `spawn_python_dev` (`econ_sidecar.rs:502-538`, включается в релизе только при ошибке запуска собранного exe, `:540-548`) запускает `python -B server.py` из `<CARGO_MANIFEST_DIR или ".">\..\sidecar\econometrica`. Во время выполнения `CARGO_MANIFEST_DIR` не задан (это `std::env::var`, а не `env!`), и путь считается от рабочего каталога программы. Хвостовой `_up_\sidecar\econometrica\server.py` оказался бы достижим только при рабочем каталоге `<установка>\_up_`, чего при штатном запуске не бывает. Это не проверялось вживую, риск низкий.

Остальные обращения к каталогу установки хвостов не касаются: справка (`lib.rs:2129`), content-packs (`lib.rs:2241-2249`), `pptx_pipeline` (`commands/pptx_processor.rs:117-133`, ищет `sidecar\pptx_pipeline.py`), RAG и Parser (`lib.rs:3817`, `3858`, каталог `brand-hub`, в поставке его нет).

## 7. Побочные факты (на поведение не влияют)

- **Удаление программы оставит хвосты.** Деинсталлятор удаляет только файлы из списка и снимает каталоги нерекурсивно: `RMDir /REBOOTOK "$INSTDIR\_up_\sidecar\econometrica"` … `RMDir "$INSTDIR"` (`installer.nsi:13980-13987`). Непустые каталоги останутся, вместе с ними примерно 1 ГБ и папка установки. Это вывод по тексту скрипта, живьём не проверялось.
- Старый `dist\…\econometrica-sidecar.exe` 2.5.0.0 лежит в профиле. Программа его не запускает, но это лишний исполняемый файл для антивируса и для ручного запуска.
- Задержка около 27–30 с перед хуком (находка 3 в `PROBE_s50_hook_live.md`) могла бы объясняться проверкой антивирусом около 15 тыс. файлов. **Это гипотеза, она не проверялась.**
