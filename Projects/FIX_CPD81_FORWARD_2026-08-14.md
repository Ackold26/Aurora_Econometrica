# Правка CPD-81 (вторая функция): forward_exports_to_inbox

Запись изменений: `5457a89` (ветка `cpd81-forward-exports`, копия `_wt_cpd81_forward`).

## Что изменено

`src-tauri/src/commands/campaign.rs`, функция `forward_exports_to_inbox` (была строка 522).
Класс дефекта тот же, что закрыт в `persist_step_exports` (запись 1414259, эталон):
результат `std::fs::copy` отбрасывался через `let _ =`, а имя файла безусловно
добавлялось в список «передано» (`forwarded.push(name)`), независимо от того,
скопировался файл в `next_workspace/inbox` или нет.

Функция передаёт выгрузки предыдущего шага пайплайна во входящие следующего —
на Windows живой источник отказа тот же, что и в первой функции: файл занят
антивирусом или другим процессом в момент копирования.

## Новая сигнатура и почему

```rust
#[derive(Debug, Default)]
pub struct ForwardExportsResult {
    pub forwarded: Vec<String>,
    pub failed: Vec<(String, String)>,
}

pub fn forward_exports_to_inbox(prev_exports_dir: &Path, next_workspace: &Path) -> ForwardExportsResult
```

Сигнатура зеркалит `PersistExportsResult` (эталон) — два списка вместо одного `Vec<String>`,
имя структуры и полей выбрано по смыслу этой функции (`forwarded`, а не `copied`, т.к. смысл
операции — «передать во входящие», не «сохранить в архив»). Внутри цикла:

```rust
match std::fs::copy(entry.path(), inbox.join(&name)) {
    Ok(_) => result.forwarded.push(name),
    Err(e) => {
        warn!("Выгрузка не передана во входящие: {name}: {e}");
        result.failed.push((name, e.to_string()));
    }
}
```

Отказ теперь: (1) журналируется `warn!` с именем файла и причиной ОС, (2) не попадает
в `forwarded`, (3) виден вызывающему через `failed`.

## Вызывающие

Единственный вызывающий — `lib.rs:3193`, внутри пайплайна: перед запуском Claude на
очередном шаге функция передаёт выгрузки последнего сохранённого шага (`campaign_dir/
steps/<последний>`) во входящие текущей рабочей папки. До правки результат читался как
`fwd.len()` только для информационного лога об успехе; отказ никак не проявлялся.

После правки:
```rust
let fwd = commands::campaign::forward_exports_to_inbox(&last.path(), &work_dir);
if !fwd.forwarded.is_empty() {
    info!("Forwarded {} files to {}", fwd.forwarded.len(), cabinet_id);
}
if !fwd.failed.is_empty() {
    warn!(
        "Не переданы во входящие {} из {} выгрузок для {}: {:?}",
        fwd.failed.len(), fwd.failed.len() + fwd.forwarded.len(), cabinet_id, fwd.failed
    );
}
```

**Решение по уровню журнала — `warn!`, не `error!`.** Проверил, что происходит с
источником после вызова: `last.path()` — это `campaign_dir/steps/<step_id>`, каталог,
куда `persist_step_exports` УЖЕ скопировал файлы на предыдущем шаге и который никто
не удаляет в этом пути выполнения (в отличие от `close_session()`, которая идёт сразу
после `persist_step_exports` и стирает временный `exports_dir` — там необратимость
реальна и обоснованно даёт `error!` по канону задачи). Здесь после отказа копирования
файл остаётся цел в архиве кампании; теряется не файл, а то, что текущий шаг стартует
без части контекста предыдущего в `inbox`. Это деградация качества шага, не потеря
данных, поэтому `error!` был бы завышением серьёзности — оставил `warn!`, как и внутри
самой функции, но с явным указанием, что каталог `inbox` в этом коде дальше НЕ трогают
(перепроверено — до `sync_inbox`/`run_claude` ничего с `work_dir` не делает).

## Решение по unique_export_path — НЕ применено

В эталоне (`persist_step_exports`) `unique_export_path()` защищает АРХИВ кампании:
совпадение имени там означает «два разных результата одного шага претендуют на одно
имя», и затирать один другим нельзя — это окончательное хранилище клиента.

Здесь цель копирования — `inbox` рабочей папки ОДНОГО запуска шага, не архив.
Совпадение имени в этом каталоге типично означает не «два разных файла», а «тот же
файл передаётся повторно» — при перезапуске шага после сбоя, при повторном проходе
пайплайна с тем же campaign_dir. Применение `unique_export_path()` здесь дало бы во
входящих `report.md`, `report (2).md`, `report (3).md` при каждом перезапуске —
Claude в промпте шага получил бы дубликаты одного и того же контента под разными
именами и не смог бы понять, какой из них актуальный. Оставил перезапись «как есть»
(`inbox.join(&name)`, без счётчика) — это осознанно другое поведение, чем в эталоне,
и обосновано комментарием прямо над структурой и функцией в коде.

## Тесты

Добавлены в `campaign.rs::tests` (после существующих тестов `persist_step_exports`):

1. `forward_exports_to_inbox_success` — файл копируется, `forwarded` содержит имя,
   `failed` пуст, файл реально лежит в `next_workspace/inbox`.
2. `forward_exports_to_inbox_copy_failure_recorded_not_lost` — отказ копирования
   воспроизведён тем же честным приёмом, что и в эталоне: место каталога `inbox`
   занято обычным файлом, поэтому `create_dir_all` внутри функции молча не создаёт
   вложенный путь, а `fs::copy` откажет, потому что родитель целевого пути — не
   каталог. Портируемо между Windows и Unix, не полагается на блокировку файла
   сторонним процессом (что нельзя стабильно сымитировать в тесте). Проверено:
   имя НЕ в `forwarded`, есть в `failed`, и — отдельным ассертом — что источник
   (`prev_exports/summary.md`) остаётся на месте, подтверждая необратимость отсутствует.
3. `forward_exports_to_inbox_name_collision_overwrites_by_design` — фиксирует
   осознанное решение не применять `unique_export_path`: при существующем файле
   с тем же именем во входящих новый файл перезаписывает его (проверено содержимое
   после вызова), а не переименовывается со счётчиком.

## Чего эта правка не закрывает

- Не трогает `persist_step_exports`, `close_session`, `summarize_step_exports` — вне
  границ задачи.
- Не вводит алерт/уведомление пользователю приложения о частичном переносе выгрузок
  между шагами пайплайна — только журнал (`warn!`). Если Антон захочет, чтобы
  неполный перенос контекста между шагами был виден в интерфейсе (не только в логе),
  это отдельная UX-задача поверх `emit_wf_status`/аналогичного канала — здесь она не
  входила в рамки (задача просила «громкую запись в журнал», не UI-сигнал).
- Класс CPD-81 (отброшенный `fs::copy`) мог остаться в других модулях за пределами
  `campaign.rs` — поиском по всему репозиторию на предмет других `let _ = std::fs::copy`
  не занимался, задача ограничивала правку двумя конкретными функциями этого файла.
