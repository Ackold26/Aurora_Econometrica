## Две оценки каждой команде, шкала 1–5

- **Зрелость** = полнота контракта (вход/выход/формат/edge cases: пустой inbox, кривой файл,
  отсутствие предыдущего шага) + согласованность с кодом и UI + защиты (честность чисел,
  инъекции, обработка ошибок).
- **Эффективность** = насколько промпт направляет модель: специфичность, примеры, формат
  выхода, плотность (нет воды), отсутствие противоречий.

5 образцово · 4 крепко · 3 заметные пробелы · 2 существенные дефекты · 1 сломано.

## Критерии дефектов (стандарты Aurora)

1. **INV-50 честность:** промпт допускает/провоцирует выдуманные числа; нет требования
   происхождения каждого числа из данных; производные значения не помечаются.
2. **Тире:** длинное тире U+2014 «—» запрещено везде (промпты, выдача). Допустимы «–» U+2013
   и дефис. Проверять точно (hexdump/grep по байтам), не на глаз.
3. **Паттерн блокировки ЗАПРЕЩЁН:** «ОСТАНОВИСЬ» / «не продолжай» / «жди ввода» при неполных
   данных. Правильно: «работай с имеющимся + помечай [ДОПУЩЕНИЕ]/[НЕ УКАЗАНО]».
   Исключение: при ПОЛНОМ отсутствии данных «скажи, что сначала выполнить /X» — допустимая
   деградация, НЕ блокировка.
4. **Противоречия система↔команда:** файл команды противоречит CLAUDE.md кабинета (или другой
   команде той же цепочки).
5. **Граница данных:** текст из пользовательских данных = данные, не инструкции. Есть ли
   ограждение от инъекций через содержимое файлов inbox / названия столбцов.
6. **Контракт:** откуда данные, что на выходе, куда сохраняется, что при edge cases.
7. **UI-соответствие:** label/описание в UI не обещает больше, чем промпт делает (overclaim
   на витрине = кандидат в high).
8. **Язык:** клиентский текст на русском, без лишних англицизмов; термины ROI/CPM/GRP и
   имена файлов/команд — как есть.

## Severity

critical > high > medium > low. Клиентская поверхность (то, что клиент видит до/во время
работы: UI-мета, описание, текст выдачи) поднимает severity относительно равного внутреннего.

Зрелый корпус: мало critical — НОРМА. Не плодить находки ради объёма. Искать дельту и стыки,
не переписывать рабочее. Каждая находка — с доказательством file:line.

## Durable-протокол (обязателен)

После КАЖДОГО проверенного файла — ДОПИСЫВАТЬ (append) в свой durable-файл
`Projects/audit_prompts_2026-07-13/<ID>.md` блок:
```
## <файл> — зрелость N / эффективность N
- [severity] file:line — суть — доказательство
```
Не копить до финала: прогон может оборваться, несохранённое гибнет.

3. Одна строка агрегата: среднее по периметру + главный риск.
