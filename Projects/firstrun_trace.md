## 2. Чем POST /v1/jobs отличается от GET /v1/meta (построчно)

Обе строятся ОДНОЙ функцией `signed_request` (`client.rs:1545-1595`). Совпадает всё:
адрес-основа, пять заголовков (`x-aurora-ticket`, `-device`, `-timestamp`, `-nonce`, `-signature`),
строка подписи (`build_request_payload`, `protocol.rs:32-50`), ключ подписи, отпечаток из билета.
Отличия ровно три:
1. способ — `POST` против `GET` (входит в подписываемую строку, `protocol.rs:43`);
2. тело — JSON до ~1 МБ; отсюда `content-type` и непустая свёртка тела (`client.rs:1590-1593`);
3. **дополнительный заголовок `Idempotency-Key`** (`client.rs:704`) — единственный заголовок,
   которого у `meta` нет вовсе. Значение собирается в продукте (`gateway_executor.rs:897`),
   это ASCII (`tc-<кабинет>-<hex>-<hex>`).

## 3. Все места мгновенного отказа ДО сети (путь создания задания)

1. `identity_for`: каталог данных недоступен — `gateway_executor.rs:656`.
2. Билет негоден и `refresh_ticket` не дал нового: лицензия не подтверждена — `:725-730`.
3. Билет не собран (`build_cloud_ticket`, в т.ч. отказ WMI-отпечатка) — `:731-732`.
4. `device.key` не читается / повреждён (длина ≠ 32) — `:688-690`, `identity_store.rs:66`.
5. `DeviceIdentity::new`: билет не разбирается или в нём нет `fingerprint_hash` — `client.rs:497-507`.
6. `CloudClient::new`: сетевой клиент не собрался — `client.rs:593-594`.
7. **`refusal_for_skipped`: любое пропущенное вложение прекращает работу** — `gateway_executor.rs:863-865`.
   Поводы: нечитаемое имя (`:569-579`), нет `metadata` (`:591-599`), файл > 24 МБ (`:605-608`),
   сумма > 48 МБ (`:610-613`), ошибка чтения (`:617-625`).
8. `signed_request`: адрес не разбирается — `client.rs:2059-2061` (`CloudError::Local`).
9. `create_job_full`: тело не сериализуется — `client.rs:701-702`.
10. `request_once`: неизвестный способ обращения — `client.rs:1604-1605`.
11. Отмена пользователем до постановки — `:809-811`, `:881-883`.

🔴 Все они — ОДИН отказ, мгновенно, БЕЗ пауз: повторяется только `CloudError::Connection`
(`client.rs:1526-1529`). Ни один из них не даёт шести попыток и не даёт минуты ожидания.

## 4. Арифметика шести попыток — что она доказывает

`attempts = RETRY_BACKOFF.len() + 1 = 6` (`client.rs:599`), паузы `[2,5,10,20,30]` = 67 с
(`client.rs:64-70`, `:1531-1535`). Повтор — ТОЛЬКО при `CloudError::Connection` (`:1526`).
Значит наблюдаемое «шесть падений и примерно минута» возможно ровно при двух условиях:
(а) транспортный отказ до сервера (`describe_transport`, `client.rs:2017-2025`) — запрос не уехал;
(б) ответ со статусом 408/425/429/500/502/503/504 (`protocol.rs:705-710`) — такой ответ
превращается в `Connection("сервис ответил {status}")` (`client.rs:1634`).
Отказ по существу (`Refused`) исключён: он возвращается с ПЕРВОЙ попытки, мгновенно, без минуты.

## 5. Что происходит иначе при ПЕРВОМ обращении с машины

По коду первого раза ровно два действия, и оба — работа с диском, без сети:
- **создаётся `device.key`** (`identity_store.rs:62-72`: `path.exists()` ложно → `random_key()` →
  `write_private` через промежуточный `.part` и переименование; на Windows права не сужаются,
  `identity_store.rs:126-131`);
- **собирается и сохраняется билет**: `decide_ticket(None, …) → Refresh` (`protocol.rs:260-261`),
  `refresh_ticket` (`gateway_executor.rs:720-738`) читает кеш лицензии и зовёт
  `build_cloud_ticket`, где берётся WMI-отпечаток машины (`online_auth.rs:461-471`).

🔴 **Оба шага стоят ДО первого сетевого круга** (`gateway_executor.rs:782` против `:802`). Значит
успешный `GET /meta` в 19:06:25 сам по себе доказывает, что оба прошли: без билета и без ключа
подписанного обращения не построить (`client.rs:1577-1586`).

🔴 **Совпадение 19:06:25 объясняется без «лишнего шага».** `CloudClient` строится ровно в двух
местах продукта (`gateway_executor.rs:198` — отмена, `:784` — исполнение), и первым подписанным
обращением с машины всегда оказывается `GET /v1/meta` из `warn_on_cabinets_mismatch`
(`:802` → `:1200`). Отдельного обращения «зарегистрируй устройство» в клиенте НЕТ: закрепление
происходит на сервере при первом же подписанном запросе, то есть при самом `meta`. Поэтому
«устройство закрепилось в 19:06:25» и «первый `GET /meta` в 19:06:25» — одно событие, а не два.

## 6. Вердикты по кандидатам

| Кандидат | Вердикт | Опровержение / основание |
|---|---|---|
| Создание `device.key` на первом запуске рушит отправку | **опровергнут** | стоит до `meta` (`:782` < `:802`); при отказе `bail` до сети (`:688-690`) |
| Свежий билет негоден для `jobs`, но годен для `meta` | **опровергнут** | билет и подпись одинаковы у обоих (`client.rs:1545-1586`); отличить `POST` от `GET` билет не может |
| Отдельный шаг «регистрация устройства» на первом запуске | **опровергнут** | таких вызовов в клиенте нет: `CloudClient::new` только в двух местах, оба ведут к `meta`/`jobs` |
| Мгновенный отказ на вложениях (`[TC-GW-INPUT]`) | **не подтверждён** | даёт ОДИН отказ без пауз и другой текст, а человек ждал минуту и увидел текст про связь |
| Отказ сервера по существу (`Refused`) | **опровергнут** | не повторяется (`client.rs:1526-1529`) → нет ни шести попыток, ни минуты; и был бы в журнале |
| `Connection`-отказ при создании задания | **установлено как единственно совместимое** | 6 попыток × 67 с (`:599`, `:64-70`) повторяются только для `Connection` (`:1526`) |
| Запрос умер на посреднике (антивирус со вскрытием TLS / корпоративный посредник / фронт-сервер) с кодом 408/425/429/5xx | **не установлено, но совместимо со всеми тремя фактами** | `decide_by_status` (`protocol.rs:705-710`) → `Connection("сервис ответил …")` (`client.rs:1634`); в журнал ПРИЛОЖЕНИЯ такой ответ не попадёт |
| Запрос не уехал вовсе (ошибка сборки запроса у `reqwest`) | **не установлено** | `describe_transport` (`client.rs:2017-2025`) уводит любую не-таймаут, не-connect ошибку в `Connection`; чем именно она была — по коду не видно |

## 7. Чего не установлено и что закрыло бы вопрос
1. **Журнал ФРОНТА (посредник перед шлюзом), а не приложения**, за 12:52:44 / 19:06:25 / 22:25:19

# Раздел 8. Смена направления: работа с файлами пользователя (11.09)

Гипотеза «первого входа» снята фактами сервера (закрепление одно, третий случай — та же
машина, «последний раз видно» обновилось в 22:25:19). Разбор ведётся заново от точки
«ответ `meta` получен».

## 8.1. Чтение входных файлов: каждый исход и текст для человека

Потолки клиента — `gateway_executor.rs:47-48`:
`INPUT_FILE_LIMIT = 24 * 1024 * 1024` (24 МБ на файл), `INPUTS_TOTAL_LIMIT = 48 * 1024 * 1024`.

| Исход | Адрес | Что видит человек |
|---|---|---|
| папки `inbox` нет / `read_dir` отказал | `:557-561` | 🔴 **ничего**: молча возвращается пустой набор, работа идёт без файлов |
| имя файла не переводится в UTF-8 | `:569-579` | «имя файла «X» записано в неизвестной кодировке» · «Переименуйте файл во «Входящих» и добавьте его заново.» |
| `metadata` недоступна | `:591-599` | «файл «X» не удалось прочитать» · «Проверьте файл во «Входящих» и добавьте его заново.» |
| размер > 24 МБ | `:605-608` → `:347-353` | «файл «X» слишком велик» · «Уберите его из «Входящих» или замените файлом поменьше.» |
| сумма > 48 МБ | `:610-613` → `:538-546` | «файл «X» не уместился: вложения во «Входящих» в сумме слишком велики» · «Уберите из «Входящих» лишние файлы – всего за раз уезжает до 48 МБ.» |
| `fs::read` отказал | `:617-625` | то же, что у `metadata`: «файл «X» не удалось прочитать» |
| файл вырос между сверкой и чтением | `:628-637` | тексты потолков, те же два |
| набор пуст (и `keep` ложно) | — | отказа нет; `defer_start` ложно (`client.rs:1186`), пуск не откладывается, файлы не шлются |

Итоговая склейка отказа — `refusal_for_skipped` (`:334-344`):
`"Работа не начата: {причина первого}.{ Не уехало файлов: N.}\n\nЧто делать: {действие первого}"`,
и дальше `anyhow::bail!("[TC-GW-INPUT] {text}")` (`:863-865`).

🔴 Важно для разбора: это **один** отказ, **мгновенный**, **без повторов** и с кодом
`[TC-GW-INPUT]`, а не `[TC-GW-NET]`. Ни шести попыток, ни минуты, ни слова «связь» в тексте.

## 8.2. Ключевой вопрос: превращается ли отказ файлов в сетевой вид?

**Не нашла, и искала специально.** Где искала: весь путь создания задания в продукте
(`gateway_executor.rs:552-643`, `:845-962`) и все места, где строится `CloudError`, в
`client.rs`. Чем искала: чтение обеих функций целиком плюс обход конструкторов `CloudError::`.
Результат: ошибки чтения файлов **вообще не становятся `CloudError`** — они собираются в
`SkippedInput` и выходят из продукта как `anyhow::Error` с кодом `[TC-GW-INPUT]`.

Обратное направление существует и работает как раз наоборот: на ЗАГРУЗКЕ файла сетевой отказ
одевается в текст про файлы — `client.rs:1279` → `:1317-1335` (`NotSent{phase: Uploading}`) →
`:223-227`: «Файлы для работы отправлены не полностью – связь прервалась». Это и есть картина
соседнего продукта (задание создано `202`, оборвалась загрузка).

## 8.3. 🔴 Превращение, которое действительно есть

`describe_transport` (`client.rs:2017-2025`):
```rust
if err.is_timeout() { "сервис не ответил вовремя" }
else if err.is_connect() { "не удалось установить соединение" }
else { format!("обрыв связи: {err}") }
```
Вызывается на `.send()` (`:1606-1610`) и на `.bytes()` (`:1619-1623`), и результат заворачивается
в `CloudError::Connection` — **единственный повторяемый вид** (`:1526-1529`).

В reqwest ошибка ПОСТРОЕНИЯ запроса (негодное значение заголовка, негодный адрес) не возникает
в момент `.header(...)`: она хранится в построителе и возвращается из `.send()`. Она не
`is_timeout()` и не `is_connect()` → попадает в третью ветку → `Connection` → повтор.

## 8.4. Тело собирается один раз, запрос — шесть раз

- тело JSON строится ОДИН раз, до цикла: `client.rs:701-702` (`serde_json::to_vec`), дальше едет
  ссылкой `Option<&[u8]>` через `request` → `request_full`;
- цикл попыток: `client.rs:1522-1538`, `attempts = 6` (`:599`), паузы `[2,5,10,20,30]` (`:64-70`);
- на КАЖДОЙ попытке заново строится сам запрос: `:1523` → `request_once` `:1607` →
  `signed_request` `:1579-1593` (новые метка времени, одноразовое число, подпись, копия тела).

🔴 Следствие: **отказ сборки запроса повторяется ровно шесть раз, мгновенно, и на сервер не
уходит ничего** — при этом человек читает «Связь с сервером потеряна» (`client.rs:336-340`).
Это ровно наблюдаемая картина.

## 8.5. Разница подготовки `GET /meta` и `POST /jobs` — ещё раз, прицельно

Одна функция на оба (`signed_request`, `client.rs:1545-1595`). Пять общих заголовков
(`:1582-1586`) одинаковы — потому `meta` и уходит. Отличий три: способ, тело с `content-type`
(`:1590-1593`) и **`Idempotency-Key`** (`:704`) — единственный заголовок, которого у `meta` нет.
Его значение собирает продукт: `format!("{label}-{}", short_stamp())` (`gateway_executor.rs:897`).

Проверка «может ли это значение быть негодным для заголовка»: **не нашла такого пути.**
Искала двумя способами: (1) генератор метки `:217-232` — `format!("tc-{cabinet_id}-{:08x}")`,
чистый ASCII; (2) обход всех мест, где метка приходит извне (`resume_session_id`):
`lib.rs:502` передаёт `None`, `lib.rs:1374-1386` — то, что вернул прошлый прогон,
`lib.rs:3407` — из `session_manager`; тонкая поставка возвращает свою же метку
(`gateway_executor.rs:1127`). Кандидат структурно живой, но не доказанный.

## 8.6. Побочная находка о чтении жалоб

`[TC-GW-NET]` навешивается на ЛЮБОЙ `CloudError` (`gateway_executor.rs:1008`), включая отказ
сервера по существу. Код в начале строки сетевую причину не доказывает — различает только
текст из `user_text()` (`client.rs:327-407`). Тексты-ориентиры:
- `Connection` → «Связь с сервером потеряна… загляните позже» (`:336-340`);
- `NotSent/Uploading` → «Файлы для работы отправлены не полностью – связь прервалась» (`:223-227`);
- `NotSent/Starting` → «Связь прервалась в тот миг, когда работа отправлялась в исполнение» (`:233-238`);
- `Disconnected` → «Связь с сервером прервалась во время работы» (`:397-400`);
- `Local` → «Программа не смогла обратиться к серверу» (`:341-344`).
Только первый даёт шесть попыток и минуту.
