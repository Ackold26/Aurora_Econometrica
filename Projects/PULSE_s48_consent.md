# Пульс s48 — экран согласия (ознакомительное использование)

## Задача (пересказ)
Правовой блок вывел пробный период из лицензионного договора в отдельный документ «Условия ознакомительного использования» (единый для линейки, п.5 ст.1286 ГК РФ). Экран первого запуска меняет роль: больше не показывает полный текст, а даёт краткую суть + кнопку открытия локального PDF + чекбокс согласия с редакцией документа. Нужно: разведка текущего механизма → точный текст окна → открытие локального PDF (тем же механизмом, что и справка) → хранение согласия с редакцией (константа фронт+Rust + сторож рассинхрона) → сторож поставки (падает, если PDF физически отсутствует в ресурсах — файла пока НЕТ, это ожидаемо красный) → тесты поведения.

## План
1. Разведка: найти компонент экрана согласия, хранение факта согласия, механизм открытия справки (PDF/файл) — записать сюда факты, ничего не трогать.
2. Переписать текст и поведение окна согласия (дословный текст).
3. Кнопка «Открыть условия» → открыть локальный PDF тем же механизмом, что справка; обработка отсутствия файла — понятное сообщение.
4. Хранение согласия: редакция+признак+время; константа фронт/Rust синхронизирована со сторожем; повторный показ при устаревшей редакции.
5. Сторож поставки: падает если PDF физически отсутствует в ресурсах сборки (пока КРАСНЫЙ — файла ещё нет от юристов, это ожидаемо).
6. Тесты поведения (не текстовые сторожа).

### Разведка механизма согласия (online_auth.rs)
Подтвердила код: `AuthRequest.consent_terms_version`/`consent_accepted_at` (online_auth.rs:86-88) заполняются ИСКЛЮЧИТЕЛЬНО из `user_config::load(...).cloud_consent` (online_auth.rs:499-503) — то есть это ТОТ ЖЕ `CloudConsent{terms_version,accepted_at}` из user_config.rs, который я уже разобрала в первой волне (согласие на облачную обработку/трансграничную передачу для кабинетов-советников). Комментарий в коде прямо называет это «Аудит-след согласия на облачную обработку (облачная редакция)». Это НЕ отдельный, отдельно от CloudConsent, механизм — это ОН И ЕСТЬ.

**Проблема с буквальным поручением «встроить в этот механизм»:** `cloud_consent_required()` (user_config.rs) начинается с `if !CLOUD_ADVISORS_ENABLED { return false; }` — т.е. в локальной редакции (`--no-default-features`, 152-ФЗ) эта проверка ВСЕГДА возвращает false и согласие никогда не запрашивается. Если посадить окно условий ознакомительного использования на этот же флаг — оно НЕ покажется в локальной редакции, что прямо противоречит пункту 4 самого поручения («окно должно показываться в обеих [редакциях]»). Плюс: сервер лицензирования получит `consent_terms_version` с семантикой «согласие на трансграничную обработку», а не «принятие пробного периода» — смешение двух разных юридических фактов в одном поле исказит аудит-след на сервере.

Второй факт: CLAUDE.md проекта (правило №8) прямо документирует, что в продукте уже НАМЕРЕННО сосуществуют две параллельные системы лицензирования (online_auth.rs приоритетная + license.rs fallback) — то есть «несколько систем на одну тему» само по себе не аномалия для этого кодовой базы, когда темы разные.

**Проверила фактически, а не предположила:** прогнала `cargo test --no-default-features trial` (локальная редакция) — все 9 значимых тестов (кроме ожидаемо красного сторожа PDF) зелёные, идентично облачной редакции. Моя реализация `trial_consent_required()` вообще не ссылается на `CLOUD_ADVISORS_ENABLED` — окно условий уже показывается в обеих редакциях корректно, это НЕ нужно чинить дополнительно.

**Решение (сообщила team-lead, жду подтверждения/возражения, работу продолжаю):** оставляю `TrialConsent` ОТДЕЛЬНЫМ полем в ТОМ ЖЕ файле `user_config.rs`, в ТОМ ЖЕ `UserConfig`, через ТЕ ЖЕ `load`/`save` (никакой второй файловой машинерии хранения нет — используется буквально тот же durable JSON и та же атомарная запись). Это не «вторая параллельная система согласия» в смысле дублирования инфраструктуры — это тот же один механизм (UserConfig + load/save), расширенный на вторую, юридически отдельную тему, ровно как в этом же файле уже разведены две другие оси (`local_only`/`execution_mode`, с явным комментарием «две оси, не путать»). AuthRequest/online_auth.rs НЕ трогаю — его семантика («аудит облачного согласия») остаётся точной.
