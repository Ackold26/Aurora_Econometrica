Medium | gateway_executor.rs:283-292 (generate_session_label) | Монотонный счётчик COUNTER полностью обрезается маской и НЕ влияет на метку. `(counter as u64) << 32` кладёт counter в биты [32,63], а `mixed & 0xFFFF_FFFF` берёт только биты [0,31] → counter вклад = 0. Уникальность метки держится ИСКЛЮЧИТЕЛЬНО на изменении младших 32 бит наносекунд (pid константа в процессе). Заявленный инвариант «наносекунды + монотонный счётчик + PID» не выполняется — счётчик мёртв. | Сценарий A (флаки-тест): `session_label_is_unique_across_calls` — два вызова подряд; если системный таймер не тикнул между ними (совпали младшие 32 бита nanos), метки идентичны → assert_ne падает в CI. Сценарий B (коллизия сессий): два «новых диалога» одного кабинета за интервал < разрешения таймера → одинаковая метка → сервер по sticky-маршрутизации продолжит СТАРУЮ серверную сессию вместо новой (переиспользование контекста). Фикс: включить counter в младшие биты, напр. `mixed ^= counter as u64` до маски, или брать hex от полного u64.

Medium | gateway_executor.rs:336-373 (execute) + claude.rs:466-467 (CLI-эталон) | Нет клиентского таймаута на `spawn_blocking(send_to_gateway)`. CLI-путь оборачивает стрим в `tokio::time::timeout(30 мин)` + taskkill; gateway полагается ТОЛЬКО на SSH ConnectTimeout=10 / ServerAlive 15×4=60с. SSH keepalive держит канал, пока жив ssh-демон сервера, НЕ forced-command. При этом init эмитится безусловно ДО вызова и снимает safety-таймер ChatPanel (465). | Сервер жив (ssh-демон отвечает на keepalive), но forced-command/движок завис в poll не отдавая stdout → ServerAlive не рвёт соединение, send_to_gateway висит без верхней границы, а safety-таймер уже снят init'ом → вечный spinner (isLoading=true), UI восстанавливается только перезапуском. CLI-путь от этого защищён 30-мин потолком. Фикс: обернуть spawn_blocking в tokio::time::timeout с потолком (≈ серверный poll-лимит), при истечении — [TC-GW-TIMEOUT].

Medium | lib.rs:1166-1184 (send_message retry-loop, ветка resume-fallback) | Ветка `Err(e) if use_resume.is_some() && attempt == 0` безусловна по типу ошибки (не проверяет класс). Унаследована от CLI, где означала «--resume отклонён». Для gateway ЛЮБАЯ ошибка при продолжении диалога (TIMEOUT/SRV/SSH) на первой попытке трактуется как resume-failure. | Пользователь ведёт диалог (session label в session_manager), сервер временно недоступен → (1) ложное системное сообщение «Контекст диалога сброшен. Начинаю новую сессию.» (ничего не сбрасывалось); (2) вторая попытка с resume=None → generate НОВЫЙ label → при транзиентном сбое (сервер ожил на 2-й попытке) стартует НОВАЯ серверная сессия, старый контекст осиротает, хотя он был жив; (3) лишний повторный вызов сервера. Фикс: в thin-ветке не заворачивать gateway-ошибки в resume-fallback (проверять, что ошибка — именно отказ resume, а не транспорт/таймаут).

Medium (латентный) | online_auth.rs:308-310 (R-04) ↔ local_mode.rs:84-113 (decide_from_online) | R-04 возвращает Err(HttpStatus) на ЛЮБОЙ не-2xx ДО чтения тела. authorize() маппит Err→"cached"(при свежем кэше)/"offline". decide_from_online: "cached"→allowed=true, "offline"→None→Ed25519-fallback. Значит серверный «blocked» доходит как Denied ТОЛЬКО если сервер отдаёт его с HTTP 2xx+телом. Если blocked приходит с 4xx/5xx — R-04 превращает его в cached/offline → блокировка обходится. До R-04 (4xx+{status:blocked}) давало Denied — это регресс для blocked-через-не-2xx. | Сервер отзывает лицензию клиента, отвечает HTTP 403+{"status":"blocked"} → local_mode: свежий кэш (<24ч) → allowed, ИЛИ нет кэша → Ed25519 с валидной подписанной лицензией → allowed. Обход отзыва. СМЯГЧЕНИЕ: (а) verify_local_mode НИГДЕ не вызывается (grep по обоим worktree) — код не на пути исполнения, латентно до подключения локального режима; (б) безопасно, если серверный контракт /auth ВСЕГДА отдаёт вердикт через HTTP 200 (blocked в теле). Проверить серверный контракт до подключения local mode; если 200 — не проблема, если 4xx — дыра. Эскалация до High при выполнении обоих условий (local mode подключён И blocked через не-2xx).

— Проверено и НЕ находка: default-сборка (весь thin за cfg, рефакторинг auto_save_response эквивалентен старому inline по всем 4 веткам suppress/empty); UI-зависание при терминальной gateway-ошибке (основной invoke('send_message') обёрнут в try/catch, ChatPanel.svelte:778-785 → снимает safety-таймер + сообщение + isLoading=false); инвариант недостижимости CLI при thin (run_claude_inner/find_claude_binary/isolated_claude_config_dir приватны, вызовы только за cfg(not thin)); безопасность транспорта (промпт через stdin не argv; node с префиксом user@ гасит option-injection; StrictHostKeyChecking=yes+CA; stderr дренаж в потоке против deadlock; MAX_RESPONSE_BYTES против OOM); invoke импортирован в settings.svelte:2 (не missing).

## ТРИАЖ (рабочая сессия, 2026-07-20)
- #1 counter мёртв — ПОДТВЕРЖДЕНО (XOR со сдвигом <<32 не задевает биты [0,31] под маской) → ИСПРАВЛЕНО: counter замешан и в младшие биты (gateway_executor.rs::generate_session_label).
- #2 нет клиентского таймаута — ПОДТВЕРЖДЕНО (ServerAlive держит канал при живом sshd независимо от forced-command; init уже снял safety-таймер UI) → ИСПРАВЛЕНО: tokio::time::timeout 1830с вокруг spawn_blocking → [TC-GW-TIMEOUT]; жёсткий kill осиротевшего потока — фаза 2.
- #3 ложный resume-fallback — ПОДТВЕРЖДЕНО (guard lib.rs:1166 безусловен по типу ошибки) → ИСПРАВЛЕНО: guard исключает префикс "[TC-GW-" (gateway-ошибки падают в честную ошибку, label/контекст сохраняются; CLI-путь не задет — его ошибки без такого префикса).
- #4 R-04↔local_mode обход blocked через не-2xx — ПОДТВЕРЖДЕНО КАК ЛАТЕНТНЫЙ (verify_local_mode не вызывается ни в одном продукте прода; пилот Econometrica local mode не использует). НЕ исправлено в блоке: правка семантики общего крейта aurora_fleet шире блока + требует факта серверного контракта /auth. → БЭКЛОГ с жёстким триггером «ДО подключения local mode»: (а) проверить, отдаёт ли auth Edge Function blocked всегда с HTTP 2xx; (б) если нет — научить R-04 читать тело при не-2xx и различать вердикт-в-теле от транспортного сбоя.
