## Вопрос 2. Один блок `<style>` без хеша в CSP style-src (4/5)

### Что делал
Добавила временную печать: для каждого найденного `<style>...</style>` блока — индекс, длину, совпал ли хеш, первые 200 символов содержимого и его вычисленный SHA-256; отдельно распечатала офсеты всех `<style>`-тегов в HTML. Затем нашла в исходниках, откуда берётся непокрытый блок, и как строится список хешируемых блоков в `builder.py`. Независимо (вторым прогоном, без изменения сторожа — прямой вызов `engines.html_export.build_html` и ручной пересчёт SHA-256) перепроверила отсутствие хеша.

### Факт (дословный вывод)
```
[block 3] len=43 matched=False hash=embtYa8eUf1YQ4PWaZ7cY4CQVH1uNYRINs7iTKAILbg=
  head: '\n\t.st0{fill:#0A1628;}\n\t.st1{fill:#C5A46D;}\n'
```
Независимая проверка (прямой вызов `build_html`, ручной пересчёт хеша):
```
inner repr: '\n\t.st0{fill:#0A1628;}\n\t.st1{fill:#C5A46D;}\n'
computed hash: embtYa8eUf1YQ4PWaZ7cY4CQVH1uNYRINs7iTKAILbg=
hash present in CSP text: False
CSP style-src: 'sha256-9p8N...' 'sha256-QB0h...' 'sha256-EiQ0...' 'sha256-B/U6...'   (4 хеша, ровно совпадают с блоками 0,1,2,4)
```

**Откуда берётся:** блок — собственный `<style type="text/css">` внутри `aurora_html/templates/brand_mark.svg` (фирменный SVG-значок, вставляется в шапку отчёта). Путь: `builder.py:_brand_mark_svg()` (строка 201) читает файл целиком как строку → `builder.py:578` кладёт в `ctx["brand_mark_svg"]` → `sections.py:532-537` вставляет сырую разметку SVG (вместе с её собственным `<style>`) в `<div class="cover-brand-mark">`.

**Почему не хеширован:** в `builder.py:606-611` список блоков для хеширования style-src собран явным перечислением четырёх источников:
```python
style_blocks_as_emitted = (
    f"\n{fonts_css}\n",
    f"\n{tokens_css}\n",
    f"\n{layout_css}\n",
    noscript_css,
)
```
SVG вставляется отдельным путём (как «разметка», не как «стиль») и в этот список не попадает — структурный пропуск на этапе сборки CSP, а не единичная опечатка.

### Главный вопрос: применяется ли блок у пользователя, открывшего отчёт

**Нет, не применяется — браузер обязан заблокировать этот `<style>` целиком.**

Обоснование из кода, не предположение:
1. CSP задана через `<meta http-equiv="Content-Security-Policy" content="...">` (проверка «Content-Security-Policy meta present» — OK). Директивы `style-src`/`script-src` **поддерживаются** через meta-тег (в отличие от `frame-ancestors`/`sandbox`/`report-uri`, которые в meta игнорируются, но это не наш случай).
2. `style-src` состоит **только** из 4 хешей, `'unsafe-inline'` отсутствует — это отдельно проверяется и проходит («style-src uses hashes (no 'unsafe-inline')» — OK). Есть отдельная разрешённая директива `style-src-attr 'unsafe-inline'`, но она покрывает только атрибуты `style=""`, а не элементы `<style>` — на блоки это не распространяется.
3. По спецификации CSP3 при hash-based `style-src` без `'unsafe-inline'` браузер выполняет/применяет только те `<style>`-блоки, чей SHA-256 совпадает с одним из перечисленных хешей. Хеш SVG-блока — `embtYa8eUf1YQ4PWaZ7cY4CQVH1uNYRINs7iTKAILbg=` — в списке отсутствует (факт выше, дважды подтверждён). Значит браузер обязан отклонить применение этого блока (и обычно пишет CSP-violation в консоль).

**Что это значит для внешнего вида отчёта — не косметика.** Сам код содержит явное признание последствий: в `layout.css:345-355` комментарий прямо говорит, что цвета `.st0`/`.st1` («навy» и «золото» логотипа) заданы ИСКЛЮЧИТЕЛЬНО через этот самый inline-`<style>` SVG, и что «Light + Fun themes: navy main + gold accent — design intent» — для светлой/«fun» темы (это `initial_theme` по умолчанию в проде и в тестовой выборке) **никакого внешнего переопределения `.st0`/`.st1` нет вообще** (проверено grep по `layout.css` — единственное правило `[data-theme="dark"] .cover-brand-mark svg .st0 {...}` относится только к тёмной теме и только к `.st0`; `.st1` — золотой акцент — не переопределён нигде ни для одной темы). Пути `<path class="st0"...>`/`<path class="st1"...>` в SVG не имеют собственного атрибута `fill=`, только `class=`.

Следствие: если браузер блокирует нехешированный `<style>` (а по спецификации обязан), фирменный значок Aurora AI в шапке отчёта на светлой/«fun» теме отрисуется без заданного цвета (SVG-дефолт для `<path>` без fill — чёрный), а не навy+золото как задумано; на тёмной теме золотой акцент (`.st1`) тоже останется без цвета, навy (`.st0`) — вернётся благодаря отдельному внешнему `!important`-правилу для тёмной темы.

Я не открывала это в живом браузере (нет доступа к нему в этой сессии) — вывод построен на прямом чтении кода CSP-политики и на общеизвестном, документированном поведении CSP3 hash-based style-src, а не на предположении о «вероятно сработает». Если нужна визуальная фотопроверка — это отдельный шаг (открыть файл в Chrome/Firefox и посмотреть DevTools → Console на CSP-violation + сравнить цвет значка).

### Положительный контроль
1. В том же прогоне метод дал 4 `matched=True` и 1 `matched=False` — то есть корректно различает совпадающие и несовпадающие хеши на одном и том же наборе данных, не «залипает» на одном ответе.
2. Независимый пересчёт (второй, отдельный вызов `build_html` + ручной SHA-256 через `hashlib`/`base64`, без переиспользования кода сторожа) дал идентичный хеш `embtYa8eUf1YQ4PWaZ7cY4CQVH1uNYRINs7iTKAILbg=`, отсутствующий в тексте CSP — то же самое отрицательный результат, полученный независимым путём.
3. Явный список `style_blocks_as_emitted` в `builder.py:606-611` — исходник, а не косвенная улика; он прямым текстом перечисляет 4 источника и не содержит SVG.

### Вывод
Нехешированный блок — собственный `<style>` внутри `aurora_html/templates/brand_mark.svg`, встраиваемый в шапку отчёта через `_brand_mark_svg()`/`sections.py`. CSP-политика документа не даёт ему шанса примениться: hash-based `style-src` без `'unsafe-inline'` — браузер обязан заблокировать этот конкретный `<style>`. Это НЕ косметический недочёт самой проверки — это реальный визуальный дефект: фирменный значок Aurora AI в отчёте, скорее всего, теряет заданные navy/gold-цвета (падает к чёрному дефолту SVG) у любого пользователя, открывающего файл в спецификации-соответствующем браузере.

### Предлагаемое исправление (словами, НЕ внесено)
В `builder.py` добавить содержимое `<style>`-блока `brand_mark.svg` в список `style_blocks_as_emitted` (пятым элементом) — тогда его хеш попадёт в `style-src` наравне с остальными четырьмя. Технически можно либо распарсить SVG и вытащить `<style>...</style>` регуляркой (как это делает сам сторож), либо (чище) заранее «зашить» цвета в SVG через `fill=` атрибуты на `<path>` и убрать внутренний `<style>` вовсе — тогда блока для хеширования не будет вообще, а тема-зависимая перекраска останется на внешних CSS-правилах (`layout.css`), как уже сделано для `.st0` в тёмной теме. Второй вариант выглядит надёжнее (меньше типов CSP-блоков для сопровождения), но требует правки самого SVG-файла — решение по объёму правки не мне.
