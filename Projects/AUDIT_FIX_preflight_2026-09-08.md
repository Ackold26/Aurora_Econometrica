## Доработка по приёмке: дыра в разборе запроса (молчаливая потеря ключа)

Приёмка правки прогнала флаги не объектом `PreflightRequest`, а по **реальному пути** – через
`TestClient` и POST `/compute/preflight` тем телом, которое собирает команда Tauri, и нашла дыру
рядом с моим сторожем:

```
HTTP seas=True  hol=True  -> код 200 уровень=reliable
HTTP seas=False hol=False -> код 200 уровень=insufficient
МУТАЦИЯ ИМЁН (camelCase useSeasonality/useHolidays) -> код 200 уровень=reliable
```

Первые две строки подтверждали мою правку сквозь HTTP. Третья – дыра: ключ в другом написании
(рассинхрон слоёв, опечатка в будущей правке команды Tauri) pydantic **выбрасывает молча**, ответ
остаётся 200, продукт возвращается ровно к аудированному дефекту, и **ни одна проверка не краснеет**.
Класс тот же, что чинил внешний аудит: молчаливая потеря флага между слоями. Мой сторож её не ловил,
потому что стоял **рядом** со слоем риска, а не **на** нём – проверки строили объект запроса
напрямую, минуя разбор.

**Закрыто.** `PreflightRequest` принимает оба написания через `AliasChoices` + `populate_by_name`
(`sidecar/econometrica/server.py:969-976`; импорт – `server.py:47`). Узко: только два мастер-флага,
`extra='forbid'` не вводился, прочие поля запроса не тронуты – посторонние ключи по-прежнему
принимаются, и на это есть отдельная проверка.

**Новый класс сторожа** `TestFlagsSurviveTheHttpLayer` (7 проверок) стоит на слое риска:
тело списано дословно с `econometrica.rs:702-715`, запрос идёт через `TestClient`.
- snake_case-тело: флаги включены → `reliable`, выключены → `insufficient` (код 200 в обоих);
- camelCase-тело на четырёх сочетаниях флагов: тот же вердикт, то же покрытие, тот же набор
  контролей, что у snake_case;
- посторонние поля запроса по-прежнему принимаются (границы доработки соблюдены).

**«Внести-поймать-откатить»:** снятие camelCase-алиасов роняет **3 проверки из 22**
(`[False-False]`, `[False-True]`, `[True-False]`), после возврата – 22 зелёных. Случай
`[True-True]` не краснеет, и правильно: при обоих включённых флагах потерянный ключ совпадает
с умолчанием, поэтому дефект в этой точке ненаблюдаем.

**Замер по ходу доработки, стоит знать:** набор проверки пришлось усилить. При прежней амплитуде
сезонной волны (300) покрытие без контролей выходило **ровно 0,500** – впритык к порогу отказа,
и вердикт `warn` против `fail` решался бы третьим знаком. Амплитуда поднята до 900 (выбрана
замером, не на глаз): включено – 0,896 `pass` → `reliable`, выключено – 0,458 `fail` →
`insufficient`. Пороги продукта при этом не трогались, менялся только набор данных проверки.
