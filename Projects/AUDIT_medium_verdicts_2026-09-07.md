## Находка 2 — `src-tauri/src/commands/claude.rs:960-964`

### ВЕРДИКТ: ПОДТВЕРЖДЕНА полностью

### ДОКАЗАТЕЛЬСТВО

Цепочка причин доказана до конца, включая тот узел, который аудитор назвать не мог, — почему
собственная защита библиотеки не срабатывает.

1. Rust разбирает нечисловые литералы как `f64` (прогон):
   `parse::<f64>("NaN") = Ok(NaN)`, `"nan" = Ok(NaN)`, `"inf" = Ok(inf)`, `"Infinity" = Ok(inf)`.
2. `claude.rs:918-922`: ячейка «NaN» проходит `parse::<f64>()`, столбец помечается числовым
   (`numeric_cols[col_idx] = true`), поэтому под ним строится формула суммы.
3. `claude.rs:958-964`: `col_sum` складывается тем же `parse().ok()`, получает `NaN`,
   и `col_sum.to_string()` даёт строку `"NaN"`, которая уходит в `set_result`.
4. **Ключевой узел.** `rust_xlsxwriter-0.79.4/src/worksheet.rs:16986` решает, помечать ли ячейку
   строковой, так: `let result_type = if result.parse::<f64>().is_err() { r#" t="str""# } else { "" };`
   — то есть проверяет ровно тем же разбором, который «NaN» проходит. Признак `t="str"`
   не ставится, и нечисловой литерал попадает в **числовую** ячейку.

Собран настоящий файл тем же кодом (копия пути `convert_to_xlsx`, `scratchpad/xlsxprobe`),
таблица «заголовок + 4 строки, в одной NaN»:

```xml
<c r="B6" s="2"><f>SUM(B2:B5)</f><v>NaN</v></c>
```

Контроль «как было до правки блока» (тот же код без `set_result`):

```xml
<c r="B6" s="2"><f>SUM(B2:B5)</f><v>0</v></c>
```

Чтение файла:

| читатель | до правки (`<v>0</v>`) | после правки (`<v>NaN</v>`) |
|---|---|---|
| openpyxl, режим кэша (`data_only=True`) | открывается, «Итого» = 0 | **весь файл не читается**: `ValueError: invalid literal for int() with base 10: 'NaN'` → `Unable to read workbook … invalid XML` |
| openpyxl, режим формул (`data_only=False`) | открывается | открывается (кэш не трогается) |
| excelize (Go, через excel MCP) | открывается | открывается, «Итого» показан как `NaN` |

Отдельная деталь: сама ячейка данных «NaN» получилась безвредной — `worksheet.rs:13360`
подменяет нечисловое значение строкой `#NUM!`. Библиотека прикрывает `write_number` и не
прикрывает `set_result`.

**Чего доказать не удалось:** поведение настоящего Microsoft Excel — его на машине нет
(excel MCP работает через excelize, не через Excel). Формулировку аудитора «Excel предлагает
восстановить файл» я не подтверждаю и не опровергаю. Доказано другое, и этого достаточно:
числовая ячейка с нечисловым значением нарушает контракт формата, и один из двух проверенных
сторонних читателей роняет **весь документ**, а не одну ячейку.

### ПОСЛЕДСТВИЕ ДЛЯ КЛИЕНТА

`convert_to_xlsx` вызывается на автосохранении ответа кабинета (`claude.rs:692`). Достаточно, чтобы

### ПРЕДЛАГАЕМОЕ ЛЕЧЕНИЕ (не применяла)

Словами дифа, в `claude.rs`:
1. При разборе ячейки принимать только конечные числа: `if let Ok(num) = cleaned.parse::<f64>() { if num.is_finite() { … } else { пишем строкой } }`. Тогда «NaN» ляжет текстом, а столбец не будет помечен числовым по нечисловой ячейке.
2. В сумме подстраховаться повторно: `set_result` вызывать только при `col_sum.is_finite()`, иначе оставить формулу без сохранённого результата (библиотека подставит свой умолчательный «0», и файл останется читаемым).
3. Сторож: таблица со строкой `NaN` → в XML не должно быть `<v>NaN</v>`, файл должен читаться в режиме кэша.

Пункт 2 применить и в `report.rs` — там `pct_result`/`total_value` тоже уходят через
`to_string()`, и хотя `serde_json` нечисловое значение не пронесёт, деление на денормальное
число теоретически даёт `inf`. Одна общая функция «сохранённый результат только для конечного
числа» закрывает оба места.
