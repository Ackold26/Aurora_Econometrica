```rust

        Ok(bytes) => return Ok(bytes),

            let pause = RETRY_BACKOFF.get(attempt).copied().unwrap_or(...);
```

## Почерк Smart Analytica (`POST /jobs → 202`, три минуты тишины, отмена самим клиентом)

Общий слой один и тот же (`aurora_gateway::cloud`) — дефект переносимый, не порок одного продукта.

**1. Двадцать секунд молчания ленты = «обрыв связи».** `progress.rs:19` `FIRST_EVENT_GRACE_SECONDS = 20`; `client.rs:880-887`:

```rust
let next = tokio::time::timeout(self.first_event_grace, body.next()).await;
let chunk = match next {
    // Молчание в начале — верный признак, что ленту копит посредник.
    Err(_) if !seen_any => return Err(CloudError::Connection("лента молчит".into())),
    Err(_) => continue,
    Ok(None) => return Ok(StreamStep::Reopen),
    ...
```

Задание к этому моменту создано (202) и живёт. Клиент считает это ошибкой ленты (`client.rs:812` `Err(_) => progress.note_stream_failure()`), после `STREAM_ATTEMPTS = 2` (`progress.rs:16`) уходит на опрос с шагом 2 с. Со стороны сервера это и есть «тишина».

### Места, где клиент снимает уже созданное задание — с условиями

**🔶 Уточнение по коду (повторное чтение 11.09):** прежде я назвала «четыре места, где клиент сам снимает задание без участия человека». Точнее так: мест пять, но **без участия человека срабатывают только два** — №1 и №2 ниже. Остальные три требуют признака отмены от продукта, то есть нажатия «Остановить».

| # | место | условие срабатывания | нужен ли человек |
|---|---|---|---|
| 1 | `client.rs:704-712` — `if !keep_inputs_confirmed(request.keep_inputs, created.keep_inputs) { let stopped = self.stop_job(&job_id, ...).await; return Err(ResendInputs { stray_job: ... }) }` | клиент просил «вложения уже на сервере», а задание этого признака не подтвердило: служба прежней версии поля не знает, либо повтор тем же ключом отправки вернул задание с иным значением | **нет** |
| 2 | `client.rs:748-763` — `if let Err(e) = self.upload_input(...) { failure = Some(e); break; }` … `if failure.is_none() { if let Err(e) = self.start_job(&job_id).await { failure = Some(e); } }` … `if let Some(err) = failure { let _ = self.cancel(&job_id).await; return Err(err); }` | сорвалась выгрузка любого вложения ИЛИ не прошёл пуск задания (`start_job`). Отмена шлётся голым `cancel`, её отказ проглочен (`let _ =`) | **нет** |
| 3 | `client.rs:745-747` — `if should_stop() { let mut empty = Progress::new(); return Ok(self.stop_job(&job_id, &mut empty, &mut on_delta).await); }` | признак отмены пришёл, пока файлы уезжали на сервер | да |
| 4 | `client.rs:781-782` — `if should_stop() { return Ok(self.stop_job(&job_id, &mut progress, &mut on_delta).await); }` | признак отмены перед очередным витком ожидания | да |
| 5 | `client.rs:793` — `Ok(StreamStep::Stopped) => return Ok(self.stop_job(...).await)`; признак спрашивается внутри чтения ленты на `client.rs:877` | признак отмены во время открытой ленты | да |

Для наблюдателя со стороны сервера все пять неотличимы от «пользователь нажал Остановить». Почерк Smart Analytica — «202, тишина, отмена клиентом» — объясняется №1 и №2: у неё вложения (презентации в сотни килобайт) уезжают отдельными запросами после постановки, и обрыв на любом из них ведёт прямиком в №2. Три минуты укладываются в связку «две попытки ленты по 20 с + опрос по 2 с + выгрузка вложений».

**2. Тот же ложный текст.** Все ветви отдают продукту `CloudError::Connection` (или `ResendInputs`) и печатают «работа на сервере продолжается». В случае №2 это прямая ложь: задание клиент только что снял сам.

**Формулировка дефекта общего слоя:** `CloudError` в поставленных версиях не различает три фазы — «до постановки», «после постановки», «после самостоятельной отмены», — а пользовательский текст обещает продолжение работы во всех трёх.

🔴 **Линейка на разных метках.** Эконометрика — `aurora_gateway-v0.6.6`; Smart Analytica — `aurora_gateway-v0.6.5` (`_wt_analytica_cloud\src-tauri\Cargo.cloud.fragment.toml:45`, `_wt_cpd81_analytica\...:45`). Обе старше исправления.

## Что лечит подъём метки до v0.6.7, а что в ней остаётся

**🔶 Весь этот раздел — новое чтение кода (11.09), не первоначальный разбор.** Читался коммит метки: `git show ce39327:aurora_gateway/src/cloud/client.rs` из дерева `_wt_gw_v066_backport` (3910 строк против 1609 в v0.6.6).

**Живо в v0.6.7 — оба дефекта, о которых спрашивала:**

```
1634:  Decision::Retry => Err(CloudError::Connection(format!("сервис ответил {status}"))),
1444:  Decision::Retry => Err(CloudError::Connection(format!("лента ответила {status}"))),
1472:  Err(_) if !seen_any => return Err(CloudError::Connection("лента молчит".into())),
1468:  let next = tokio::time::timeout(self.first_event_grace, body.next()).await;
601:   first_event_grace: Duration::from_secs(FIRST_EVENT_GRACE_SECONDS),   // те же 20 с
```

То есть маскировка 408/425/429/5xx под обрыв связи — **жива**; объявление 20 секунд молчания ленты обрывом — **живо**, срок не изменился.

**Починено в v0.6.7 частично — и это важнее всего для нашего случая.** Различение фазы есть (`NotSent`, `SendPhase`, `client.rs:151,156,178`), но к постановке задания оно применяется **только для одного отказа**:

```rust
// v0.6.7 client.rs:1174-1195
let created = match self.create_job_full(...).await {
    Ok(created) => created,
    Err(err) if is_slow_channel_refusal(&err) => {
        return Err(CloudError::NotSent(NotSent { phase: SendPhase::TooSlow, ... }))
    }
    Err(err) => return Err(err),          // ← строка 1212: обычный Connection уходит как есть
};

// v0.6.7 client.rs:1940-1942
fn is_slow_channel_refusal(err: &CloudError) -> bool {
    matches!(err, CloudError::Refused(refusal) if refusal.error == REQUEST_TIME_SKEW)
}
```

Наш случай — шесть быстрых отказов на `POST /v1/jobs` — это `Connection`, а не `REQUEST_TIME_SKEW`. Он попадает в `Err(err) => return Err(err)` и доезжает до человека прежним видом ошибки. Текст при этом смягчён (`v0.6.7 client.rs:336-340`): вместо «его результат можно забрать позже – работа на сервере продолжается» стало «Если задание уже было принято, работа на сервере могла продолжиться – загляните позже, результат может быть готов». Утверждение стало возможностью, но человеку по-прежнему предлагают вернуться за результатом, которого при неотправленном задании не будет.

Появился и новый вид `Disconnected(work)` (`v0.6.7 client.rs:396+`) — обрыв ПОСЛЕ начала работы, с сохранением накопленного текста.

**Вывод одной строкой:** подъём метки v0.6.6 → v0.6.7 лечит различение фазы для отправки файлов и пуска (`NotSent`/`SendPhase`), сохраняет накопленный текст при обрыве в работе (`Disconnected`), смягчает формулировку `Connection` с утверждения до возможности и приносит нашу правку кириллицы (`Utf8Stream`), — но НЕ лечит ни маскировку кодов 408/425/429/500/502/503/504 под «обрыв связи» (`v0.6.7 client.rs:1634`, `1444`), ни объявление 20 секунд молчания ленты обрывом (`v0.6.7 client.rs:1472`, срок прежний), ни главный случай показа: обрыв на самой постановке задания остаётся видом `Connection` без признака фазы (`v0.6.7 client.rs:1212`), и человеку по-прежнему предлагают вернуться за несуществующим результатом.
