## 2. Рекомендованный канал для нашего случая

**Kaspersky CompanyAccount + официальная процедура support.kaspersky.com/1870**, а не разовая жалоба через форму для частных пользователей и не OpenTIP как основной путь. Обоснование:
- Мы — разработчик ПО (вендор), а не конечный пользователь, у которого сработал детект случайно. Официальная инструкция прямо разводит потоки «для приложений дома» и «для бизнеса» — CompanyAccount создан именно под вендорский/корпоративный случай, с более формальным и отслеживаемым процессом (тикет, история переписки).
- Для нашего детекта — поведенческий `PDM:Trojan.Win32.Generic` — есть отдельная официальная страница с чётким списком требуемых материалов ([support.kaspersky.com/kes-for-windows/14.0/diagnostics/15898](https://support.kaspersky.com/kes-for-windows/14.0/diagnostics/15898)): trace-файлы приложения на момент срабатывания, точный текст события, файл/ссылка в архиве с паролем `infected`, и отдельно — **GSI-отчёт** (Get System Info) для случаев с PDM. Это прямое указание, что подача по поведенческому детекту требует иного комплекта, чем по статической сигнатуре (см. п.4).
- OpenTIP — полезен как предварительный шаг («отправить на повторный анализ») и для отслеживания вердикта по хешу, но известен нестабильной формой именно для false positive-сценария (см. GitHub issue выше) — не полагаться на него как единственный канал.
- Наш установщик 258 МБ: публичного лимита размера ни для OpenTIP, ни для формы поддержки, ни для CompanyAccount не нашла. Стандартная практика при большом файле — прикладывать не сам бинарник, а **ссылку на скачивание** (сайт продукта / прямая ссылка на релиз) плюс хеш (SHA-256); это соответствует требованию инструкции «файл или ссылка» и снимает риск отказа по размеру. Рекомендую сразу готовить пакет как «хеш + прямая ссылка + trace/GSI», а не пытаться приаттачить 258 МБ напрямую.

## 3. Программа белого списка (Allowlist / бывш. Whitelist Program) — есть, подробности

Программа **действует** и предназначена именно для превентивной подачи (не разовая жалоба, а постоянная регистрация продукта, чтобы новые сборки не ловились). Ключевые условия по официальной странице [kaspersky.com/partners/allowlist-program](https://www.kaspersky.com/partners/allowlist-program):

- **Стоимость:** бесплатно.
- **Требования к сайту компании:** действующий сайт с актуальной информацией о компании и продукте, указан юридический адрес, элементы интерфейса не вводят пользователя в заблуждение.
- **Требования к ПО:** не имитирует интерфейс сторонних продуктов/системные сообщения ОС; не рекламирует несвязанное ПО и ресурсы; не обращается на вредоносные/потенциально нежелательные ресурсы; не использует манипулятивные формулировки, вынуждающие платить; средства удалённого администрирования допустимы только если ранее не замечены в использовании киберпреступниками; цифровая подпись должна быть уникальной и не скомпрометированной (то есть иметь собственную подпись — плюс к пункту про сертификаты, см. часть 5).
- **Что даёт:** независимая экспертиза Kaspersky, подтверждение отсутствия ложных срабатываний, отдельная линия поддержки для участников программы.
- **Регистрация:** кнопка «Register in the program» на странице программы → https://whitelisting.kaspersky.com/program_registration. Детальный состав документов и сроки рассмотрения **не опубликованы** на открытых страницах — это выясняется только после старта регистрации.

Для нас эта программа важнее разовой жалобы, если у продукта регулярные релизы: разовое обращение снимает конкретный детект конкретной сборки, а Allowlist снижает риск повторения на будущих версиях.

## 4. Что писать при поведенческом детекте (`PDM:Trojan.Win32.Generic`)

Официальная позиция Kaspersky (энциклопедия + техстраницы): PDM — это вердикт **Proactive Defense Module / System Watcher**, основанный на поведенческом анализе последовательности действий процесса (не на сигнатуре и не на статическом анализе файла). Это объясняет, почему подача отличается от обычной жалобы на статический детект:

- Требуется **GSI-отчёт** (Get System Info) — специальная диагностическая утилита Kaspersky, собирающая системные логи вокруг момента срабатывания ([support.kaspersky.com/3632](https://support.kaspersky.com/3632), [support.kaspersky.com/kes-for-windows/14.0/diagnostics/15898](https://support.kaspersky.com/kes-for-windows/14.0/diagnostics/15898)).
- Требуется **точный текст события детекта** и **trace-файлы приложения** на момент срабатывания — то есть нужно воспроизвести срабатывание и залогировать его, а не просто прислать инсталлятор.
- В описании желательно явно указать: что делает установщик в момент срабатывания (распаковка, запись в автозагрузку/Startup, порождение процессов) — по внешним источникам именно такая последовательность (инсталлятор → извлечение EXE → запись в автозагрузку) типично триггерит PDM-эвристику.
- Отличие от статического детекта: при обычной сигнатуре обычно достаточно файла/хеша и описания; при PDM Kaspersky прямо просит доказательства поведения процесса (GSI + trace + точный текст события), потому что вердикт вынесен не по содержимому файла, а по рантайм-поведению — соответственно, одной подписи или хеша недостаточно для реабилитации.

Источники: [Heuristic and proactive detections — Kaspersky IT Encyclopedia](https://encyclopedia.kaspersky.com/knowledge/heuristic-and-proactive-detections/), [Files to send to Kaspersky Technical Support in case of PDM malware detection](https://support.kaspersky.com/kes-for-windows/14.0/diagnostics/15898), практика сообщества на GitHub-issues разработчиков ([kirodotdev/Kiro#8950](https://github.com/kirodotdev/Kiro/issues/8950), [lemonade-sdk/lemonade#2318](https://github.com/lemonade-sdk/lemonade/issues/2318)).

## 6. Прямой ответ: помогает ли подпись кода против PDM?

**Нет, не помогает** — по крайней мере, прямых подтверждений обратного не нашла ни в одном источнике. PDM — поведенческий вердикт Proactive Defense Module/System Watcher, срабатывающий на **последовательность действий процесса** (распаковка, запись в автозагрузку и т.п.), а не на отсутствие подписи или репутацию файла. Официальная процедура подачи по PDM (п.4) требует GSI-отчёт и trace-логи поведения — не хеш и не сертификат. В документированных кейсах на GitHub (Kiro, Lemonade SDK и др.) разработчики с корректно подписанными установщиками всё равно ловили PDM-детект, и решением было либо обращение в поддержку с реабилитацией, либо участие в Allowlist Program — не (повторная) подпись.

**Разграничение по сферам действия подписи кода** (по совокупности источников, включая общее понимание механики Windows/AV, не опровергнутое ни одним найденным источником):
- **SmartScreen (Windows)** — да, подпись + накопленная репутация издателя снижает предупреждения; но для российского юрлица САМА подпись сейчас практически недостижима легальным путём у публично доверенных УЦ (см. п.5.1–5.3).
- **Статические антивирусные эвристики** — подпись действительно снижает вероятность срабатывания статических/эвристических сигнатур, так как добавляет доверенный признак к файлу.
- **Поведенческие детекты (PDM и аналоги)** — подпись **не является защитой**, так как вердикт не завязан на статических признаках файла.

**Вывод для решения «вкладываться ли в сертификат ради этой конкретной задачи»:** если основная боль — именно `PDM:Trojan.Win32.Generic`, сертификат подписи кода эту проблему не решит; решает её только обращение в Kaspersky по официальной процедуре (CompanyAccount + GSI-отчёт) и/или участие в Allowlist Program. Сертификат имеет смысл отдельно — как общая гигиена для SmartScreen и статических эвристик — но с учётом п.5 для российского юрлица это сейчас нетривиальная и не полностью решённая задача (легальных публично доверенных путей нет; отечественная инфраструктура SmartScreen не снимает; иностранное юрлицо — вариант без свежего прямого подтверждения).

## 7. 🔴 Чего подтвердить не удалось

- Актуальность/устаревание адреса `false_detection@kaspersky.com` — не нашла его ни в одном официальном источнике 2026 года (только `newvirus@kaspersky.com` в качестве общего адреса). Не факт, что он не работает — просто нет свежего подтверждения ни рабочего, ни нерабочего статуса.
- Точный максимальный размер файла для загрузки в форму false positive / OpenTIP / CompanyAccount — публично не опубликован ни на одной из проверенных страниц.
- Точные сроки ответа Kaspersky на обращение вендора (SLA) — не публикуются официально; форумные упоминания о задержках (до 10+ дней) есть, но это не официальный SLA, а анекдотические случаи (не включила в таблицу как факт).
- Детальный список документов и сроки рассмотрения заявки в Allowlist Program после старта регистрации — форма регистрации требует перехода на сам портал, содержимое анкеты не индексируется публично.
- Применимость закона от 31.07.2026 (иностранные организации → российские квалифицированные сертификаты) конкретно к code-signing сертификатам ПО, а не только к ЭП для документооборота — текст новости этого не разъясняет, требуется первоисточник закона.
- Признаёт ли Microsoft УЦ Минцифры/ОТУЦ в Trusted Root именно для целей код-подписи/SmartScreen — не нашла ни подтверждения, ни официального опровержения на 2026 год; статья xakep.ru от 23.06.2026 говорит о проблеме как об открытой, но это не позиция самой Microsoft.
- Не удалось прочитать форумную ветку Kaspersky «vendor application for whitelisting» и «how to report false positive» напрямую (дважды ошибка соединения ECONNRESET) — выводы по этим темам собраны из других источников (официальные страницы), не из самого форума.
