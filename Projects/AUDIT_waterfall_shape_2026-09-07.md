## 3. Ключевое следствие: правка CPD-104 на живых данных не исполняется

Обе формулы с сохранённым результатом (`report.rs:1623` доля канала, `report.rs:1630` итог)
физически лежат **внутри** блока `if let Some(wf) = decompose["waterfall"].as_array()`
(строки 1597…1648). Раз блок не исполняется, правка не производит ничего.

Проверено поиском по XML внутри обеих книг:

```
book_live.xlsx: формулы с сохранённым результатом: []          ← ни одной
book_test.xlsx: формулы с сохранённым результатом: [('B4/B$6', '0.3'), ('B5/B$6', '0.7'), ('SUM(B4:B5)', '1000')]
```

### Что ровно строит сторож

`report.rs:3752-3785`, дословно:

```rust
#[test]
fn waterfall_formula_results_are_cached_not_zero() {
    …
    let decompose = json!({"waterfall": [
        {"category": "TV", "value": 300.0},
        {"category": "Digital", "value": 700.0}
    ]});
    let path = std::env::temp_dir().join("aurora_cpd104_waterfall_test.xlsx");
    build_xlsx(&json!({}), &decompose, &json!({}), &[], None, "test", &path, None)
        .expect("build_xlsx waterfall");
    let text = xlsx_all_text(&path);
    assert!(
        text.contains("<f>B4/B$6</f><v>0.3</v>"), …
    );
    assert!(
        text.contains("<f>SUM(B4:B5)</f><v>1000</v>"), …
    );
}
```

Это **массив словарей с ключами `category` и `value`**. Движок таких ключей не производит вовсе:
`decomposer.py:1482-1486` отдаёт словарь `{labels, values, types}`, и `category` в нём нет ни на
каком уровне. Живой файл демо-проекта:

```json
"waterfall": {
  "labels": ["Baseline", "Performance бюджет", "Онлайн-видео бюджет", "Наружная реклама бюджет", "ТВ бюджет", "Итого"],
  "values": [10262506440.0, 743506518.0, 1010053470.0, 105034893.0, 70134957.0, 12191236278.0],
  "types":  ["baseline", "channel", "channel", "channel", "channel", "total"]
}
```

Сторож проверяет форму, которой не бывает, и потому зелёный при полностью мёртвой правке.
Отдельная примета того же: на входе сторожа книга получается **без листа «ROI каналов»**
(в его `decompose` нет ключа `channels`) — то есть сторож строит книгу, какой клиент никогда не
получает, и сверяет её XML.

Путь данных сквозной, без преобразований по дороге: `decomposer.py:1528` пишет тот же словарь в
`results/decomposition.json`; `DecomposeStep.svelte:353` кладёт ответ `econ_decompose` в хранилище
как есть; `ReportStep.svelte:714-722` передаёт его в `econ_export_xlsx` как есть.

## 4. Где ещё тот же разрыв формы

Сверила **каждое** обращение `as_array()` в `src-tauri` по результатам движка с фактическим типом
в живых файлах демо-проекта (`decomposition.json`, `optimization.json`, `model-diagnostics.json`):

Пути, для которых живого артефакта в проекте нет (прогноз и сценарии), проверены по коду движка,
который их и собирает — там везде списки, разрыва нет:
`planning.py:431-441` строит `'predictions': list(...)`, `'ci_low': list(...)`,
`'period_labels': list(...)`; `planning.py:451` и `scenario.py:1296` — `'scenarios': scenarios`
(список). Соответствуют `report.rs:542, 2023, 2050-2064, 2127`.

Обращения `as_array()` в `commands/pptx_processor.rs:475-727` относятся к разбору презентаций,
а не к результатам расчётного движка — в область этого зонда не входят и на живом артефакте
не проверялись.

### Вывод по вопросу «класс или единичный случай»

**По фактам — единичный случай в двух точках вызова** (`report.rs:717` и `report.rs:1597`), а не
распространившийся класс: все остальные тринадцать обращений к результатам движка совпадают
с формой по факту.

**Но предпосылка класса налицо, и она уже срабатывала дважды.** Договорённости о форме между
Python и Rust не проверяет ничто: ни типов, ни схемы, ни общего описания — Rust просто пробует
`as_array()` и при неудаче молча пропускает целый блок вывода. Тот же самый ключ и та же самая
ошибка уже ловились на стороне Python — комментарий `methodology_cert.py:255-262` описывает
дословно это: «Прежний код итерировал `waterfall` как список словарей с ключом `category`, а
декомпозер отдаёт `{labels, values, types}`… Ещё одно доказательство, что модуль не вызывался ни
разу». То есть в двух независимых местах написали один и тот же неверный домысел о форме — значит
опасность не в конкретной строке, а в том, что молчаливый пропуск ничем не отличим от «данных нет».

## 5. Предлагаемое лечение (не применяла)

### Какая сторона должна поменяться: **Rust**

Форму `{labels, values, types}` уже читают три независимых потребителя, и все три работают:

1. `DecomposeStep.svelte:172-187` — диаграмма вкладов на шаге разложения продаж
   (`waterfallDisplay`, читает `data.waterfall.labels/values/types`, для количественного KPI
   пересобирает `values`);
2. `ModelComparisonView.svelte:189-205` — две диаграммы при сравнении моделей
   (`snap?.decomposition?.waterfall`);
3. `charts/generators.py:13-23` — `waterfall_chart(data)`, где `data['labels']`, `data['values']`,
   `data['types']`; вызывается из `server.py:1989` и через него попадает в отчёт .html и в .pptx.

Менять движок значит трогать все три плюс формат уже сохранённых на дисках клиентов
`decomposition.json` (старые проекты перестанут открываться корректно). **Это дороже и заметно
рискованнее.** Менять Rust — трогать один файл и двух читателей, которые сейчас всё равно не
работают: сломать нечего.

### Что делать по существу (словами дифа, не применяла)

1. В `report.rs` завести одну функцию разбора, например
   `fn waterfall_rows(decompose: &Value) -> Vec<(String, f64)>`, которая читает словарь
   `{labels, values, types}`, идёт по индексу и отдаёт пары «категория – значение»,
   **пропуская элемент с `type == "total"`** (он не слагаемое, а итог; иначе сумма удвоится
   и все доли станут вдвое меньше). Оба места (`:717` и `:1597`) переводятся на неё.
2. Сохранить снисходительность к старой форме: если `waterfall` пришёл массивом — читать как
   сейчас. Это дёшево (одна ветка) и защищает открытие старых проектов, где на диске лежит
   что-то иное.
3. Только после этого чинить деление на ноль (находка Medium №3 из
   `Projects/AUDIT_medium_verdicts_2026-09-07.md`): при нулевой сумме не писать формулу деления
   вовсе.
4. Сторож `report.rs:3752` переписать на форму, которую **отдаёт движок**, и лучше не на
   синтетику, а на настоящий `decomposition.json` — он лежит готовым в демо-проекте, прогонять
   пайплайн не нужно. Проверять сторож должен две вещи: лист «Декомпозиция» в книге **есть**,
   и формулы несут сохранённый результат.
5. Отдельно и в первую очередь — сторож на само существование листов: «на живом
   `decomposition.json` книга обязана содержать листы Обзор, Executive Summary, Спецификация,
   Декомпозиция, ROI каналов, Spend vs Effect, Динамика». Молчаливый пропуск блока из-за формы
   ловится только такой проверкой, и она закрывает весь класс, а не одну строку.

### Цена

Пункты 1–2 — 20–25 строк в одном файле, полдня вместе с проверкой на живом файле демо-проекта.
Пункт 3 — 3 строки. Пункты 4–5 — день; пункт 5 самый ценный, потому что ловит будущие разрывы
формы, а не этот конкретный.

Правка меняет содержимое клиентской выгрузки (лист появляется), поэтому после неё нужна живая
проверка файла глазами, а не только зелёная приёмка.

## 6. Последствие для клиента (что он видит сегодня)

Формат .xlsx предлагается на шаге отчёта отдельной кнопкой с подписью
«XLSX – для самостоятельной работы с данными» (`ReportStep.svelte:1093`). В том, что клиент
получает, **нет листа «Декомпозиция» и нет диаграммы вкладов**; в отчёте-разметке нет таблицы
«Вклады в продажи». Разложение продаж клиент видит только на экране и в отчёте .html/.pptx —
их собирает Python и по своей, рабочей ветке.

Косвенная примета, что этим путём никто не ходил: в `exports/` эталонного демо-проекта лежат
только `.html`, `.pptx` и `.json` от 31.08 — ни одной выгрузки `.xlsx`.
