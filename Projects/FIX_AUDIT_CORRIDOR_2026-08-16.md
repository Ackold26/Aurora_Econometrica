## F-13 · High · сторож единиц срабатывает на «единица неизвестна»

**Что было.** Защита строилась на списке каналов с ЗАДАННОЙ стоимостью единицы ≠ 1.
`_resolve_current_unit_costs` возвращает только каналы с заданной положительной стоимостью,
поэтому канал без стоимости вообще в список несовпадений не попадал никогда — и прямой проход
подставлял `1.0`, складывая пункты рейтинга с рублями.

**Что стало.** Появилась `classify_channel_units` (`optimize/bounds.py`) — раскладывает каналы
на три непересекающихся списка:

| группа | признак | поведение |
|---|---|---|
| `priced` | стоимость задана и ≠ 1 | отказ (как раньше) |
| `unknown` | стоимость НЕ задана, но есть признак натуральных единиц: имя канала (`NON_MONEY_NAME_HINTS`) либо `unit_costs_snapshot` обучения | **отказ (новое)** |
| `money` | стоимость задана и = 1, либо не задана и признаков нет | считаем, допущение названо явно в `unit_assumption` |

Отказ отдаёт `status='unit_mismatch'` с разделёнными списками `priced_channels` /
`unknown_unit_channels` и reason `non_money_channels` / `unknown_unit_channels` / `mixed_units`.
Чисел в ответе нет вовсе.

**Как отличаю натуральные единицы от рублей.** Взяла эвристику, уже принятую в движке:
список имён `UNIT_HINTS` из гейта UNIT_SMELL (`engines/optimizer.py`) и `engines/decomposer.py` —
TRP, GRP, OTS, IMPRESSION, CLICK, ПОКАЗ, КЛИК, ПРОСМОТР, ВИЗИТ, ПУНКТ, ОХВАТ, РЕЙТИНГ. Там она
объявлена внутри функций, импортировать нечего, поэтому в `bounds.py` копия с явной ссылкой на
источник. Второй признак — снимок стоимостей, применённых при обучении: если при обучении у канала
была стоимость ≠ 1, а сейчас её нет, данные натуральные, а перевода в деньги не существует.

**Почему не «отказывать всегда, когда стоимость не задана».** Рассматривала и отвергла: в проектах,
где все данные уже в рублях, `unit_costs` штатно пуст (движок везде читает `unit_costs.get(c, 1.0)`),
и такой отказ убил бы функцию у всех без исключения — поле было бы мёртвым, а не безопасным.
Взятый порядок: отказ везде, где есть хоть какой-то признак не-денег, и явно названное допущение
там, где признаков нет (`unit_assumption` со списком каналов). Тихого счёта не осталось ни в одной ветке.

**🔬 Живая проверка (эталонный проект кагоцел, только чтение).**
Было: `status='ok'`, `budget_used.lo=157 151 849`, продажи 10,38–11,81 млрд — при том, что среди
каналов `TRPs бренд (W 25-54)` и `unit_costs={}`.
Стало: `status='unit_mismatch'`, `reason='unknown_unit_channels'`,
`unknown_unit_channels=['TRPs бренд (W 25-54)']`, чисел нет.

**Мутации (внести-поймать-откатить), место реального вычисления — `classify_channel_units`:**
1. Отключила ветку имени канала (`if False and any(hint ...)`) → упали
   `test_aggregate_sales_refuses_when_unit_is_unknown` и `test_mixed_units_report_both_groups`. Откатила.
2. Отключила ветку снимка обучения → упал `test_unknown_unit_detected_by_training_snapshot`. Откатила.

## F-07 · Medium · приведение к суммарному бюджету — по активным периодам, с проверкой разумности

**Что было.** `lo`/`hi` умножались на число ВСЕХ строк данных, тогда как сами они считаются по
`spend[spend > 0]` — по активным периодам. Для флайтового канала это завышало суммарную трату в
`n_периодов / n_активных` раз, и никакой проверки не было: `budget_used.lo` мог оказаться больше
`budget_used.current` при статусе `ok`.

**Что стало.**
- `compute_per_channel_bounds` отдаёт `n_active_periods` (число периодов с ненулевой тратой), а
  докстринг прямо говорит, что `lo`/`hi` — трата за один АКТИВНЫЙ период.
- Приведение поканальное: `граница канала × число активных периодов этого канала`. Для канала,
  работавшего каждый период, результат совпадает с прежним.
- Если `n_active_periods` неизвестно (кто-то собрал `per_channel` вручную) — `status='unavailable'`,
  reason `active_periods_unknown`, чисел нет.
- Если у канала активных периодов больше, чем периодов обучения, — `reason='periods_disagree'`
  (коридор и проход читали разные данные).
- **Проверка разумности:** коридор обязан накрывать текущую трату — он вокруг неё и построен.
  Не накрывает → `status='implausible_bounds'`, reason `corridor_does_not_bracket_current`, продаж нет.
  Отдельная ветка `corridor_totals_invalid` на `lo > hi` и неположительный текущий бюджет.
  Статуса `ok` при несогласованных числах больше не бывает.

**🔬 Живая проверка (кагоцел).** Флайтовость подтверждена: активных периодов у каналов
23, 27, 31, 31, 22 из 31. Прежнее приведение × 31 завышало границы OLV на 35%, ТВ-канала на 41%.
Числа по этому проекту теперь не выдаются вовсе — раньше срабатывает отказ по единицам (F-13).

**Мутации:**
3. Вернула `* n_periods` вместо `* active[c]` в месте расчёта `budget_used` → упал
   `test_flight_channel_scaled_by_its_own_active_periods`. Откатила.
4. Отключила проверку «коридор накрывает текущую трату» → упал
   `test_bounds_not_bracketing_current_are_refused`. Откатила.

## F-14 · Medium · у каждой группы чисел — свой признак основания

**Что было.** В одном словаре: `budget_used` (уже суммарные), `corridor_budget_basis: 'per_period'`
(описывает соседний блок), `basis: 'total_over_training_period'` (описывает продажи), плюс
`corridor_basis_mismatch`. Три признака на четыре группы чисел.

**Что стало.** Числа разложены по группам, у каждой — своё поле `basis`, общих признаков рядом нет:

```
aggregate_sales = {
  'status': 'ok',
  'n_periods': N,
  'corridor_budget': {lo, hi,          basis='budget_per_active_period'},
  'budget_used':     {lo, hi, current, basis='budget_total_over_training_period'},
  'sales':           {lo, hi, current, basis='sales_total_over_training_period'},
  'active_periods_per_channel': {канал: n},
  'unit_assumption': {...},   # если у части каналов стоимость единицы не задана
  'message': ...
}
```

Убраны: верхнеуровневые `lo`/`hi`/`current` (были продажами без своей группы), `basis`,
`corridor_budget_basis`, `corridor_basis_mismatch`. Значения признаков — константы модуля
(`BUDGET_PER_ACTIVE_PERIOD`, `BUDGET_TOTAL_OVER_TRAINING`, `SALES_TOTAL_OVER_TRAINING`).

Дополнительно на верхнем уровне коридора появился `aggregate_budget_basis` — признак у КАЖДОГО
числа `aggregate_budget` отдельно (`lo`/`hi` — за активный период, `current` — за весь период
обучения). Само поле `aggregate_budget` не тронуто: им пользуется интерфейс.

**Мутация:**
5. Вернула в ответ общие `basis` и `corridor_budget_basis` → упал
   `test_aggregate_sales_computed_at_corridor_bounds`. Откатила.

## F-08 · Low · продажи считаются по явному запросу

**Что было.** `project_dir` передавался в коридор всегда, поэтому каждый вызов поднимал прямой
проход: чтение `models/latest.pkl` + повторное чтение файла данных + три прохода — за поле,
которого интерфейс ещё не показывает.

**Что стало.** В `SafeCorridorRequest` появился `include_sales: bool = False`. Без него `project_dir`
в `compute_safe_corridor` не передаётся, а в ответ кладётся
`aggregate_sales = {'status': 'not_requested', 'reason': 'include_sales_off', 'message': ...}` —
поле не молчит и не отдаёт нулей, потребитель видит, чего не хватает.

**Замеры (кагоцел).** Цена самого прохода (загрузка модели + данные + три вызова) в свежем
процессе — **0,707 с**; аудитор мерил прирост 0,18 с на прогретом. По умолчанию эта цена больше
не платится. Побочно: после F-13 отказ по единицам срабатывает ДО прохода, поэтому даже
`include_sales=true` на кагоцеле стоит 0,046 с вместо прежних 0,199 с.

**Мутация:**
6. Вернула безусловный `project_dir=req.project_dir` → упал
   `test_corridor_without_include_sales_does_not_touch_the_model` («прямой проход поднялся без
   запроса продаж»). Откатила.
