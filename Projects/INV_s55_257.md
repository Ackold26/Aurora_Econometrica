## Подробности

### 1. L1 — квартальная/годовая гранулярность «мес год» искажает края срока

- **Где:** `sidecar/econometrica/engines/narrative_adapter.py:914` (`format_period_span`) вызывает `_parse_period_label`
  (:904) и `_ru_month_year` (:900), правило разбора то же, что у `_derive_data_coverage`. Гранулярность определяет
  `sidecar/econometrica/engines/planning.py:151` → `utils/forecast_validation.py::detect_granularity`.
- **Как воспроизводится:** квартальные метки начала периода (`QS`) вида `['2026-01-01', …, '2026-10-01']` дают
  «янв 2026 – окт 2026», хотя план фактически покрывает по декабрь 2026; метки конца периода (`QE`)
  `['2026-03-31', …, '2026-12-31']` дают «мар 2026 – дек 2026», хотя план начинается в январе. Годовые (`YS`) —
  аналогично. Видит покупатель в HTML и PPTX (подпись «Срок плана»), только при квартальных/годовых наборах данных
  (для MMM это редкость — недельные и месячные данные разобраны верно).
- **Набросок правки:** в `format_period_span` для `granularity in ('Q', 'Y')` печатать не «мес год», а «Qn год» /
  просто «год» (то есть отдельная ветка форматирования по гранулярности, а не универсальный «мес год» для любых
  ISO-меток). Гранулярность уже доступна вызывающей стороне (`planning.py`), нужно её прокинуть в `format_period_span`
  (сейчас функция получает только `first`/`last`, без гранулярности).
- **Тесты рядом:** `tests/test_planning_section_reports.py` (42 теста на `format_period_span`/`_derive_data_coverage`,
  описаны в `AUDIT_s53_datefix.md`), под квартал/год новых тестов там нет — только пример из аудита (`probe1.py`,
  не оформлен в pytest).
- **Риск правки:** нужно прокинуть параметр гранулярности через сигнатуру `format_period_span` — это тронет всех
  вызывающих (`aurora_pptx/builder.py`, `aurora_html/sections.py`), но сигнатура и так уже параметризована по
  первому/последнему значению, риск локальный.
- **Объём:** S (≤1 ч) — сама функция короткая, но нужно решить формат для Q/Y (например «Q1 2026 – Q4 2026»).
- **Зависимость:** для MMM квартальные данные редки (сказано и в самом аудите s53), поэтому это решение владельца —
  чинить сейчас или отложить.

### 2. L2 — экран и отчёт по-разному подписывают один и тот же срок при недельных данных

- **Где:** экран — `src/lib/components/pipeline/PlanningStep.svelte:764` и
  `src/lib/components/pipeline/ValidateStepV13.svelte:1273`, обе строки идентичны:
  `({mpData.period_labels[0]} – {mpData.period_labels[mpData.period_labels.length - 1]})`, то есть выводят
  `period_labels` как есть (например `2025-W01 – 2025-W32`). Отчёт (HTML/PPTX) после правки s53 — через
  `format_period_span`, даёт «дек 2024 – авг 2025» для тех же данных.
- **Как воспроизводится:** покупатель видит на шаге планирования в программе `2025-W01 – 2025-W32`, а в
  выгруженном отчёте — «дек 2024 – авг 2025» для тех же дат. Формального противоречия нет (неделя 2025-W01
  действительно начинается 30.12.2024), но год первого края отличается («2025» на экране, «2024» в отчёте).
  Для месячных данных экран и отчёт уже согласованы (`2024-12 – 2025-07` vs «дек 2024 – июл 2025»).
- **Набросок правки:** на выбор владельца — (а) на экране показывать тот же человекочитаемый формат, что в отчёте
  (потребует того же `format_period_span`-подобного форматтера на фронтенде, JS-порт python-функции или API,
  отдающий уже отформатированную строку); (б) оставить как есть и не считать дефектом (недельный формат на экране
  осмыслен для планирования по неделям).
- **Тесты рядом:** нет — ни один существующий тест не сравнивает экран с отчётом.
- **Риск правки:** если портировать форматтер на фронтенд — риск рассинхронизации двух реализаций одного правила
  (Python и JS) при будущих правках; лучше отдавать готовую строку с бэкенда, если решат чинить.
- **Объём:** S–M — сама правка мала, но требует решения по архитектуре (где считать: JS или Python).
- **Зависимость:** решение владельца — унифицировать или оставить.

### 3. L4 — строка «итого» без даты в хвосте входного файла ломает сценарий

- **Где:** `sidecar/econometrica/engines/planning.py:121` (`work[date_col] = pd.to_datetime(work[date_col],
  errors="coerce")` — нечитаемая дата, включая «итого», превращается в `NaT`), `:197-199`
  (`future_dates = [ts.isoformat() if pd.notna(ts) else None for ts in future_df[date_col]]` — `NaT` даёт `None`
  в списке будущих дат), потребитель — `sidecar/econometrica/server.py:540`
  (`future_dates: list[str] | None = None`, комментарий `:538` — «ISO-даты будущих периодов»).
- **Как воспроизводится** (по `AUDIT_s53_datefix.md` L4, проба на фикстуре): 104 недели истории + 6 недель плана +
  строка «итого» с пустым KPI в хвосте файла → хвост определяется как 7 периодов вместо 6 (строка «итого» тоже
  считается периодом плана, потому что её KPI пуст), в `future_dates` появляется `None` вторым элементом. Дальше по
  цепочке модель запроса с `None` в датах отклоняется валидацией (`REJECT ValidationError`) — то есть сбой происходит
  раньше, чем `None` дойдёт до отчёта. **Как это видит покупатель на экране — гипотеза, не проверялась ни в аудите
  s53, ни в этой описи**: вероятно, сообщение «Не удалось построить прогноз базового плана» с текстом ошибки
  валидации, но живого прогона с такой фикстурой через полный конвейер (Tauri → движок → экран) никто не делал.
- **Набросок правки:** после `pd.to_datetime(errors="coerce")` явно отбрасывать хвостовые строки, где вся строка
  (не только дата) выглядит как «итого»/пустая строка-агрегат — например, строки без даты И без значений медиа-
  каналов не считать частью хвоста плана, а не полагаться только на пустой KPI.
- **Тесты рядом:** не найдено ни одного pytest-теста на этот сценарий (только проба аудита s53, не оформленная в
  `tests/`).
- **Риск правки:** трогает общую функцию определения хвоста плана (`detect_media_plan_tail`, судя по имени в
  `AUDIT_s53_datefix.md` «Справочно» разделе) — это путь, которым идут ВСЕ сценарии планирования, ошибка в правиле
  отсева задела бы весь конвейер, а не только строку «итого».
- **Объём:** M (≤полсессии) — нужен сначала живой прогон, подтверждающий гипотезу «REJECT ValidationError», прежде
  чем писать правку (правило `verify_defect_real_before_reporting` — не чинить на гипотезе).
- **Зависимость:** нужна проверка перед правкой; данных о частоте такого входа у реальных клиентов нет.
