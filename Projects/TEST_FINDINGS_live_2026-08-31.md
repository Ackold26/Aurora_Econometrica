## Находки

### 🟠 L-01. Тихая установка отвечает кодом ноль, не сообщая, куда встала
**Где:** установка `Optimizer MMM_2.5.0_x64-setup.exe /S`.
**Что:** код возврата 0, программы нет ни в `%LOCALAPPDATA%\Programs\`, ни в `C:\Program Files`. Фактический путь — `%LOCALAPPDATA%\Optimizer MMM`, найден только по записи в реестре.
**Почему важно:** класс «инструмент рапортует о факте, но не об адресате». Для нас — процедурная ловушка при выпуске: проверять след, а не код возврата.
**Как повторить:** тихая установка, затем поиск по ожидаемым путям.
**Тяжесть:** для клиента не виден, для нашей приёмки опасен.

### 🟠 L-02. Две записи об установке одновременно после перехода на пользовательскую установку
**Где:** список установленных программ Windows.
**Что:** после установки 2.5.0 в системе одновременно `HKCU → Optimizer MMM 2.5.0` (новая, рабочая) и `HKLM → Optimizer MMM 2.4.6` (старая машинная, указывает на `C:\Program Files\Optimizer MMM`).
**Дополнительно:** старый каталог **повреждён** — главного исполняемого файла нет, остались `help-econometrica`, `sidecar`, `_up_` и `uninstall.exe`.
**Почему важно:** клиент, обновляющийся со старой машинной установки, увидит две одинаково названные программы, одна из которых нерабочая. Прямо задевает сценарий выдачи тестового доступа.
**Решение:** за владельцем — определить поведение установщика при обнаружении старой машинной установки.

### 🟠 L-03. Журнал аудита повреждается при одновременной записи
**Где:** `%LOCALAPPDATA%\com.aurora.econometrica\audit.log`.
**Что:** записи от 15.08 16:42:33 физически перемешаны — строки наложены друг на друга, метка времени разорвана посередине:
```
2026-08-15T16:42:33.2302026-08-15T16:42:33.231		online_authonline_auth		2026-08-15T16:42:33.231OKOK
```
Похоже на одновременную запись нескольких потоков без блокировки (в тот момент шли частые проверки `online_auth`).
**Почему важно:** это журнал **аудита**. Продукт продаётся доверием к воспроизводимости и прослеживаемости; журнал, который сам себя портит, эту опору подрывает. Если запись из журнала когда-нибудь понадобится как доказательство — она может оказаться нечитаемой.
**Как повторить:** вызвать частые повторные обращения `online_auth` подряд.
**Не проверено:** есть ли та же гонка у других продуктов линейки — вероятно да, механизм общий.

### 🔵 L-04. Обещание режима «Российские сервисы» без работающего провайдера — подтверждено живым журналом
**Где:** тот же журнал, запись 10.08 09:36:02.
**Что:** дословно —
```
pdn_blocked FAIL cabinet=lawyer-advertising: Резидентный РФ режим: ошибка шлюза —
поток прерван ошибкой шлюза [-33001]: Provider 'ru-resident' is not configured.
Данные НЕ отправлены в облако США.
```
**Почему важно:** это CPD-113 (продукт предлагает платный режим, которого шлюз не умеет), подтверждённый не рассуждением, а живым отказом на этой машине. Запись относится к кабинету Legal, но шлюз общий на линейку — у Эконометрики тот же путь надо проверить отдельно.
**Смягчающее:** отказ честный — данные в США не ушли, и человеку сказано.

### 🟡 L-05. Установка весит 1 883 МБ, около половины — балласт
**Что:** в поставку попадает `dist/` — второй экземпляр того же движка, рантаймом не читаемый, плюс `.hypothesis/`, `__pycache__/`, `tests/`.
**Почему важно:** покупателю, скачивающему пробную версию, почти два гигабайта — заметный барьер входа.
**Осторожно:** сужать состав поставки перед этим выпуском **нельзя** — установщик резко похудеет, и пост-сборочная проверка «меньше предыдущего → блокер» даст ложную тревогу, а отличить «убрали лишнее» от «выпали ресурсы» будет уже нечем. Отдельным шагом после демонстрации.

### 🔵 L-06. Проверка данных и предполётная проверка называют разное число наблюдений
**Где:** демо-набор `planning/synth_fmcg_brand.xlsx`, 130 строк = 104 недели факта + 26 недель медиаплана вперёд.
**Что:**
- `/compute/validate` считает **104** строки (`file.rows=104`) – будущие строки без известной выручки в расчёт не входят. Вердикт «ГОТОВ К МОДЕЛИРОВАНИЮ».
- `/compute/preflight` считает **130** (`n_obs=130`) – берёт все строки файла.

Каждое число по-своему осмысленно: одно про обучающую историю, другое про объём файла. Но пользователю они предъявляются как «сколько у вас наблюдений», без пояснения, какое из двух что означает.
**Почему важно для показа:** покупатель проходит обе проверки подряд, одну за другой, и видит два разных числа об одном файле. Вопрос «так сколько у вас данных – 104 или 130?» на демонстрации прозвучит почти наверняка, и отвечать на него придётся вживую. Для программы, которая продаётся честностью метрик, расхождение без подписи – слабое место.
**Что делать:** к показу достаточно подготовить ответ. По существу – подписать оба числа («недель истории для обучения» против «строк в файле, включая план»).

### ✅ L-07. Проверка данных не считает медиаплан вперёд ошибкой — опасение снято
**Что проверялось:** 26 строк прогнозной части не имеют выручки (её ещё нет). Было опасение, что проверка данных назовёт их пропусками и напугает покупателя на первом же шаге.
**Факт:** `/compute/validate` отвечает `status=ok`, вердикт «ГОТОВ К МОДЕЛИРОВАНИЮ», пустые строки молча не включаются в расчёт. `/compute/preflight` – `overall_tier="reliable"`, режим «bayesian», все под-проверки пройдены: число обусловленности 1,15 при пороге 30, подозрительных пар каналов ноль, разброс по каналам в норме.
**Значение для показа:** первый экран, который увидит покупатель, зелёный и убедительный. Это хорошая точка входа в демонстрацию.
**Оговорка:** покрытие априорного прогноза 0,8 при пороге «не ниже 0,8» – ровно на границе. Статус «пройдено», но запаса нет; если покупатель придёт со своими данными, этот показатель может уйти в красное.

### 🔴 L-08. Предполётная проверка считает наблюдениями строки медиаплана — и объявляет надёжным то, что по её же порогам ненадёжно
**Найдено:** 01.09, при разборе L-06 (исполнитель заметил класс, я подтвердила пробой на живом движке).
**Тяжесть: высшая из найденных.** Бьёт ровно по тому, что продукт продаёт как главное отличие.

**Механика.**
- `engines/validator.py:450` — при обнаружении хвоста медиаплана таблица обрезается до истории,
  с прямым комментарием в коде: «Статистику считаем только по истории».
- `server.py:1065` — предполётная проверка читает файл **заново** и берёт `n_obs = len(df)`
  **без** этой обрезки.
- `engines/ols_modeler.py:552` — пороги достаточности: `n < 20` — байесовский ненадёжен, только OLS;
  `20 ≤ n < 30` — пограничная область с предупреждением; `n ≥ 30` — надёжно.

Итог: строки медиаплана вперёд, где целевой величины нет и быть не может, считаются
наблюдениями и **надувают** число, по которому выносится вердикт о достаточности данных.

**Доказано пробой на живом движке 2.5.0.** Файл: 15 недель истории + 20 недель медиаплана.

| Что спросили | Ответ | Оценка |
|---|---|---|
| `/compute/validate` | `rows = 15`, `status = warning`, «ГОТОВ К МОДЕЛИРОВАНИЮ (с оговорками)» | честно |
| `/compute/preflight` | `n_obs = 35`, `overall_tier = reliable`, `recommended_mode = bayesian` | 🔴 неверно |

По собственным порогам программы при 15 наблюдениях полагается тон `bad` и текст «данных
недостаточно (нужно n≥20) для надёжной оценки». Вместо этого — «надёжно, считайте байесовским».

**Почему это важнее прочего.** Продукт продаётся обещанием «если данных недостаточно, модель не
рисует цифру там, где её нет — честно показывает, где результат не надёжен» (дословно из
ванпейджера). Здесь программа делает ровно обратное, причём молча. Покупатель на пробном периоде
почти наверняка принесёт файл со своей историей и планом вперёд — это штатный формат работы, а не
экзотика.

**Лечение (дёшево).** Считать `n_obs` по той же обрезанной истории, что и проверка данных, —
то есть переиспользовать существующий разбор хвоста медиаплана вместо повторного `len(df)`.
Правка в одном месте (`server.py:1065`), логика уже написана и работает в соседнем модуле.

**Не путать с L-06.** L-06 — про подписи двух разных чисел на экране (косметика). L-08 — про то,
что надутое число **меняет вердикт** о пригодности данных. Первое — неудобство, второе — ложное
обещание надёжности.
