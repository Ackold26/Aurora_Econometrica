# PULSE — CPD-104: формулы в xlsx без сохранённого результата

## Пересказ задачи своими словами
Программа пишет в выгрузку `.xlsx` формулы Excel (`=B4/B$8`, `=SUM(B4:B7)` и т.п.) через
`rust_xlsxwriter`. Библиотека сама не считает — в кэш результата формулы попадает `0`.
Excel при открытии формулу пересчитывает и показывает верное число, но любой другой
потребитель (импорт в учётную систему, скрипт, просмотрщик без движка формул) читает
кэш и видит нули вместо реальных долей и итогов. Опасно именно тем, что ноль выглядит
как достоверное число, а не как ошибка.

Три места (все проверены заказчиком лично):
- `report.rs:1618` — доля канала: `=B{row}/B${total}`
- `report.rs:1623` — итоговая сумма: `=SUM(B4:B{total_row})`
- `claude.rs:959` — SUM по числовому столбцу в выгрузке переписки

## План
1. Найти в исходниках крейта `rust_xlsxwriter-0.79.4` (кэш cargo) точную сигнатуру метода
   `Formula::set_result` — не по памяти, а фактически.
2. Проставить вычисленный результат при записи каждой из трёх формул, используя уже готовые
   переменные из окружающего кода (не пересчитывать значения другим путём).
3. Формулу не убирать — оставить живой для пересчёта в Excel, только добавить кэш.
4. Хирургическая правка: только точки формул, ничего соседнего не трогать.
5. Гейт: `cargo check` (с `CARGO_TARGET_DIR="D:/cargo-targets/ai-agency"`) = 0.
6. Доказательство: unit-тест в стиле уже существующих в файле (`build_xlsx` → запись во
   temp-файл → распаковка как zip → чтение XML листа), краснеющий без правки и зеленеющий
   с ней. Порт 7529 (движок программы) не трогать.

### Точная сигнатура метода библиотеки
Найдена в исходниках `rust_xlsxwriter-0.79.4` (кэш cargo,
`C:\Users\ackol\.cargo\registry\src\index.crates.io-1949cf8c6b5b557f\rust_xlsxwriter-0.79.4\src\formula.rs:832`):
```rust
pub fn set_result(mut self, result: impl Into<String>) -> Formula
```
Builder-метод, потребляет `self`, возвращает `Formula`. Значение — строка (число нужно
переводить через `.to_string()`). Используется как `Formula::new(...).set_result(...)`.

### Как доказала, что число реально попадает в файл
Написала 2 unit-теста (по одному на файл, в стиле уже существующих в файле — вызов
продуктовой функции → запись во временный xlsx → распаковка как zip → чтение XML листа,
приём как в соседних тестах `glossary_from_frontend_extraction` и др.):
- `report.rs::tests::waterfall_formula_results_are_cached_not_zero`
- `claude.rs::tests::convert_to_xlsx_sum_formula_result_is_cached_not_zero`

Оба сначала прогнаны на реальном XML через зонд-тест (временный, потом заменён на
финальный) — увидела фактический формат кэша библиотеки: `<f>B4/B$6</f><v>0.3</v>` и
`<f>SUM(B4:B5)</f><v>1000</v>` — не предположила, а прочитала.

Затем по правилу «проверяй след, а не рапорт» проверила оба направления вручную:
1. **RED без правки** — временно откатила `.set_result(...)` в обоих файлах (только код
   правки, тест не трогала), прогнала тесты → оба упали с падением ассерта на
   `<f>SUM(B4:B5)</f><v>0</v>` / `<f>SUM(B2:B4)</f><v>0</v>` (дословно тот дефект, что
   описан в задаче).
2. **GREEN с правкой** — вернула правку, прогнала снова → оба зелёные.
3. Финальный совместный прогон: `cargo test --lib -- commands::report:: commands::claude::`
   → **73 passed; 0 failed** (весь набор тестов обоих файлов, не только новые два —
   ничего соседнего не сломано).
