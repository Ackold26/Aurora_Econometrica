# PROBE — порядок приёма файла vs записи media_plan.json (2026-09-08)

## 1. Порядок — доказанный ответ

**"Принятие" файла и "проверка" — это ОДИН и тот же вызов.** Отдельного шага
«скопировать файл пользователя в каталог проекта ДО проверки» в текущем UI-потоке
не существует: `validate_data` читает файл напрямую с ВНЕШНЕГО пути, выбранного
пользователем в системном диалоге, и этот путь никогда не копируется внутрь
`<project_dir>` ни до, ни после проверки.

Цепочка вызовов, файл:строка:

1. `src/lib/components/pipeline/ImportStep.svelte:265-333` (`pickFile`/`loadFile`) —
   пользователь выбирает файл через `@tauri-apps/plugin-dialog` `open()`. Результат —
   абсолютный ВНЕШНИЙ путь (например, `C:\Users\...\Downloads\file.xlsx`). Вызывается
   `econ_data_preview` (только предпросмотр первых строк, ничего не пишет в
   `project_dir`) и `importData.set({..., file: path, ...})` — в стор кладётся ТОТ ЖЕ
   внешний путь, копии в каталог проекта нет.
2. `src/lib/components/pipeline/ValidateStepV13.svelte:230-244` (`autoRunValidate`) —
   вызывает `invoke('econ_validate', { filePath: imp.file, projectDir: projectId })`.
   `imp.file` — тот же внешний путь из шага 1.
3. `src-tauri/src/commands/econometrica.rs:183-196` (`econ_validate`) — не копирует файл,
   а просто резолвит `project_dir` (по guard'у от path traversal,
   `resolve_project_dir_arg` :168-181) и пробрасывает `file_path` + `project_dir` телом
   HTTP-запроса в python-сайдкар.
4. `sidecar/econometrica/engines/validator.py:445` (`validate_data`) — открывает файл
   ПО ЭТОМУ ЖЕ внешнему пути (`Path(file_path)`, строки 455-468) и, если чтение прошло
   успешно, в конце (строки 543-549) вызывает `_write_media_plan_state(project_dir, ...)`,
   которая пишет `<project_dir>/results/media_plan.json` (:368-442).

Есть команда `project_upload_data` (`src-tauri/src/commands/project.rs:496-524`),
которая ДЕЙСТВИТЕЛЬНО копирует файл в `<project_dir>/data/<filename>` и прописывает
`data_file` в `project.json` — но **она не вызывается нигде во фронтенде**
(`grep -rn "project_upload_data" src/` — 0 совпадений). Мёртвый код, на текущий поток
не влияет.

**Вывод:** буквальный сценарий «подмена файла в каталоге проекта до проверки»
структурно не реализован — подменять там нечего, каталог проекта не хранит копию
исходных данных. Реальная опасность — другая (см. §3).

## 2. Таблица зонда

Прямой вызов `validate_data()` из `sidecar/econometrica` (без интерфейса), исходный
`results/media_plan.json` перед каждым прогоном восстановлен в состояние «план есть»
(`n_future_periods: 6, confirmed: true, source_hash: PREV_GOOD_FILE_HASH_ABC123` — как
от прошлого УСПЕШНОГО импорта другого файла).

| # | Ранний выход | `validate_data` статус | `media_plan.json` после |
|---|---|---|---|
| а | Путь не существует | `error`, «Файл не найден: ...» | **не тронут**, байт-в-байт как до вызова |
| б | Неподдерживаемое расширение (`.txt`) | `error`, «Неподдерживаемый формат: .txt» | **не тронут** |
| в | Битое чтение (`.xlsx` с мусорным бинарным содержимым) | `error`, «Ошибка чтения файла: Excel file format cannot be determined...» | **не тронут** |
| г | Пустой `.csv` (0 байт) | `error`, «Ошибка чтения файла: No columns to parse from file» | **не тронут** |

Во всех 4 случаях `media_plan_json_unchanged = True` (побайтовое сравнение до/после).
Файл не удаляется, не создаётся заново — старое содержимое переживает попытку.
(Скрипт зонда и артефакты: `C:\Users\ackol\AppData\Local\Temp\claude\...\scratchpad\probe_validate.py`,
временный проект `...\scratchpad\probe_mediaplan_2026-09-08\`.)

Замечание: заявленный в задаче сценарий «пустой .csv» на практике попадает в ветку
`except Exception as e: return {'Ошибка чтения файла: {e}'}` (строка 467-468,
pandas бросает `EmptyDataError` раньше проверки `n_cols == 0`), а не в отдельную
ветку «Файл пуст» (validator.py:475-480, тоже без записи state — тот же результат,
пятый ранний выход с тем же поведением).

## 3. Вердикт

**Опасно, но при УЖЕ подтверждённом уровне риска у самих разработчиков** — правка от
2026-09-08 (см. комментарий в `validator.py:376-381`, "аудит High-2") как раз чинила
соседний баг того же класса (файл писался, только если хвост НАЙДЕН, и никогда не
обнулялся). Текущий зонд показывает: чинили не всё дерево ранних выходов, а только
путь "успешное чтение → нет хвоста". Четыре более ранних выхода (нет файла,
неподдерживаемый формат, битое чтение, пустой файл) остаются нетронутыми симметрично
старому багу.

**Конкретный сценарий, при котором признак солжёт:**

1. Пользователь на шаге «Валидация» успешно проверяет файл `plan_v1.xlsx` с реальным
   медиапланом на 6 будущих периодов → `media_plan.json` пишется
   `{n_future_periods: 6, confirmed: true}`.
2. Позже пользователь возвращается на шаг «Импорт» ТОГО ЖЕ проекта и выбирает ДРУГОЙ
   файл — например, случайно берёт битый/повреждённый экспорт из Excel, или файл с
   пустым содержимым (частая ошибка: сохранили пустой шаблон вместо заполненного).
   `ImportStep.svelte:279` (`isReimport`) спрашивает подтверждение сброса ТОЛЬКО если
   шаг 2 (декомпозиция/обучение модели) уже завершён — если нет, `resetDownstream`
   вообще не вызывается, и `filePath`/`importData` просто переписываются на новый файл
   без предупреждений.
3. `autoRunValidate()` вызывает `econ_validate` на битом файле → `validate_data`
   попадает в один из 4 ранних выходов → возвращает `status: error` → фронтенд
   показывает пользователю ошибку и блокирует шаг («Ошибка чтения файла...»).
   **Но** `results/media_plan.json` на диске остаётся ПРЕЖНИМ — всё ещё
   `{n_future_periods: 6, confirmed: true, source_hash: <хэш plan_v1.xlsx>}`.
4. `media_plan_absent(project_dir)` (`sidecar/econometrica/engines/optimizer.py:267-291`)
   — единственная точка чтения этого файла на стороне движка при оптимизации/
   декомпозиции — читает `results/media_plan.json` **напрямую с диска, независимо от
   текущего состояния фронтенда**. Если пользователь (или отложенный/повторный вызов
   пайплайна на этом же `project_dir`, например через прямой invoke без прохождения
   UI-гейта шага 1) дойдёт до decompose/optimize, минуя повторную успешную валидацию —
   движок увидит `media_plan_absent = False` и посчитает, что «план на 6 периодов
   подтверждён», хотя ни один принятый файл в проекте сейчас такого плана не содержит:
   последняя ПОПЫТКА импорта провалилась, а признак говорит о позапрошлом файле.

Практический вес риска — **средний, не критический**: штатный UI-гейт (`setStepError`
на шаге 1) в норме не даёт продолжить пайплайн без успешной валидации, поэтому
эксплуатация требует либо прямого вызова команд в обход UI, либо прочтения
`media_plan.json` сторонним кодом (уже есть один такой потребитель — `optimizer.py`).
Правильное исправление — то же средство, что уже применено для ветки «нет хвоста»:
на ЛЮБОМ раннем выходе `validate_data` тоже вызывать `_write_media_plan_state` с
`tail_found=None` (честное «определить не удалось», как для отказавшего исключения
внутри try/except на строке 539-541), а не оставлять файл молчаливо описывать данные
позапрошлого импорта.
