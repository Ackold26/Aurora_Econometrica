# Следующая сессия — докачка по частям (пункт 2): сервер, затем клиент

> Скопируй этот файл в начало новой сессии. **cwd = `D:\Docs\Aurora_Ai\Dev\Aurora_Econometrica_thinwt`** (worktree тонкой редакции, ветка `feat/econ-thin-client`, запушена).

## Зачем (одним абзацем, доказано боем 26.07.2026)

Живая приёмка 2.4.1 на машине клиента (PC204, «Сони») показала: наши повторы и раздельные таймауты работают, но **не лечат** — сеть клиента обрывает **порционный ответ примерно после 4 КБ**. Файлы 2,0–2,9 КБ доходят все, файлы 20 КБ (пакет контента) и 34 КБ (`econometrist.vault`) не доходят **никогда**: 10 обрывов из 10 на 3251, 4278, 4278, 4279, 5645, 5647, 5647, 5649 байт. Разброс узкий, повторяемость полная — это порог посредника (проверка защищённых соединений антивирусом или шлюз организации), а не помехи.

Наша функция `/content` отдаёт файл **порциями без заявленной длины** (`Transfer-Encoding: chunked`, `Content-Length` отсутствует — видно и снаружи зондом, и в журнале клиента как «сервер обещал неизвестно»). Обходного пути у клиента нет: на запрос части функция отвечает файлом целиком (200 вместо 206) — проверено зондом.

**Ручная передача файла клиенту отвергнута владельцем как несистемная** («не развернёшь на потенциальных клиентов»). Решение — докачка по частям.

## Работа

### Часть A — сервер (главное лечение)

1. Выгрузить текущий код функции: `supabase functions download content --project-ref quzhkfvglqmppxcrindh` (CLI лежит в `C:\Tools\supabase\supabase`). Локальных исходников этой функции в репозиториях **нет** — сначала выгрузка, потом правка.
2. Переписать отдачу файла:
   - читать объект из хранилища целиком в память (файлы — единицы–десятки КБ, это дёшево) и отдавать с **явным `Content-Length`**, без порционной передачи;
   - поддержать заголовок `Range: bytes=N-M` → ответ **206** с корректным `Content-Range: bytes N-M/ПОЛНЫЙ`;
   - `Accept-Ranges: bytes` в ответе;
   - некорректный диапазон → **416**;
   - сохранить существующую проверку лицензии по `fingerprint_hash` и текущие коды ошибок.
3. Задеплоить и **проверить зондом снаружи** (не поверить деплою на слово):
   ```bash
   U="$SUPABASE_URL/functions/v1/content?fingerprint_hash=493288e1961cca7a6902a77aefc98ce904cc745c01d66fd8cda0ab5528efce72&product=econometrica&version=c3&file=econometrist.vault"
   curl -s -D - -o /dev/null "$U" | grep -iE "^HTTP|content-length|accept-ranges|transfer-encoding"
   curl -s -D - -o /dev/null -H "Range: bytes=0-1023" "$U" | grep -iE "^HTTP|content-range|content-length"
   ```
   Ждём: первый — `200` + `Content-Length: 34165`, без `chunked`; второй — `206` + `Content-Range: bytes 0-1023/34165` + `Content-Length: 1024`.

### Часть B — клиент

4. `content_updater.rs`: докачка кусками для материалов кабинета и пакета контента. Размер куска — **1–2 КБ** (ниже порога клиента), склейка в памяти, сверка итога с полным размером из `Content-Range`, повторы уже есть. Готовый образец рядом: `updater.rs::download_attempt` (Range + `.part` + отклонение противоречивого `Content-Range`, порт Oracle).
5. Тесты: расширить локальный тестовый сервер из `content_updater.rs` сценарием «сервер режет соединение после N байт» — доказать, что кусками файл собирается целиком, а без Range — нет.
6. Заодно починить **дребезг вызовов** (найден в том же журнале): при старте уходит по 4–6 одновременных запросов авторизации и по 4 параллельные загрузки одного файла. В загрузчике установщика защита уже есть (`in_flight_downloads`) — перенести на материалы кабинета.

## Что НЕ делать

- Не «увеличивать таймауты» и не наращивать число повторов — порог от этого не сдвинется, доказано десятью попытками подряд.
- Не считать задачу закрытой по зелёным тестам: закрывает её только живая приёмка на машине клиента.
